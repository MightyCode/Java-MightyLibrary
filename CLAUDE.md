# CLAUDE.md — Java-MightyLibrary

Moteur de jeu 2D/3D en Java 11 (LWJGL 3.3.6, OpenGL 3.3 core, GLFW, OpenAL, STB, Assimp ; JOML, org.json, JBox2D). Trois modules Maven (`mightylib`, `mightylib-test`, `demo`) sous un pom parent, plus trois poms de configuration (`bom/`, `base-parent/`, `game-parent/` : versions, build commun, parent des jeux dont hérite la démo) : `mightylib/` = la bibliothèque (`io.github.mightycode.mightylib`), `mightylib-test/` = le kit de test des jeux (`io.github.mightycode.mightylib.test`, portée `test` des jeux, classpath seulement), `demo/` = la démo qui sert de banc d'essai (`io.github.mightycode.mightylibdemo`), qui en dépend comme un projet externe. Objectif : en faire une bibliothèque réutilisable (jar) pour les futurs jeux et logiciels de l'utilisateur.

## Priorités
- **La 2D est prioritaire** (rendu 2D, tilemaps, texte, GUI, Camera2D, animations, physique 2D).
- **La 3D est secondaire** : ne pas l'étendre ni la refactorer sans demande, mais ne pas la casser (`Mesh`/`Renderer`/`Shader` sont communs ; les scènes 3D `Scene3D`, `Scene3DBis`, `Game3D2D` et `TerrainGeneration3D` doivent rester fonctionnelles).

## Build et vérification
- Maven multi-module (pom parent à la racine, modules `mightylib`, `mightylib-test` et `demo`, poms `bom`, `base-parent` et `game-parent`) : sources en `<module>/src/main/java`, tests JUnit 5 en `<module>/src/test/java` (mêmes packages que le code testé, pour accéder au package-private) ; les fichiers des tests de la bibliothèque sont dans `mightylib/src/test/resources`, lus par le classpath (`TestFiles`). Commandes depuis la racine. Compiler après chaque modification :
  - Linux : `mvn`/`java` (JDK 21) sont dans le PATH : `mvn -o -q compile`.
  - Windows : `mvn`/`java` ne sont pas dans le PATH, utiliser les outils d'IntelliJ :
    ```bash
    JAVA_HOME="$HOME/.jdks/ms-21.0.9" "/d/Program Files/JetBrains/IntelliJ IDEA Community Edition 2024.2.3/plugins/maven-plugin/lib/maven3/bin/mvn" -o -q compile
    ```
  - Tests : même commande avec `test` au lieu de `compile` (quelques secondes ; les tests tagués `gl` ouvrent une fenêtre cachée, `-DexcludedGroups=gl` les écarte). Un seul module : `-pl <module> -am` (sans `-am`, les autres modules viennent du dépôt local, peut-être périmés).
  - `package` au lieu de `compile` : la démo est compilée et testée contre les jars de la bibliothèque et du kit (vérification que la bibliothèque se suffit) ; à lancer quand les poms (dont `bom`, `base-parent`, `game-parent`, `mightylib-test`) ou la frontière bibliothèque/démo changent.
  - `scenario.py` choisit ces chemins selon l'OS (surchargeables par `MIGHTY_JAVA`, `MIGHTY_MVN`, `MIGHTY_MAVEN_JDK`). Sur une nouvelle machine, lancer une fois `mvn -q compile` (sans `-o`) pour télécharger les dépendances, et `python tools/demo_assets.py` pour le paquet de démonstration (modèle de `Scene3D`, hors de git).

## Règles pour Claude
- **Philosophie du moteur** (`docs/decisions.md`) : classes de base simples + implémentations concrètes proposées + injection ; l'utilisateur final utilise les classes déjà implémentées, ou hérite + injecte les siennes ; l'usage courant reste facile (« simple » = niveau d'usage de Processing) et la réimplémentation (presque) complète reste possible. Bases sans hypothèse sur un jeu précis, points d'accroche choisis, rien de propre à la démo dans la bibliothèque ; signaler tout système qui impose une implémentation en dur.
- **Penser à long terme, à l'échelle d'un vrai jeu** (des milliers de ressources, chargement en continu, nombreuses scènes, mods, projets tiers), pas à celle de la démo : une solution qui suffit à la démo mais ne tiendra pas à cette échelle doit être signalée comme telle, avec la cible durable, et inscrite dans `docs/current.md` ou `docs/later.md`. Préférer corriger le modèle qui produit les bugs plutôt qu'empiler des pansements.
- **Économiser les tokens** : lire des extraits (Grep, Read avec offset/limit) plutôt que des fichiers entiers ; filtrer les journaux ; réponses courtes ; pas de capture d'écran sauf rendu impossible à vérifier autrement (une seule à la fois, et seulement la zone utile avec `screenshot --rect x y largeur hauteur` ou `--corners x y x2 y2` quand on sait où regarder ; cadrer avec la commande `camera`) ; si une information manque, ajouter une commande qui la renvoie en texte/JSON.
- Ne jamais importer `io.github.mightycode.mightylibdemo.*` depuis `mightylib` (passer les IDs en paramètre).
- Tout code GL s'exécute sur le thread principal (y revenir par `MainThread.execute`) ; les tâches de `Workers` (dont les workers de `Resources`) ne font que de l'I/O/CPU. Pas de `new Thread` pour une tâche courte : utiliser `Workers`. Toujours créer/détruire les objets GL via `GenDeleteResources`.
- Toute ressource GL créée dans une scène est libérée dans `unload()` (ce que `launch` a créé) ou `release()` (ce que `init` a créé : `unload` n'est pas appelé si la scène est quittée pendant son chargement) ; vérifier l'état CPU des ressources avec la commande `resources` ; vérifier les fuites avec l'étape `leakcheck <Scène>` de `scenario.py` (voir `docs/debug-tools.md`).
- Fins de ligne normalisées par `.gitattributes` (LF dans le dépôt) : `git add` normal. Ne pas réécrire de fichier source avec `sed` (utiliser Edit).
- Git : `dev` est la branche de travail, `master` ne reçoit que des versions finies. Une branche de sujet depuis `dev`, fusionnée dans `dev` par `/pr-ml` (PR GitHub, commit de fusion, pas de squash) ; `dev` → `master` seulement quand l'utilisateur demande explicitement une nouvelle version (« commite », « livre », « pousse » ne suffisent pas), et toujours en lui demandant d'abord son numéro : `git merge --no-ff dev -m "Merge branch 'dev' for version X.Y.Z"` puis tag annoté `git tag -a vX.Y.Z -m "Version X.Y.Z"` sur cette fusion (pousser avec `--follow-tags`). Un commit par changement logique, avec la ligne `Co-Authored-By` demandée par le système. Ne pas modifier/commiter `target/` ni `.idea/workspace.xml`. Les autres fichiers de `.idea/` modifiés par IntelliJ (`compiler.xml`, `inspectionProfiles/`, `misc.xml`…) : les commiter sans demander, dans un commit à part (`IDE: …`) sur la branche en cours, et ne pas en parler à l'utilisateur.
- **Fin de chaque objectif : nettoyer les docs dans le même commit, ou dans un commit de docs sur la même branche avant la fusion.** `current.md`/`later.md` = ce qui reste, jamais l'historique : supprimer la ligne de l'objectif atteint (ou la réduire à son reste), sans « fait ». Décrire le nouvel état dans `architecture.md` (au présent, sans historique). Relire le fichier après modification : plus aucune trace de ce qui est fini.
- Un bug existant découvert hors du sujet en cours : le noter dans `docs/later.md` ou `docs/futur-discussion.md` (et le signaler), pas le corriger en douce.
- Avant de commencer un gros point (passage de `later.md` à `current.md`), en discuter avec l'utilisateur pour s'assurer que tout est prévu (`/planification-ml`).
- **Point hebdomadaire** : une revue des bonnes pratiques (`/revue-pratiques`) par semaine. Dernière revue : **2026-11-22**. Au début de toute nouvelle discussion, si la dernière revue date de 7 jours ou plus, le rappeler à l'utilisateur (une ligne) avant de commencer. Après chaque revue, mettre à jour cette date.
- **Analyses automatiques, pendant la revue hebdomadaire** : `python tools/analyse.py` (Error Prone + SpotBugs) et `python tools/coverage.py` (JaCoCo) font partie de la revue ; on analyse leurs résultats puis on choisit les actions à mener (corrections par thème, tests à ajouter), sans date ni rappel à part.
- Décrire comment vérifier manuellement ce qui n'a pas pu l'être (quelle scène, quoi observer).

## Conventions de code
- Java 11 (pas de `record`, ni de `switch` expression). Accolades K&R, 4 espaces, commentaires en anglais, peu de Javadoc, sauf une Javadoc courte sur chaque accroche d'une classe extensible (quand elle est appelée, ce qu'elle peut faire, ce qu'elle doit appeler).
- API publique (`docs/architecture.md`, « API publique ») : une nouvelle classe publique concrète est `final`, sauf classe extensible déclarée dans `ExtensibleClasses` (accroches documentées, aucun champ `protected`) ; un nouveau package a son `package-info.java` avec son statut `@API` (`STABLE`, `EXPERIMENTAL`, `INTERNAL`) et, s'il n'est pas `internal`, son `exports` dans `mightylib/src/main/java/module-info.java` ; un type public utilisé seulement par un autre package de la bibliothèque va dans le package `<propriétaire>.internal` (statut `INTERNAL` par son `package-info`) ; seul un membre d'un type exporté s'annote `@API(status = INTERNAL)`.
- **Code propre pour IntelliJ, Error Prone et SpotBugs dès l'écriture** : avant de commiter, relire son diff avec la liste du point 14 de `docs/bonnes-pratiques.md` (imports, `@Override`, `default` de `switch`, interfaces dans les signatures, `entrySet`, compteurs `Atomic*`, pas de `catch` vide, `requireMainWindow`…). Un cas voulu se déclare avec sa raison (`//noinspection`, `.idea/inspectionProfiles`, `tools/spotbugs-exclude.xml`, `-Xep:…:OFF` du `pom.xml`, mot dans `.idea/dictionaries/project.xml`), jamais en silence. Pas de `mvn clean` à la racine : il efface l'export IntelliJ de `target/analyse`.
- Enums préfixées `E`, interfaces préfixées `I` ; utilitaires statiques souvent en PascalCase (`GenDeleteResources.GenBuffers`, `Logger.CheckOpenGLError`).
- Appel GL sensible suivi de `Logger.CheckOpenGLError("message")` ; dans le code appelé à chaque dessin, l'entourer de `if (Logger.isGLErrorCheck())`.
- Logs moteur : `System.out/err.println` avec préfixe `--`. Exception inattendue mais gérée : `Logger.LogException(message, e)` (jamais `printStackTrace()`) ; échec attendu d'une ressource : `ResourceException` (une ligne). `InterruptedException` : remettre le drapeau (`Thread.currentThread().interrupt()`) et s'arrêter.
- Toute nouvelle commande déclare son identifiant (espace de noms de son propriétaire), son niveau (`USER`/`CHEAT`/`DEV`), sa description et sa syntaxe déclarée (`syntax(racine)` : arguments typés, options `--nom`, descriptions, niveau et condition par branche ; la complétion, l'aide et l'analyse en sortent), et répond par un `message` lisible pour son niveau (le détail pour le développeur dans les `data`) ; voir `docs/debug-tools.md`, section Commandes.
- Pour tester une fonctionnalité, ajouter une scène de démo plutôt que modifier une existante. Nom sans préfixe `Test`, dimension en fin de nom (un nom Java ne commence pas par un chiffre) : `DisplayModesScene`, `RopeSimulation2D` ; l'ajouter à `DemoScenes` avec sa description (un test le vérifie) : elle apparaît alors dans le menu et pour la commande `scene`.
- **Toute scène 2D de la démo se pilote à la caméra** : `DemoCamera.free(this)` au début du `launch` (Z Q S D en AZERTY et flèches, Maj = vitesse double, clic droit glisser, molette = zoom ; `DemoCamera.free(this, ActionId.MIDDLE_CLICK)` si la scène utilise le clic droit). Une scène qui avait besoin de ces touches recule les siennes (jamais l'inverse) et met à jour son aide ; ses textes et son interface fixes à l'écran utilisent `setReferenceCamera` avec une copie de `camera2D()` prise au `launch`. Seules exceptions : saisie de texte, interface fixe, jeu où le joueur utilise ces touches (`TextFieldScene2D`, `GUIWidgetsScene`, `PlatformerBox2D`), et les écrans de menu, de chargement ou de test d'entrées. Vérifier dans chaque nouvelle scène : `input key hold D`, `input scroll 3`, `?camera` (`docs/architecture.md`, « Caméra 2D pilotée »).

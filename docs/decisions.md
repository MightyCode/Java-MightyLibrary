# Décisions durables

- **Placeholders pour les seules données primaires** (texture, son, shader, police, animation, modèle) : une erreur de ressource ne fait pas tout planter, en debug comme chez le joueur. Données complexes (cartes, JSON, règles…) → `null`, un placeholder y cacherait l'erreur. Placeholder voyant/audible (damier magenta, bip), aussi pendant le chargement. Mode strict = exception, pour les tests et `scenario.py`.
- **Mode `DEBUG`/`RELEASE`** (`EEngineMode`) plutôt qu'un état « admin ».
- **Package `network` conservé** malgré `ServerThread.run()` vide.
- **Pas de Lombok** : peu d'accesseurs triviaux, méthodes générées introuvables dans le source, processeur d'annotations à configurer, API publique implicite.
- **Envoi des textures : `DIRECT` par défaut, `PBO` en option** (`ETextureUpload`). Mesuré sur RTX 4080 SUPER (pilote 610.88), 4096x4096 : direct 8 ms au total ; PBO 3 ms dans les appels mais 36 ms jusqu'à la fin du transfert. Sur Scene3D l'envoi entier (128 Mo) ne coûte que ~15 ms, rien à gagner là. Le résultat dépend de la carte : `textureupload bench` le mesure chez l'utilisateur.
- **Packages `io.github.mightycode.mightylib` / `…mightylibdemo`** (compte GitHub `MightyCode`, accepté par Maven Central). Passer à `fr.<domaine>.mightylib` avec une entreprise et un produit fini, avant toute publication sur Maven Central.
- **Décodeurs de sons : mp3 par JLayer (LGPL), le reste sans LGPL** : ogg = STB Vorbis (LWJGL), wav = `javax.sound.sampled` (JDK), flac = décodeur écrit pour le moteur (`FlacStream`, vérifié par le MD5 du fichier), mp3 = JLayer (LGPL), JavaMP3 (MIT) plantant sur un mp3 tronqué. Obligations de la LGPL : `licence.md`. Tout autre format : un `SoundDecoder` de plus.
- **`Engine` unique par processus, vue courante plutôt que singletons** : GLFW et le périphérique son n'existent qu'une fois par processus, mais tout le reste (`Resources`, `GLResources`, shaders, sons, fenêtres) est porté par une instance d'`Engine`, ce qui rend le multi-fenêtre et les tests possibles sans état global. Le code d'une scène crée ses objets sans paramètre (la vue courante) ; un worker n'a pas de vue : échec explicite plutôt qu'un repli silencieux sur la fenêtre principale (un objet GL créé dans la mauvaise fenêtre est un bug dur à trouver). Restent statiques : `MainThread`, `Workers`, `GameTime`, `Logger.DO_CHECK`, mode du moteur.
- **`Context` = une scène et ses fenêtres, `WindowContext` = une fenêtre** : un jeu a un contexte, un logiciel peut en ouvrir d'autres (fenêtres indépendantes avec leurs scènes) et des sous-fenêtres (dialogues, outils) dessinées par une `WindowView`. Tous partagent ressources, textures, buffers et programmes par un contexte GL racine caché ; seuls VAO, FBO et RBO sont propres à une fenêtre (`Shape` recrée son VAO à la demande, un `FrameBuffer` reste dans sa fenêtre). Un dialogue modal bloque les entrées de ses parents (pas de verrou natif) ; une sous-fenêtre appartient à la scène qui l'ouvre.
- **Commandes : trois niveaux qui ne sont pas une sécurité** (`USER` joueur, `CHEAT` triches, `DEV` développeur et moddeur) : en local, le joueur possède sa JVM et ses fichiers ; les niveaux délimitent ce qui est visible et évitent les erreurs. En réseau, le serveur décidera. Pas de niveau `MODDER` tant que les mods n'ont pas de besoins propres (l'enum ordonnée permet de l'insérer entre `CHEAT` et `DEV`). Niveau obligatoire dans le constructeur (un oubli est une erreur de compilation, pas une commande invisible). Refus silencieux : une commande hors niveau n'existe pas pour la source. La triche est choisie par le jeu (plafond du build, commande `cheats` optionnelle ou `setSessionLevel`), le moteur n'impose aucune règle de sauvegarde. La sortie du programme n'est visible qu'en `DEV` ; un joueur ne voit que ses commandes, leurs messages et ceux du jeu.
- **Commandes à propriétaire, calquées sur les fenêtres** : moteur, jeu ou vue ; celles d'une vue s'exécutent sous elle et partent avec elle (comme `closeWindowsOpenedBy`), y compris quand la scène est quittée pendant son chargement. Une commande déclare elle-même l'état dont elle dépend (condition `requires(CommandCondition.launched(scène))` dans sa syntaxe) plutôt que le moteur ne bloque les commandes d'une scène en chargement.
- **Syntaxe des commandes : arbre maison plutôt que Brigadier** : pas de dépendance (la bibliothèque doit rester légère, `licence.md` inchangé), des options nommées `--nom valeur` que Brigadier n'a pas, des messages d'erreur et des niveaux (`USER`/`CHEAT`/`DEV`, refus identique à un mot inconnu) à adapter de toute façon. Le schéma est du code Java chaîné (aucune réflexion, aucune évaluation de texte) : un jeu ou un mod écrit ses propres `ArgumentType`.
- **Options `--nom` sans alias courts** : `-s` entrerait en collision entre le moteur, le jeu et les mods qui ajoutent des options aux mêmes commandes ; un nom long est lisible dans les scripts et complété par Tab.

# Outils de debug et de mesure

## Commandes (registre de l'`Engine`, accès selon le niveau)
- **Accès** : en debug, tout (niveau `DEV`) : console en jeu (`²`), entrée standard et serveur de debug. En release, aucun par défaut (`EngineConfig.setCommandAccess`, `setMaxCommandAccess`, `setCheatCommand` ; option `-Dmightylib.commands.access=none|user|cheat|dev`, bornée par le plafond du build ; un jeu sans console du tout : `setMaxCommandAccess(null)`, l'option est alors ignorée). Détail : `architecture.md`, section **Commandes**. Démo : `-Ddemo.release=true` (release, accès `USER`, plafond `CHEAT`), `-Ddemo.commands.max=none|user|cheat|dev` ; avec `scenario.py` : `-D mightylib.commands.access=user -D demo.commands.max=cheat` (la console en jeu est au niveau joueur, le serveur reste `DEV` ; pour voir ce que voit le joueur : `as user <ligne>` et `complete --as user "<début>"`, pas la console pilotée par `input`).
- `help` : identifiant, propriétaire (`engine`, `plugin <espace>`, `scene`, `window`) et description des commandes visibles par la source ; `help <cmd>` ou `<cmd> --help` : description, une ligne d'usage par branche, arguments et options (`--help` marche n'importe où sur la ligne, même après une erreur, sauf après `--`). Les `data` de `help <cmd>` contiennent l'arbre visible en JSON (`id`, `level`, `description`, `branches` : `usage`, `description`, `arguments` `{name, type, optional, variadic, values?}`, `options` `{name, values, repeatable, default?}`). Le serveur de debug, l'entrée standard et `api` sont au niveau `DEV` : ils voient tout.
- Découpage (`CommandLine.Split`) : espaces ; guillemets doubles pour un mot avec espaces ; `\` gardés (chemins Windows) ; guillemet non fermé = erreur. Dans `scenario.py` : `'screenshot "target/a b.png"'`.
- `Commands.submit(line, source)` depuis tout thread, exécutée au début du tick suivant (`processPendingCommands`) ; source (`ICommandSource` : `game`, `stdin`, `server#N`, `api` par défaut) donnée par `getCurrentSource()` et son niveau par `getCurrentLevel()` pendant l'exécution ; les `ICommandListener` reçoivent chaque commande soumise et son résultat, avec le niveau de la source au moment de l'exécution, ou le niveau plus bas qu'elle a ensuite si la commande l'a baissé (`cheats off` : `lowered`, puis la réponse à ce niveau, pour que le joueur voie encore la ligne ; `CommandEcho` les écrit dans le journal de la console et baisse alors le niveau de la ligne déjà écrite, `ConsoleLog.lower`). Entrée standard lue dans un thread à part (mode debug).
- **Écrire une commande** (package `utils/enginecommand/syntax`) :
  - `BaseCommand(Identifier, ECommandLevel, description)` : espace de noms du propriétaire (`mightylib`, le jeu, le mod), niveau minimal et description (première ligne de l'aide), tous obligatoires. Enregistrement : `registry.commands().register(commande)` dans `IPlugin.register` (jeu, mod : identifiant de l'espace du plugin, figée ensuite ; deux plugins → `IllegalStateException` nommant les deux, `replace` pour remplacer), `Scene.addCommand` dans `init` (existe pendant le chargement), `WindowView.addCommand`. Identifiant déjà pris entre vues → `IllegalArgumentException`, sauf entre deux vues différentes (même scène dans deux fenêtres) : choisir la fenêtre avec `window`.
  - `syntax(CommandNode racine)` (abstraite, appelée une fois au premier enregistrement : les champs qu'elle utilise sont posés par le constructeur ; une erreur de schéma est une `IllegalStateException` à l'enregistrement) déclare les branches : `racine.executes("…", ctx -> …).then(literal("mode", "…").then(argument("mode", choice("poll", "service"), "…").option(Option.of("interval", "…").value("ms", longValue(1, 60000)).defaultValue(1000L)).executes(ctx -> …)))`. Imports statiques : `Arguments.*`, `CommandNode.literal`, `CommandNode.argument`. Règles : toute branche s'exécute ou continue ; un argument variadique, `text` ou `commandLine` est le dernier de sa branche ; une option répétable n'a pas de valeur par défaut ; après un argument facultatif (`.optional()`) seulement des facultatifs ; noms d'arguments et d'options uniques sur une branche.
  - **Convention** : positionnels = ce que la commande vise (sous-commande, cible, valeur principale) ; options = réglages facultatifs (`watch mode poll --interval 500`, `wait loaded --timeout 10`, `screenshot [chemin] --rect x y l h --scale 0.5`). Options `--nom valeur` ou `--nom=valeur`, drapeaux `--nom`, `--` termine les options ; noms en minuscules kebab, pas d'alias courts (collisions entre moteur, jeu et mods) ; `--help` est ajoutée par le moteur. Les littéraux passent avant les arguments au même niveau ; les arguments d'un même niveau sont essayés dans l'ordre, sans retour en arrière.
  - **Types** (`Arguments`) : `integer`, `longValue`, `decimal` (bornes facultatives), `bool`, `word`, `text` (le reste de la ligne, mots joints par une espace ; un texte commençant par `--` s'écrit après `--`), `commandLine` (idem, mais plusieurs mots sont rejoints entre guillemets pour être redécoupés : `as`, `complete`), `choice`, `enumOf(Classe)`, `oneOf(Supplier)` (valeurs dynamiques, strict), `suggest(Supplier)` (proposées, libres), `identifier`, `path([dossier])`. Un type maison implémente `ArgumentType` (`parse` lève `CommandSyntaxException.expected("un entier…", mot)`, `complete(début, ctx)` lit les arguments précédents par `ctx.get(...)`) : ex. `resources/internal/ResourceArguments` (`type`, `names`, option `--regex`, branches `selection(…)` de `reload`, `resources`, `watch`).
  - **Handler** (`ICommandHandler`) : reçoit un `CommandContext` (`get`, `getOr`, `has`, `getList` pour un variadique ou une option répétable, `currentLevel()`, `source()`, `commandName()` ; option à plusieurs valeurs → `List`, drapeau → `true`) et **renvoie** `CommandResult.ok(message, data JSON)`/`error(...)`, sans écrire en console ; résultat différé : `CommandResult.later(future)` (abandon après `Commands.COMMAND_TIMEOUT_SECONDS` = 30 s). Le `message` est une phrase lisible par le joueur ; les `data` sont le détail pour le développeur (journal : `DEV` seulement). Une `CommandException` donne sa réponse d'erreur telle quelle.
  - **Niveau et condition par branche** : `.level(ECommandLevel.DEV)` sur un nœud ou une option : absent de la complétion, de l'aide et du JSON pour les niveaux inférieurs, avec l'erreur d'un mot inconnu (ex. `console log`, `stats` hors `fps`, chemin de `screenshot`, `spawn list`). `.requires(CommandCondition…)` : `hidden(prédicat)` (la branche n'existe pas ; sur la racine, la commande n'existe pas), `check(prédicat, message)` (visible, refus avec message), `launched(scène | () -> scène)` (« Scene still loading » avant le `launch`, sur la racine d'une commande de scène ou de `camera`), `window()` (« No window » sur un moteur démarré sans fenêtre ; à mettre en premier sur la racine d'une commande qui lit une fenêtre, sa scène, ses entrées ou GL ; sans vue courante, `Commands` utilisé seul, elle laisse passer). Les `check` sont évalués à l'entrée du nœud (pour un argument, avant que son type lise le mot ; s'il est refusé, un autre argument du même niveau peut prendre le mot, sinon son message est l'erreur), pas à la complétion : un `Supplier` de valeurs doit supporter une scène en chargement. Les `hidden` de la racine sont évalués sous le propriétaire de la commande (sa vue), comme l'exécution.
- **Complétion** (Tab de la console) : `Commands.complete(début de ligne[, source])` → `CommandCompletion` (début du mot, choix triés sans casse, `replacement()` : le seul choix suivi d'une espace, sinon la partie commune). Noms (chemins, et identifiants des chemins partagés ou une fois `espace:` tapé) des commandes visibles, puis les candidats de la syntaxe : littéraux et valeurs de l'argument attendu, options visibles non encore données et `--help` quand le mot commence par `-`, valeurs de l'option qui attend sa valeur. Les commandes générales complètent leurs sous-commandes et valeurs (actions, axes, touches, boutons de manette, caméras, batchs, ressources, fenêtres, scènes trouvées dans le package des scènes, fichiers pour `exec`).
- **Tester ce que voit le joueur** (sans piloter la console) : `as <user|cheat|dev> <ligne>` exécute la ligne avec le niveau `min(niveau demandé, niveau de la source)` (jamais plus haut ; une commande `DEV` est inconnue sous `as user`) ; `complete [--as <niveau>] "<début de ligne>"` donne dans ses `data` `start`, `typed`, `candidates`, `replacement` de `Commands.complete`, un espace final compris. Les deux sont `DEV` : `as user complete …` n'existe pas, écrire `complete --as user …`. Exemple : `python tools/scenario.py "scene Scene2D" wait-loaded "?complete --as user \"stats \"" "?as user help stats" "?as user screenshot target/x.png"` (le joueur ne voit que `fps`, `screenshot` sans chemin : « Unknown argument »).
- Plusieurs ticks : `Commands.addTickTask` (comparer `Commands.getTick()`, une tâche peut être appelée plusieurs fois par tick).

## Serveur de debug
- `127.0.0.1:7777` (`EngineConfig.setDebugServerPort()`, `-1` = désactivé), sinon port libre suivant ; affiché (`--Debug server listening on …`) et écrit dans `-Dmightylib.debugServer.portFile=<fichier>` (utilisé par `scenario.py` : plusieurs jeux/scénarios simultanés, un `--log` chacun). `--attach`/`mighty.py` : `--port` si pas 7777.
- Protocole : une commande par ligne → une ligne JSON `{"success", "message", "data"}`. Client : `python tools/mighty.py <commande>` (`--wait N`, `--json`, sans argument = interactif).
- Suivi du journal : `console follow on|off` ; le client reçoit aussi, entre les réponses, `{"event": "log", "id", "type": OUT|ERR|COMMAND|RESULT|ERROR|DATA|MESSAGE, "source", "text"}` pour chaque ligne (file de 10 000 lignes par client et thread d'écriture à lui : un client lent ne bloque pas le jeu, l'excédent est perdu). `python tools/mighty.py --follow` : affiche tout le journal (sortie du programme, commandes de toutes les sources et résultats) et envoie les lignes tapées comme commandes.

## Commandes utiles
- `console` (mode : closed, overlay, detached) ; `console open|close|toggle|detach|attach|clear` (`clear` sous `DEV` : vide seulement la console du joueur) ; `console log [n]` (dernières lignes du journal avec leur id et le niveau qui les voit, 20 par défaut) ; `console log since <id>` (lignes suivantes, pour interroger sans suivi) ; `console logs [on|off]` (`DEV`, bascule sans argument : cache ou montre la sortie du programme dans la console, le journal la garde) ; `console data [on|off]` (`DEV`, bascule sans argument : montre ou cache les `data` JSON des réponses dans la console, cachées par défaut ; `-Dmightylib.console.data=shown` pour les voir dès le départ ; les réponses du serveur de debug les contiennent toujours) ; `console copy [n] [--all]` (met dans le presse-papiers les `n` dernières lignes montrées par la console avant la commande elle-même, toutes sans `n`, comme Ctrl+C sur une sélection ; `--all` (`DEV`) ignore le filtre de `console logs off` et `console data off` ; réponse `{lines, chars}`, presse-papiers inchangé s'il n'y a aucune ligne) ; la réponse de `console` sans argument donne aussi `logsShown`, `dataShown`, `scroll` (`"end"` ou `{id, row}`), `newLinesBelow` (lignes sous la vue, 1000 = plus de 999) et `selection` (`null`, `{in: "input", start, end}` ou `{in: "log", from: {id, char}, to: {id, char}}`) ; `console follow [on|off]` (voir **Serveur de debug**).
- `help [commande]` ; `as <niveau> <ligne>`, `complete [--as <niveau>] "<début>"` ; `cheats [on|off]` (si le jeu l'active : `EngineConfig.setCheatCommand`) ; `scene` (courante : `id` si elle est enregistrée, `scene` = sa classe, `loading`) / `scene <nom>` (scène enregistrée par un plugin : identifiant `demo:platformer2d.platformerbox2d`, ou chemin seul sans casse s'il est unique, ex. `platformer2d.PlatformerBox2D` ; ambigu → erreur listant les identifiants ; complétion : les chemins, l'identifiant complet en cas d'ambiguïté) ; `demo:lifecycle` (démo, `DEV` : événements vus par les crochets de `DemoPlugin` : démarrage, changements de scène et dernière scène par contexte, fenêtres ouvertes et fermées) ; `wait <ticks> [--timeout s]` / `wait loaded [--timeout s]` (fenêtre visée au départ ; erreur si elle se ferme pendant l'attente) ; `reload <all|Type> [noms…] [--regex motif]` (sélection vide = 0 donnée, pas une erreur ; `reload ShaderData texture2D` relit et recompile un shader pendant l'affichage, un GLSL cassé garde l'ancien programme avec une ligne de journal) ; `resources [all|Type] [noms…] [--regex motif]` (détail des données choisies, 100 au plus ; `sourceFiles` : chaque chemin logique, la source qui le sert et, pour une donnée multi-fichiers, s'il a été lu, ex. `?resources CubeMapData sky`) ; `resources sources [chemin]` (`DEV` : la pile des sources de la plus basse à la plus haute, propriétaire, disque ou classpath en dossier/jar, observable ; avec un chemin logique complété dossier par dossier, les sources qui l'ont et celle qui le sert, ex. `?resources sources textures/sources/replaced.png` dans `ResourceSourcesScene2D`) ; `resources batch <nom>` (ce que charge un batch : dépendances connues, chargées, mémoire CPU/GPU estimée) ; `resources preload|unpreload <batch>` (précharge un batch, ou annule) ; `watch [status|<all|Type> [noms…] [--regex motif]|mode poll|service [--interval ms]|off]` (rechargement à chaud sur changement de fichier, éteint par défaut, voir `architecture.md`) ; `sounds` (sources : son, état `waiting|playing|paused|stopped|released`, possédée, boucle, son de repli, position lue dans OpenAL, gain propre et final, nœud ; position de l'auditeur) / `sounds gains` (arbre des gains : valeur propre et produit avec les ancêtres) ; `services` (services du moteur dans leur ordre de création : clé, contrat, implémentation, plugin, plugin remplacé, `requires`/`after`, repli utilisé, couche d'overlay ; gestionnaires de scènes et d'entrées et le plugin de leur fabrique ; démo : `EngineServices2D`) ; `exit`. Détail de `resources` : `architecture.md`.
- `problems [--level error|warning] [--last N]` : les ERROR et WARNING envoyés par `Logger` depuis le démarrage (compteurs par niveau et par catégorie, 20 derniers, piles dans les `data`) ; `problems clear` les oublie. Un journal sans problème = `problems` sans ERROR.
- `stats [champs…]` (chemins pointés, ex. `fps glObjects.Texture` ; sinon temps, appels de dessin, changements de shader/texture, changements d'état GL envoyés et évités (`glStateChangesPerFrame`, `glStateChangesSkippedPerFrame`), uniforms, octets envoyés, objets GL, mémoire). Décrit la dernière seconde **complète** (attendre `sleep:1.5`). `stats reset` remet à zéro `maxFrameMsSinceReset`, `maxFrameIntervalMsSinceReset` (< 100 ms visé), `maxTickMsSinceReset`, `maxSwapMsSinceReset`.
- `gl` (objets GL vivants, éléments partagés et références, dont les programmes `Shader`, et `retainedObjects` : `Material` et `Mesh` retenus, `orphanMaterial` et `orphanMesh` retenus par personne mais pas libérés) ; `gl materials` (`DEV` : les matériaux et meshes retenus ou orphelins du moteur avec leurs références, `data` : par matériau `shader`, `references`, `blend`, `sortKeyPart`, `version` ; par mesh `references`, `vbos`, `vertices` ; `sharedMaterials`, `sharedMeshes`, `orphanMaterials`, `orphanMeshes` ; scène `SharedMaterial2D`) ; `gl summary` (par type `éléments/références`) ; les deux listent dans `failed` les éléments dont le premier chargement a échoué (`Shader <nom>` : GLSL qui ne compile pas), réessayés quand leur donnée est rechargée, et dans `fallbacks` les éléments de repli (`dataType`, `elementType`, `neededBeforeDrawing`, `state` : `loaded`, `waiting` ou `failed`), leur nombre et ceux en échec dans le message. `gl text [--contains <chaîne>]` : les `Text` réellement dessinés par la dernière frame (`DrawnTexts`), du haut vers le bas puis de gauche à droite, avec position (du premier caractère, dans l'espace de la caméra du texte), taille et corps : contrôler l'écran en texte sans capture (par exemple comparer avec `layout.rows()` de la console).
- `colorspace` (`DEV` : modes du moteur, de la scène courante de la fenêtre cible et résolu ; `data` : `engine`, `scene`, `view`, `resolved`) ; `colorspace engine linear|gamma` ; `colorspace view linear|gamma|inherit|toggle` (scène courante, `toggle` = l'autre mode que le résolu ; « No window » sans fenêtre). `picture` (`USER` : gamma, luminosité, contraste du joueur) ; `picture gamma|brightness|contrast <valeur>` ([0,25 ; 4]) ; `picture reset` ; sauvegardé dans `data/configs/mightylib/display.json`. Propriété de lancement `-Dmightylib.colorSpace=linear|gamma` (mode du moteur au démarrage, `-D mightylib.colorSpace=linear` de `scenario.py`). **F7** (démo, `ColorSpaceToggleService`) bascule la scène courante. Comparer des rendus : `screenshot` avant/après dans le scratchpad puis différence de pixels en Python ; scènes `ColorSpaceSplit2D` et `ColorSpaceSplit3D` (gauche linéaire, droite gamma).
- `shaders` (`DEV` : version écrite par le prélude, defines globaux, shaders déclarés avec les defines de leur entrée ; `data` : `version`, `folder`, `defines`, `shaders` avec `files`, `tags`, `defines`) ; `shaders define <nom> [valeur]` (define global, la valeur = le reste de la ligne ; nom invalide → erreur ; tous les shaders sont relus, `changed` faux si la valeur était déjà celle-là) ; `shaders undefine <nom>` (un define posé, complété). Exemple : `python tools/scenario.py "scene ShaderDefines2D" wait-loaded "input key I" sleep:1 "?shaders"` (I pose ou retire `DEMO_INVERT` : couleurs inversées).
- `batch` (`DEV` : mode du lot 2D et, par vue, dessins et appels de la dernière frame, barrières et leurs causes — classe du renderer dessiné seul, `clear`, `scissor`, `framebuffer`, `context`, `view`, `flush`, `full`, `tableFull`, `mode`, `sortKey` — dont celles qui ont coupé un tri, et les appels par format de lot (`formats sprite x3 shape x22 stroke x3`) ; seules les vues affichées à la dernière frame sont dans le message, les autres dans les `data` avec `shownLastFrame` faux) ; `batch mode <off|orphan|ring|instanced>` (à chaud). Le message de `batch` donne aussi, par vue, les octets envoyés (par appel et dessins par appel) et le culling de vue (`N of M tested culled`, dessins sans boîte par classe) ; `data` : `bytes`, `bytesPerCall`, `drawsPerCall`, `formatBytes` (octets écrits par format), `viewCull` (`tested`, `culled`, `noBounds`, `noBoundsClasses`). **Culling de vue** (`batch cull`, `DEV`) : `batch cull on|off` (à chaud ; `-Dmightylib.viewCulling2D=on|off` au démarrage) ; `batch cull inset <pixels>` (zone de test réduite de N pixels de chaque côté : les dessins disparaissent au bord, rien ne doit disparaître plus loin ; 0 = la vue) ; `batch cull show [on|off]` (la boîte de chaque dessin testé, marges comprises, par les dessins de debug de la vue, en coordonnées du monde, une frame : vert dessiné, rouge éliminé ; les dessins d'une autre caméra que la caméra 2D de la vue ne sont pas montrés) ; `batch cull freeze` / `unfreeze` (la boîte de vue de chaque caméra est figée, clé = l'objet matrice de vue : on déplace la caméra pour voir ce qui serait éliminé ; une caméra nouvelle après le gel garde sa boîte) ; `batch cull list` (le premier appel lance l'enregistrement, les suivants rendent en JSON les dessins éliminés de la dernière frame complète : classe, boîte du monde, place de caméra, 1 000 au plus, `truncated` ; `batch cull list off` l'arrête). Exemple : `python tools/scenario.py "scene ViewCulling2D" wait-loaded "?stats" "batch cull inset 200" "batch cull show on" "screenshot"` (les dessins disparaissent à 200 pixels du bord, les boîtes sont vertes dedans et rouges au bord ; le texte de l'aide y disparaît aussi). `stats` donne `viewCullTestedPerFrame`, `viewCulledPerFrame`, `viewCullNoBoundsPerFrame`, `batchBytesPerFrame`, `batchDrawsPerCall`, `batchBytesPerCall`, `tilesCulledPerFrame` et `tilesDrawnPerFrame`. Un programme de lot qui ne lit pas son format écrit une ligne `--Batch program …` et ses shaders sont dessinés seuls. Réglage au démarrage : `EngineConfig.setBatch2DMode` ou `-Dmightylib.batch2D=ring`. `stats` donne `batchFlushesPerFrame` (appels du lot), `batchedDrawsPerFrame`, `batchBarriersPerFrame` et `renderCpuMs` (CPU de `displayWindows`, sans l'échange des tampons). Mesure : scène `BatchStress2D` (Page Haut/Page Bas : N, F : rectangles, les sept formes vectorielles du moteur mêlées, ou le mélange de jeu (slimes animés et tuiles d'un atlas, formes, textes), M : mode, O : tri par état), `python tools/scenario.py "scene BatchStress2D" wait-loaded "input key PAGE_UP" sleep:2 "?stats"` ; contre ses seuils : `tools/stress.py` (Profilage). Comparer deux modes : même scène lancée avec `-D mightylib.batch2D=off` puis `orphan`, `screenshot --rect`, comparaison pixel à pixel (scène non animée : `SharedMaterial2D`).
- `debugdraw` (`DEV` : dessins de debug des vues, `IView.debugDraw()` : allumés ou non, et par vue les dessins vivants par durée de vie, `oneFrame x2, seconds x18`) ; `debugdraw on|off` (éteint : rien n'est enregistré, ceux en attente sont jetés), `debugdraw clear` (jette tous les dessins), `debugdraw list`. Réglage au démarrage : `EngineConfig.setDebugDraw` ou `-Dmightylib.debugDraw=off` (défaut `on`, release compris). Démo : `python tools/scenario.py "scene DebugDrawing2D" wait-loaded "input key C" sleep:0.3 "input key R" "input key hold SPACE" sleep:0.5 "?debugdraw list" "input key release SPACE"` (C : cercle 120 frames, R : rectangle jusqu'au retrait, Espace tenue : ligne).
- `textureupload` (mode d'envoi des grosses textures à la carte et coût depuis le réglage) ; `textureupload direct|pbo` ; `textureupload bench` (compare les façons d'envoyer une texture sur cette carte, médiane de 5 essais, bloque ~1 s). Réglage au démarrage : `EngineConfig.setTextureUpload` ou `-Dmightylib.texture.upload=pbo`. Mesuré sur RTX 4080 SUPER : `pbo` n'est pas plus rapide (voir `decisions.md`).
- `screenshot [chemin] [--rect x y l h | --corners x y x2 y2] [--scale f]` (PNG de la frame suivante, défaut `screenshots/` ; le chemin est réservé à `DEV` ; `--rect` et `--corners` s'excluent ; `--scale 0.5` = 4 fois moins de pixels ; pixels fenêtre, origine en haut à gauche). Seulement si le texte ne suffit pas.
- `camera` (liste : position, direction/yaw/pitch/fov en 3D, zoom/rotation en 2D) ; `camera <id|nom>`. 3D : `camera main3D move x y z` / `lookat x y z`. 2D : `camera main2D move x y`, `zoom n` ou `zoom nx ny` (borné, garde le point de référence), `rotation degrés`. Une scène expose ses caméras par `registerCamera(camera, nom)` (`main3D`, `main2D` d'office).
- **Vérifier une forme 2D** : scène `VectorShapes2D` (toutes les formes, contours, jointures, extrémités), puis `camera main2D zoom 3`, `camera main2D rotation 25` et `screenshot --rect` sur un bord : il reste lisse, l'épaisseur en pixels d'écran ne change pas avec le zoom (touche X ; molette, Ctrl, Shift : zoom ; Alt + molette : rotation ; Z Q S D en AZERTY ou glisser au clic droit : déplacement ; la souris sur une forme affiche son renderer), `colorspace view linear` pour le bord en linéaire ; `leakcheck VectorShapes2D` pour les fuites.
- `monitors [full|modes]` : écrans (résolution, position ; `full` : zone de travail, fréquence ; `modes` : modes vidéo `LxH@Hz`), index de celui de la fenêtre. Choix de l'écran au démarrage (liste `--Monitors :` au journal) : `-Dmightylib.window.monitor=primary|secondary|largest|<index>|<nom>`, sinon `EngineConfig.setMonitorSelector(MonitorSelectors.Primary()|Secondary()|Index(i)|Name(t)|Largest())` ; introuvable → principal ; fenêtre centrée dans la zone de travail.
- **Plusieurs fenêtres** : `windows` (contextes, fenêtres avec id, titre, parent, `modal`, `blocked` = attend une fenêtre modale, focus, `mode` et `display` (réglages d'affichage), tailles, objets GL propres à la fenêtre ; `target` = celle des commandes) ; `window` (la cible), `window <id|titre|contexte>` (la choisir ; vaut pour la console, l'entrée standard et le serveur de debug : une commande lancée par le code d'une scène, `Commands.execute`, agit sur la fenêtre de cette scène), `window main` (retour), `window close [réf]` (fermer en fin de frame), `window mode windowed|fullscreen|borderless [réf]` (changer le mode, la cible par défaut ; la réponse donne le mode appliqué et la taille ; `window vsync <true|false> [réf]`, `vsync` dans `display`). Exemple : `python tools/scenario.py "scene DisplayModesScene" wait-loaded "window mode fullscreen" "input key W" sleep:1 "?window mode fullscreen 2" "?windows" "window mode windowed"` (la seconde fenêtre passe en sans bordure : l'écran a déjà un plein écran exclusif ; plein écran = l'écran de l'utilisateur change de mode, le prévenir). La cible est celle de `input`, `screenshot`, `monitors`, `scene`, `camera`, `wait-loaded`, `exit` ; elle revient à la fenêtre principale quand elle est fermée. `gl` ajoute `glContexts` (VAO/FBO/RBO de chaque contexte GL, suppressions en attente). Exemple : `python tools/scenario.py "scene MultiWindowScene" wait-loaded "input key M" sleep:1 "?windows" "window Dialog" "screenshot --scale 0.4" "input key ESCAPE"` (M : dialogue modal, T : fenêtre d'outils avec le renderer de la fenêtre principale, C : second contexte `second-1`).

## Simuler des entrées (`input`)
Appliqué par `InputManager.postUpdate()` au tick suivant, vu par tout ce tick (déterministe). Action ou axe = identifiant complet (`demo:enter`) ou chemin seul s'il est unique parmi les liés (`ENTER`, insensible à la casse) ; un chemin partagé par plusieurs espaces de noms est refusé avec la liste des identifiants.
- Actions : `input <ACTION> [ticks]`, `input hold|release <ACTION>`, `input list` (identifiants des actions et des axes liés).
- Souris (pixels fenêtre ; bouton `left|right|middle|<n>`) : `input mouse x y` (gardé jusqu'à un vrai mouvement), `input click [x y]` ou `input click left|right|middle [x y]`, `input mouse hold|release [bouton]` (ici le bouton peut être un nombre), `input scroll y [x]`.
- Clavier (fin de `GLFW_KEY_…` ou nombre) : `input key <TOUCHE> [ticks]`, `input key hold|release <TOUCHE>`, `input text "texte"`. Passe par `KeyboardManager`/`MouseManager`, donc par les actions liées.
- Vérifier la console (scène `ConsoleFeedScene`, `console open`) : Ctrl+touche = `input key hold LEFT_CONTROL`, `input key <TOUCHE>`, `input key release LEFT_CONTROL` (de même `LEFT_SHIFT`). Les touches simulées sont des positions physiques et leur lettre est celle de la disposition de l'utilisateur : en AZERTY Ctrl+A = `input key Q`, Ctrl+Z = `input key W` ; C, V, X, L ne changent pas. Sélection à la souris : `input mouse x y`, `input mouse hold`, `input mouse x2 y2`, `input mouse release` (double clic : `input click`, `sleep:0.3`, `input click` ; sans pause les deux clics tombent dans le même tick et ne comptent que pour un), puis `?console` (`selection`, `scroll`, `newLinesBelow`). Presse-papiers : `Get-Clipboard` (PowerShell) après Ctrl+C ou `console copy` ; **les scénarios écrasent le presse-papiers de l'utilisateur**, le prévenir.
- Vérifier le menu et le focus (scène `MenuScene`, `TextFieldScene2D`) : les touches simulées comptent un appui par tick, laisser `sleep:0.1` entre deux touches identiques (`input key S`). Champ : `input mouse 300 185`, `input click`, `input text pla`, `?gl text --contains Plat` (la liste filtrée), `input key ENTER` (lance la première scène : `wait-loaded`, `?scene`). Navigation : `input key S` (champ → liste, puis ligne suivante), `input key ENTER`, `?gl text --contains ->` (la ligne sélectionnée est affichée `->nom<-`). Tant que le champ a le focus la scène ne voit aucune touche (`TextFieldScene2D` compte les appuis sur Entrée vus par la scène). Un build sans accès aux commandes ne démarre pas le serveur de debug : le menu y est vérifiable à la main seulement.
- Texte : lire `KeyboardManager.getTypedText()` (rappel `glfwSetCharCallback` + texte simulé), pas `getCorrespondingCharMainKeyPressed`.
- Axes : `input axis <AXE> <valeur> [ticks]`, `… hold <valeur>`, `… release` (remplace les liaisons ; ex. `input axis LOOK_RIGHT 2 30`).
- `input state` : ce que voit le tick (souris virtuelle, boutons, défilement, touches, texte, actions, axes non nuls, `cursorShown`, `cursorMode`).
- Manettes (`gamepad` ; boutons `A`, `DPAD_UP`, `START`… ; axes `LEFT_X`, `RIGHT_TRIGGER`…) : `gamepad list` (connectées, boutons tenus, axes hors zone morte, joueurs), `gamepad connect` / `disconnect <id>` (virtuelle 16+), `gamepad <id> button <B> [ticks]`, `gamepad <id> hold|release <B>`, `gamepad <id> axis <AXE> <valeur> [ticks]` / `hold <valeur>` / `release`, `gamepad assign <id> <joueur>`, `gamepad autoassign on|off`. Scène : `GamepadScene`.

## Scripts (`exec <fichier> [--timeout s]`)
- Une commande par ligne, chemin relatif au répertoire de travail ; vides et `#` ignorées ; arrêt au premier échec. Réponse `{"lines": [{line, command, success, message, data}]}`. Scripts ponctuels dans `tools/scripts/` (ignoré par git) ; seul un script permanent est versionné, ailleurs.
- Les lignes s'enchaînent dans le même tick jusqu'à une réponse différée (`wait`, `screenshot`, `exec`). Entrée simulée vue au tick suivant (`input click`, `wait 1`, `input state`) ; après `scene X`, `wait loaded`.
- Chaque ligne s'exécute avec la source qui a lancé `exec` (son niveau), même les lignes jouées plus tard : un script ne s'élève pas.
- Délai par réponse différée : 30 s (`exec` 300 s). Script récursif refusé. Script long avec `scenario.py` : augmenter `--timeout` (`python tools/scenario.py --timeout 60 "?exec tools/scripts/x.txt"`).

## `scenario.py` (lancer et vérifier le jeu, Claude)
Une fenêtre s'ouvre chez l'utilisateur (sur l'écran secondaire, `--monitor` vide = choix du projet) : le prévenir. `--platform x11|wayland` impose la plateforme GLFW (Linux : tester ce qui touche aux fenêtres sous les deux ; sous Wayland, `--monitor` est sans effet). À la fin des étapes, `problems` est interrogé : son bilan (compteurs, derniers problèmes) est affiché et un ERROR fait échouer le scénario. La regex du journal (`PROBLEM_PATTERN`) ne cherche que ce qui échappe à `Logger` : exception non attrapée, erreurs GLFW (`[LWJGL] … error`), plantage avant le moteur, `--Exit with error` (écrit après le dernier `problems`) ; les lignes `--` et la pile qui les suit sont comptées par `problems`.
```bash
python tools/scenario.py "scene Scene2D" wait-loaded "?gl summary" "input ESCAPE" sleep:0.5 scene
```
- Compile (`--no-compile`), construit `target/classpath.txt` (classpath d'exécution de la démo, natives comprises, régénéré quand un des `pom.xml` du réacteur change : `-o test-compile dependency:build-classpath -pl demo -am` dans le réacteur, la bibliothèque y est donc `mightylib/target/classes`), lance avec `demo/target/classes` + ce classpath depuis la racine (journal `target/scenario.log` ; `--modulepath` : les mêmes entrées en `--module-path`, `--add-modules ALL-MODULE-PATH` pour les modules des natives, `--module io.github.mightycode.mightylibdemo/…Main`), enchaîne, envoie `exit`, affiche `problems`, liste les lignes suspectes du journal (dédoublonnées `(xN)`). Code 0 si tout réussit, sans ERROR ni ligne suspecte.
- Étapes en plus : `wait-loaded` (fin de chargement de la scène du dernier `scene X`), `sleep:S`, `leakcheck <Scène> [n=2] [via=MenuScene]` (allers-retours ; affiche `no leak` ou les compteurs modifiés : ceux de `gl`, noms sans suffixe `#id`, et `sound.ownedSources`, les sources possédées de `sounds`, et `retained.Material`/`retained.Mesh`, les objets partageables encore retenus par un utilisateur, `retained.orphanMaterial`/`retained.orphanMesh`, ceux retenus par personne mais pas libérés), `log <regex> [n=10]`. `drag x1 y1 x2 y2 [--hold S]` : glisser complet au bouton gauche (appui en x1 y1, déplacement en 5 étapes pendant S secondes, 0,5 par défaut, relâchement ; remplace `input mouse` + `hold` + `release` + `sleep`). Exemple : `"drag 20 490 300 430 --hold 1s" "?console"`.
- Sortie : `ok` par étape réussie ; `?` devant une étape = réponse complète ; un échec affiche tout.
- Blocage : rien après `--timeout` s (20) → bloqué ; `wait-loaded` trop long → `BLOCKED` + état `gl`, arrêt. Jeu tué après `--max-duration` (300 s).
- `-D clé=valeur` (répétable) : propriété système donnée au jeu (ex. `-D mightylib.commands.access=user`).
- Son muet (`-Dmightylib.sound=silent`, `EngineConfig.SOUND_PROPERTY`) : le service `SilentSoundService` remplace celui du son, quel que soit le plugin qui le fournit, sans aucun appel OpenAL (ligne `--mightylib.sound=silent: no sound device`) ; les sources existent (commande `sounds`) mais rien ne s'entend ; autre valeur : avertissement, ignorée. Un périphérique absent donne le même service, en repli.
- Ressources du moteur depuis un dossier (`-Dmightylib.resources.engine=<dossier>`, `EngineConfig.ENGINE_RESOURCES_PROPERTY`, ou `EngineConfig.setEngineResourcesFolder`) : la source classpath du moteur (`assets/mightylib/` du jar) est remplacée par ce dossier, sur le disque donc observable (ex. `-D mightylib.resources.engine=mightylib/src/main/resources/assets/mightylib` pour éditer et recharger à chaud les shaders et les polices du moteur depuis le dépôt) ; reste actif en release. `resources sources` montre la pile obtenue.
- Démo lancée depuis son jar (source de la démo dans le jar, non observée) : `package` puis `java -cp demo/target/mightylib-demo-<version>-jar-with-dependencies.jar io.github.mightycode.mightylibdemo.main.Main` depuis la racine, et `scenario.py --attach` pour la piloter.
- `wait-loaded` passe par la commande `wait loaded` : il attend la fin de tout changement de scène, demandé par `scene X` ou par le jeu (menu, touche simulée), puis la fin du chargement.
- `--strict` : échec ou nom inconnu arrête le jeu (sinon log `… its fallback is used` et `usingFallback` dans `resources` ; démo : `FallbackScene` sans `--strict`). `--attach` (jeu déjà lancé, ni lancé ni fermé), `--keep-open`.
- Souris jamais capturée (`-Dmightylib.input.noCursorCapture=true`, `MouseManager.NO_CAPTURE_PROPERTY` : curseur visible et libre pour l'utilisateur) : regard 3D testé par `input mouse`/`input axis`/`gamepad` ; `--capture-mouse` pour la capture.
- Fluidité d'un chargement : `python tools/scenario.py "scene GLLoading" "stats reset" wait-loaded stats` (`reset` après `scene` exclut le tick qui exécute `init`). Préchargement : `scene PreloadScene`, puis `resources batch <batch>` et `input ENTER`.
- Fuite à la main : `gl` sur une scène, allers-retours, `gl` à nouveau : compteurs et références identiques.

## Paquet de démonstration (`tools/demo_assets.py`)
Les ressources lourdes de la démo (`resources/models/backpack/`, utilisé par `Scene3D`) ne sont pas dans git : elles sont dans une archive jointe à une release GitHub (tag `demo-assets-N`). Le manifeste `tools/demo_assets.json` donne le tag, l'URL et le sha256 de l'archive, et le sha256 de chaque fichier (chemins relatifs à `resources/`). Bibliothèque standard seulement.
- `python tools/demo_assets.py` : si tous les fichiers du manifeste sont à jour, « up to date » sans réseau ; sinon télécharge l'archive (HTTPS, sha256 vérifié avant ouverture), extrait **seulement** les entrées du manifeste (chemins absolus et `..` refusés), chaque fichier écrit puis renommé après vérification de son sha256. Erreur (réseau, 404, empreinte) : une ligne, code 2, aucun fichier partiel.
- `--check` : sans réseau, liste les fichiers manquants ou différents, code 1 s'il y en a.
- `--pack demo-assets-N` : construit `target/demo-assets/mightylib-demo-assets-N.zip` à partir de `resources/` et met à jour le manifeste ; refuse un fichier que git n'ignore pas.
- **Ajouter une ressource au paquet** : l'ajouter à `files` du manifeste et à `.gitignore`, `--pack demo-assets-<N+1>`, publier la release (`gh release create demo-assets-<N+1> <archive>`, publique), commiter le manifeste.
- Sans le paquet, `Scene3D` envoie un WARNING et affiche « Model 'backpack' missing: run python tools/demo_assets.py ». Le test de fumée ignore alors `Scene3D` (`SmokeCases`, présence des fichiers du manifeste, sans Python) ; la CI télécharge le paquet et l'exige (`-Dmightylib.test.requireDemoAssets=true`).

## Profilage
- **JFR** : événements `mightylib.Frame`/`mightylib.Tick` et `mightylib.BatchSend` (l'envoi d'un lot 2D : tri, envoi des tampons et appels de dessin ; champs `draws`, `drawCalls`, `bytes` ; ce qui n'est pas dans cet événement est de l'écriture CPU des dessins). `jcmd <pid> JFR.start duration=30s filename=rec.jfr` (pid : `jcmd -l`) ou `-XX:StartFlightRecording=…` ; `jfr print --events mightylib.Frame rec.jfr`, ou JMC/VisualVM.
- **JFR en un appel** : `python tools/scenario.py --jfr "scene BatchStress2D" wait-loaded "input key PAGE_UP" sleep:5` enregistre `target/jfr/scenario.jfr` (profil `profile`, `DebugNonSafepoints` pour garder les méthodes inlinées ; `--jfr-file` change le fichier), puis résume en texte à la fermeture du jeu. `python tools/jfr_summary.py target/jfr/scenario.jfr [--since S] [--until S] [--root Renderer.display] [--top N] [--thread main]` relit un enregistrement : méthodes les plus chaudes du thread principal (`self` = en haut de la pile, `total` = dans la pile, en pourcentage des échantillons retenus ; seul le code Java est échantillonné, les appels GL natifs sont dans `BatchSend`), allocations par classe et par site de la bibliothèque (`jdk.ObjectAllocationSample`, estimées), durées de `mightylib.Frame`, `Tick` et `BatchSend`. `--since` écarte le chargement de la scène (secondes depuis le début de l'enregistrement), `--root` ne garde que les échantillons dont la pile contient le texte. Le mélange de `BatchStress2D` : `"input key F" sleep:0.3 "input key F"` avant les Page Haut (cas de `tools/stress.py`, ci-dessous).
- **Bancs du coût CPU d'un dessin du lot 2D** : `python tools/bench.py` (environ 40 s ; `--no-gl` : seulement le lot sans GL ; `--isolated` : une JVM par cas, environ 1 min de plus ; `--repeat N` : N exécutions, médiane par cas ; `--json`) lance `DrawBatch2DBenchTest` (`mightylib`, sans GL : écriture d'un rectangle, test de culling, faux envoi) et `Batch2DCostBenchTest` (`mightylib-test`, fenêtre cachée : le chemin complet `display()` → `submitToBatch` de 16 000 renderers de chaque type (rectangle texturé, coloré, mêlé, animation, forme vectorielle sans et avec contour, texte), dans la vue ou hors de la vue) et imprime les ns par dessin (médiane après chauffe ; `send` : la fin de la vue (tri, envoi, appels GL), à part des `display()`). Ce sont des tests JUnit actifs seulement avec `-Dmightylib.bench=true` : `mvn test` ne les exécute pas ; ils mesurent et ne vérifient rien. Un cas varie avec les cas passés avant lui dans la même JVM et d'une JVM à l'autre (décisions du JIT, ±20 % sur certains cas) : comparer avant et après un changement avec `--isolated --repeat 3`. Le coût d'une frame entière d'une scène : `tools/stress.py`.
- **Seuils de la scène d'acceptation du lot 2D** : `python tools/stress.py` (environ 1 min par lancement du jeu, une fenêtre par lancement ; `--case mot…` : les cas dont le nom contient un des mots, `--list` : cas et seuils sans lancer, `--json` : une ligne par cas, `--no-compile`) lance `BatchStress2D` en mode `orphan`, vsync coupée, par cas (mode rectangles, formes ou mélange ; N = 16 000 ou 128 000 ; tout visible, ou ~10 % visible par `camera main2D zoom 3.2` ; trié par état (O) ou non ; les cas d'un même mode, N et vue partagent un lancement), prend après chauffe 3 échantillons de `stats` à 1,2 s d'écart et compare leur médiane aux seuils du cas (`renderCpuMs` et, quand il est fixé, `drawCallsPerFrame`) : `PASS`/`FAIL` par cas, code de sortie 1 si un cas échoue. Les seuils sont ceux de la machine de l'utilisateur (mesure + ~15 %, écrits dans le script avec leur date) : ailleurs, seuls les appels comptent. Hors `mvn test` ; le rendu, les appels et les allocations sont vérifiés par `BatchStress2DGLTest`. L'atlas de la scène se régénère par `python tools/generate_stress_atlas.py` (depuis `tileset.png` et `slime.png`).
- **GPU** : RenderDoc ou Nsight Graphics (OpenGL 3.3 core).
- **Erreurs GL** : `EngineConfig.setOpenGLErrorCheck(true)` (`Logger.isGLErrorCheck()`) = `glGetError` après les appels sensibles, plus lent.

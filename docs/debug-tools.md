# Outils de debug et de mesure

## Commandes (registre de l'`Engine`, accès selon le niveau)
- **Accès** : en debug, tout (niveau `DEV`) : console en jeu (`²`), entrée standard et serveur de debug. En release, aucun par défaut (`EngineConfig.setCommandAccess`, `setMaxCommandAccess`, `setCheatCommand` ; option `-Dmightylib.commands.access=none|user|cheat|dev`, bornée par le plafond du build ; un jeu sans console du tout : `setMaxCommandAccess(null)`, l'option est alors ignorée). Détail : `architecture.md`, section **Commandes**. Démo : `-Ddemo.release=true` (release, accès `USER`, plafond `CHEAT`), `-Ddemo.commands.max=none|user|cheat|dev` ; avec `scenario.py` : `-D mightylib.commands.access=user -D demo.commands.max=cheat` (la console en jeu est au niveau joueur, le serveur reste `DEV` ; pour voir ce que voit le joueur : `as user <ligne>` et `complete --as user "<début>"`, pas la console pilotée par `input`).
- `help` : identifiant, propriétaire (`engine`, `game`, `scene`, `window`) et description des commandes visibles par la source ; `help <cmd>` ou `<cmd> --help` : description, une ligne d'usage par branche, arguments et options (`--help` marche n'importe où sur la ligne, même après une erreur, sauf après `--`). Les `data` de `help <cmd>` contiennent l'arbre visible en JSON (`id`, `level`, `description`, `branches` : `usage`, `description`, `arguments` `{name, type, optional, variadic, values?}`, `options` `{name, values, repeatable, default?}`). Le serveur de debug, l'entrée standard et `api` sont au niveau `DEV` : ils voient tout.
- Découpage (`CommandLine.Split`) : espaces ; guillemets doubles pour un mot avec espaces ; `\` gardés (chemins Windows) ; guillemet non fermé = erreur. Dans `scenario.py` : `'screenshot "target/a b.png"'`.
- `Commands.submit(line, source)` depuis tout thread, exécutée au début du tick suivant (`processPendingCommands`) ; source (`ICommandSource` : `game`, `stdin`, `server#N`, `api` par défaut) donnée par `getCurrentSource()` et son niveau par `getCurrentLevel()` pendant l'exécution ; les `ICommandListener` reçoivent chaque commande soumise et son résultat, avec le niveau de la source au moment de l'exécution, ou le niveau plus bas qu'elle a ensuite si la commande l'a baissé (`cheats off` : `lowered`, puis la réponse à ce niveau, pour que le joueur voie encore la ligne ; `CommandEcho` les écrit dans le journal de la console et baisse alors le niveau de la ligne déjà écrite, `ConsoleLog.lower`). Entrée standard lue dans un thread à part (mode debug).
- **Écrire une commande** (package `utils/enginecommand/syntax`) :
  - `BaseCommand(Identifier, ECommandLevel, description)` : espace de noms du propriétaire (`mightylib`, le jeu, le mod), niveau minimal et description (première ligne de l'aide), tous obligatoires. Enregistrement : `IProjectLoading.registerCommands(registry)` (jeu), `Scene.addCommand` dans `init` (existe pendant le chargement), `WindowView.addCommand`. Identifiant déjà pris → `IllegalArgumentException`, sauf entre deux vues (même scène dans deux fenêtres) : choisir la fenêtre avec `window`.
  - `syntax(CommandNode racine)` (abstraite, appelée une fois au premier enregistrement : les champs qu'elle utilise sont posés par le constructeur ; une erreur de schéma est une `IllegalStateException` à l'enregistrement) déclare les branches : `racine.executes("…", ctx -> …).then(literal("mode", "…").then(argument("mode", choice("poll", "service"), "…").option(Option.of("interval", "…").value("ms", longValue(1, 60000)).defaultValue(1000L)).executes(ctx -> …)))`. Imports statiques : `Arguments.*`, `CommandNode.literal`, `CommandNode.argument`. Règles : toute branche s'exécute ou continue ; un argument variadique, `text` ou `commandLine` est le dernier de sa branche ; une option répétable n'a pas de valeur par défaut ; après un argument facultatif (`.optional()`) seulement des facultatifs ; noms d'arguments et d'options uniques sur une branche.
  - **Convention** : positionnels = ce que la commande vise (sous-commande, cible, valeur principale) ; options = réglages facultatifs (`watch mode poll --interval 500`, `wait loaded --timeout 10`, `screenshot [chemin] --rect x y l h --scale 0.5`). Options `--nom valeur` ou `--nom=valeur`, drapeaux `--nom`, `--` termine les options ; noms en minuscules kebab, pas d'alias courts (collisions entre moteur, jeu et mods) ; `--help` est ajoutée par le moteur. Les littéraux passent avant les arguments au même niveau ; les arguments d'un même niveau sont essayés dans l'ordre, sans retour en arrière.
  - **Types** (`Arguments`) : `integer`, `longValue`, `decimal` (bornes facultatives), `bool`, `word`, `text` (le reste de la ligne, mots joints par une espace ; un texte commençant par `--` s'écrit après `--`), `commandLine` (idem, mais plusieurs mots sont rejoints entre guillemets pour être redécoupés : `as`, `complete`), `choice`, `enumOf(Classe)`, `oneOf(Supplier)` (valeurs dynamiques, strict), `suggest(Supplier)` (proposées, libres), `identifier`, `path([dossier])`. Un type maison implémente `ArgumentType` (`parse` lève `CommandSyntaxException.expected("un entier…", mot)`, `complete(début, ctx)` lit les arguments précédents par `ctx.get(...)`) : ex. `resources/ResourceArguments` (`type`, `names`, option `--regex`, branches `selection(…)` de `reload`, `resources`, `watch`).
  - **Handler** (`ICommandHandler`) : reçoit un `CommandContext` (`get`, `getOr`, `has`, `getList` pour un variadique ou une option répétable, `currentLevel()`, `source()`, `commandName()` ; option à plusieurs valeurs → `List`, drapeau → `true`) et **renvoie** `CommandResult.ok(message, data JSON)`/`error(...)`, sans écrire en console ; résultat différé : `CommandResult.later(future)` (abandon après `Commands.COMMAND_TIMEOUT_SECONDS` = 30 s). Le `message` est une phrase lisible par le joueur ; les `data` sont le détail pour le développeur (journal : `DEV` seulement). Une `CommandException` donne sa réponse d'erreur telle quelle.
  - **Niveau et condition par branche** : `.level(ECommandLevel.DEV)` sur un nœud ou une option : absent de la complétion, de l'aide et du JSON pour les niveaux inférieurs, avec l'erreur d'un mot inconnu (ex. `console log`, `stats` hors `fps`, chemin de `screenshot`, `spawn list`). `.requires(CommandCondition…)` : `hidden(prédicat)` (la branche n'existe pas ; sur la racine, la commande n'existe pas), `check(prédicat, message)` (visible, refus avec message), `launched(scène | () -> scène)` (« Scene still loading » avant le `launch`, sur la racine d'une commande de scène ou de `camera`). Les `check` sont évalués à l'entrée du nœud (pour un argument, avant que son type lise le mot ; s'il est refusé, un autre argument du même niveau peut prendre le mot, sinon son message est l'erreur), pas à la complétion : un `Supplier` de valeurs doit supporter une scène en chargement. Les `hidden` de la racine sont évalués sous le propriétaire de la commande (sa vue), comme l'exécution.
- **Complétion** (Tab de la console) : `Commands.complete(début de ligne[, source])` → `CommandCompletion` (début du mot, choix triés sans casse, `replacement()` : le seul choix suivi d'une espace, sinon la partie commune). Noms (chemins, et identifiants des chemins partagés ou une fois `espace:` tapé) des commandes visibles, puis les candidats de la syntaxe : littéraux et valeurs de l'argument attendu, options visibles non encore données et `--help` quand le mot commence par `-`, valeurs de l'option qui attend sa valeur. Les commandes générales complètent leurs sous-commandes et valeurs (actions, axes, touches, boutons de manette, caméras, batchs, ressources, fenêtres, scènes trouvées dans le package des scènes, fichiers pour `exec`).
- **Tester ce que voit le joueur** (sans piloter la console) : `as <user|cheat|dev> <ligne>` exécute la ligne avec le niveau `min(niveau demandé, niveau de la source)` (jamais plus haut ; une commande `DEV` est inconnue sous `as user`) ; `complete [--as <niveau>] "<début de ligne>"` donne dans ses `data` `start`, `typed`, `candidates`, `replacement` de `Commands.complete`, un espace final compris. Les deux sont `DEV` : `as user complete …` n'existe pas, écrire `complete --as user …`. Exemple : `python tools/scenario.py "scene Scene2D" wait-loaded "?complete --as user \"stats \"" "?as user help stats" "?as user screenshot target/x.png"` (le joueur ne voit que `fps`, `screenshot` sans chemin : « Unknown argument »).
- Plusieurs ticks : `Commands.addTickTask` (comparer `Commands.getTick()`, une tâche peut être appelée plusieurs fois par tick).

## Serveur de debug
- `127.0.0.1:7777` (`EngineConfig.setDebugServerPort()`, `-1` = désactivé), sinon port libre suivant ; affiché (`--Debug server listening on …`) et écrit dans `-Dmightylib.debugServer.portFile=<fichier>` (utilisé par `scenario.py` : plusieurs jeux/scénarios simultanés, un `--log` chacun). `--attach`/`mighty.py` : `--port` si pas 7777.
- Protocole : une commande par ligne → une ligne JSON `{"success", "message", "data"}`. Client : `python tools/mighty.py <commande>` (`--wait N`, `--json`, sans argument = interactif).
- Suivi du journal : `console follow on|off` ; le client reçoit aussi, entre les réponses, `{"event": "log", "id", "type": OUT|ERR|COMMAND|RESULT|ERROR|MESSAGE, "source", "text"}` pour chaque ligne (file de 10 000 lignes par client et thread d'écriture à lui : un client lent ne bloque pas le jeu, l'excédent est perdu). `python tools/mighty.py --follow` : affiche tout le journal (sortie du programme, commandes de toutes les sources et résultats) et envoie les lignes tapées comme commandes.

## Commandes utiles
- `console` (mode : closed, overlay, detached) ; `console open|close|toggle|detach|attach|clear` (`clear` sous `DEV` : vide seulement la console du joueur) ; `console log [n]` (dernières lignes du journal avec leur id et le niveau qui les voit, 20 par défaut) ; `console log since <id>` (lignes suivantes, pour interroger sans suivi) ; `console logs [on|off]` (`DEV`, bascule sans argument : cache ou montre la sortie du programme dans la console, le journal la garde) ; `console copy [n] [--all]` (met dans le presse-papiers les `n` dernières lignes montrées par la console avant la commande elle-même, toutes sans `n`, comme Ctrl+C sur une sélection ; `--all` (`DEV`) ignore le filtre de `console logs off` ; réponse `{lines, chars}`, presse-papiers inchangé s'il n'y a aucune ligne) ; la réponse de `console` sans argument donne aussi `logsShown`, `scroll` (`"end"` ou `{id, row}`), `newLinesBelow` (lignes sous la vue, 1000 = plus de 999) et `selection` (`null`, `{in: "input", start, end}` ou `{in: "log", from: {id, char}, to: {id, char}}`) ; `console follow [on|off]` (voir **Serveur de debug**).
- `help [commande]` ; `as <niveau> <ligne>`, `complete [--as <niveau>] "<début>"` ; `cheats [on|off]` (si le jeu l'active : `EngineConfig.setCheatCommand`) ; `scene` (courante et `loading`) / `scene <Nom>` (relatif au package de la première scène, ex. `Platformer2D.PlatformerBox2D`) ; `wait <ticks> [--timeout s]` / `wait loaded [--timeout s]` (fenêtre visée au départ ; erreur si elle se ferme pendant l'attente) ; `reload <all|Type> [noms…] [--regex motif]` (sélection vide = 0 donnée, pas une erreur) ; `resources [all|Type] [noms…] [--regex motif]` (détail des données choisies, 100 au plus) ; `resources batch <nom>` (ce que charge un batch : dépendances connues, chargées, mémoire CPU/GPU estimée) ; `resources preload|unpreload <batch>` (précharge un batch, ou annule) ; `watch [status|<all|Type> [noms…] [--regex motif]|mode poll|service [--interval ms]|off]` (rechargement à chaud sur changement de fichier, éteint par défaut, voir `architecture.md`) ; `exit`. Détail de `resources` : `architecture.md`.
- `stats [champs…]` (chemins pointés, ex. `fps glObjects.Texture` ; sinon temps, appels de dessin, changements de shader/texture, uniforms, octets envoyés, objets GL, mémoire). Décrit la dernière seconde **complète** (attendre `sleep:1.5`). `stats reset` remet à zéro `maxFrameMsSinceReset`, `maxFrameIntervalMsSinceReset` (< 100 ms visé), `maxTickMsSinceReset`, `maxSwapMsSinceReset`.
- `gl` (objets GL vivants, éléments partagés et références) ; `gl summary` (par type `éléments/références`). `gl text [--contains <chaîne>]` : les `Text` réellement dessinés par la dernière frame (`DrawnTexts`), du haut vers le bas puis de gauche à droite, avec position (du premier caractère, dans l'espace de la caméra du texte), taille et corps : contrôler l'écran en texte sans capture (par exemple comparer avec `layout.rows()` de la console).
- `textureupload` (mode d'envoi des grosses textures à la carte et coût depuis le réglage) ; `textureupload direct|pbo` ; `textureupload bench` (compare les façons d'envoyer une texture sur cette carte, médiane de 5 essais, bloque ~1 s). Réglage au démarrage : `EngineConfig.setTextureUpload` ou `-Dmightylib.texture.upload=pbo`. Mesuré sur RTX 4080 SUPER : `pbo` n'est pas plus rapide (voir `decisions.md`).
- `screenshot [chemin] [--rect x y l h | --corners x y x2 y2] [--scale f]` (PNG de la frame suivante, défaut `screenshots/` ; le chemin est réservé à `DEV` ; `--rect` et `--corners` s'excluent ; `--scale 0.5` = 4 fois moins de pixels ; pixels fenêtre, origine en haut à gauche). Seulement si le texte ne suffit pas.
- `camera` (liste : position, direction/yaw/pitch/fov en 3D, zoom/rotation en 2D) ; `camera <id|nom>`. 3D : `camera main3D move x y z` / `lookat x y z`. 2D : `camera main2D move x y`, `zoom n` ou `zoom nx ny` (borné, garde le point de référence), `rotation degrés`. Une scène expose ses caméras par `registerCamera(camera, nom)` (`main3D`, `main2D` d'office).
- `monitors [full|modes]` : écrans (résolution, position ; `full` : zone de travail, fréquence ; `modes` : modes vidéo `LxH@Hz`), index de celui de la fenêtre. Choix de l'écran au démarrage (liste `--Monitors :` au journal) : `-Dmightylib.window.monitor=primary|secondary|largest|<index>|<nom>`, sinon `EngineConfig.setMonitorSelector(MonitorSelectors.Primary()|Secondary()|Index(i)|Name(t)|Largest())` ; introuvable → principal ; fenêtre centrée dans la zone de travail.
- **Plusieurs fenêtres** : `windows` (contextes, fenêtres avec id, titre, parent, `modal`, `blocked` = attend une fenêtre modale, focus, `mode` et `display` (réglages d'affichage), tailles, objets GL propres à la fenêtre ; `target` = celle des commandes) ; `window` (la cible), `window <id|titre|contexte>` (la choisir), `window main` (retour), `window close [réf]` (fermer en fin de frame), `window mode windowed|fullscreen|borderless [réf]` (changer le mode, la cible par défaut ; la réponse donne le mode appliqué et la taille ; `window vsync <true|false> [réf]`, `vsync` dans `display`). Exemple : `python tools/scenario.py "scene DisplayModesScene" wait-loaded "window mode fullscreen" "input key W" sleep:1 "?window mode fullscreen 2" "?windows" "window mode windowed"` (la seconde fenêtre passe en sans bordure : l'écran a déjà un plein écran exclusif ; plein écran = l'écran de l'utilisateur change de mode, le prévenir). La cible est celle de `input`, `screenshot`, `monitors`, `scene`, `camera`, `wait-loaded`, `exit` ; elle revient à la fenêtre principale quand elle est fermée. `gl` ajoute `glContexts` (VAO/FBO/RBO de chaque contexte GL, suppressions en attente). Exemple : `python tools/scenario.py "scene MultiWindowScene" wait-loaded "input key D" sleep:1 "?windows" "window Dialog" "screenshot --scale 0.4" "input key ESCAPE"` (D : dialogue modal, T : fenêtre d'outils avec le renderer de la fenêtre principale, C : second contexte `second-1`).

## Simuler des entrées (`input`)
Appliqué par `InputManager.postUpdate()` au tick suivant, vu par tout ce tick (déterministe). Action ou axe = identifiant complet (`demo:enter`) ou chemin seul s'il est unique parmi les liés (`ENTER`, insensible à la casse) ; un chemin partagé par plusieurs espaces de noms est refusé avec la liste des identifiants.
- Actions : `input <ACTION> [ticks]`, `input hold|release <ACTION>`, `input list` (identifiants des actions et des axes liés).
- Souris (pixels fenêtre ; bouton `left|right|middle|<n>`) : `input mouse x y` (gardé jusqu'à un vrai mouvement), `input click [x y]` ou `input click left|right|middle [x y]`, `input mouse hold|release [bouton]` (ici le bouton peut être un nombre), `input scroll y [x]`.
- Clavier (fin de `GLFW_KEY_…` ou nombre) : `input key <TOUCHE> [ticks]`, `input key hold|release <TOUCHE>`, `input text "texte"`. Passe par `KeyboardManager`/`MouseManager`, donc par les actions liées.
- Vérifier la console (scène `ConsoleFeedScene`, `console open`) : Ctrl+touche = `input key hold LEFT_CONTROL`, `input key <TOUCHE>`, `input key release LEFT_CONTROL` (de même `LEFT_SHIFT`). Les touches simulées sont des positions physiques et leur lettre est celle de la disposition de l'utilisateur : en AZERTY Ctrl+A = `input key Q`, Ctrl+Z = `input key W` ; C, V, X, L ne changent pas. Sélection à la souris : `input mouse x y`, `input mouse hold`, `input mouse x2 y2`, `input mouse release` (double clic : `input click`, `sleep:0.3`, `input click` ; sans pause les deux clics tombent dans le même tick et ne comptent que pour un), puis `?console` (`selection`, `scroll`, `newLinesBelow`). Presse-papiers : `Get-Clipboard` (PowerShell) après Ctrl+C ou `console copy` ; **les scénarios écrasent le presse-papiers de l'utilisateur**, le prévenir.
- Texte : lire `KeyboardManager.getTypedText()` (rappel `glfwSetCharCallback` + texte simulé), pas `getCorrespondingCharMainKeyPressed`.
- Axes : `input axis <AXE> <valeur> [ticks]`, `… hold <valeur>`, `… release` (remplace les liaisons ; ex. `input axis LOOK_RIGHT 2 30`).
- `input state` : ce que voit le tick (souris virtuelle, boutons, défilement, touches, texte, actions, axes non nuls, `cursorShown`, `cursorMode`).
- Manettes (`gamepad` ; boutons `A`, `DPAD_UP`, `START`… ; axes `LEFT_X`, `RIGHT_TRIGGER`…) : `gamepad list` (connectées, boutons tenus, axes hors zone morte, joueurs), `gamepad connect` / `disconnect <id>` (virtuelle 16+), `gamepad <id> button <B> [ticks]`, `gamepad <id> hold|release <B>`, `gamepad <id> axis <AXE> <valeur> [ticks]` / `hold <valeur>` / `release`, `gamepad assign <id> <joueur>`, `gamepad autoassign on|off`. Scène : `GamepadScene`.

## Scripts (`exec <fichier> [--timeout s]`)
- Une commande par ligne, chemin relatif au répertoire de travail ; vides et `#` ignorées ; arrêt au premier échec. Réponse `{"lines": [{line, command, success, message, data}]}`. Scripts ponctuels dans `tools/scripts/` (ignoré par git) ; seul un script permanent est versionné, ailleurs.
- Les lignes s'enchaînent dans le même tick jusqu'à une réponse différée (`wait`, `screenshot`, `exec`). Entrée simulée vue au tick suivant (`input click`, `wait 1`, `input state`) ; après `scene X`, `wait loaded`.
- Chaque ligne s'exécute avec la source qui a lancé `exec` (son niveau), même les lignes jouées plus tard : un script ne s'élève pas.
- Délai par réponse différée : 30 s (`exec` 300 s). Script récursif refusé. Script long avec `scenario.py` : augmenter `--timeout` (`python tools/scenario.py --timeout 60 "?exec tools/scripts/x.txt"`).

## `scenario.py` (lancer et vérifier le jeu, Claude)
Une fenêtre s'ouvre chez l'utilisateur (sur l'écran secondaire, `--monitor` vide = choix du projet) : le prévenir. `--platform x11|wayland` impose la plateforme GLFW (Linux : tester ce qui touche aux fenêtres sous les deux ; sous Wayland, `--monitor` est sans effet). Les erreurs GLFW (`[LWJGL] … error`) et OpenAL (`Error when …`, `SoundManager.DisplayError`) comptent comme problèmes.
```bash
python tools/scenario.py "scene Scene2D" wait-loaded "?gl summary" "input ESCAPE" sleep:0.5 scene
```
- Compile (`--no-compile`), construit `target/classpath.txt`, lance (journal `target/scenario.log`), enchaîne, envoie `exit`, liste les lignes suspectes du journal (dédoublonnées `(xN)`). Code 0 si tout réussit.
- Étapes en plus : `wait-loaded` (fin de chargement de la scène du dernier `scene X`), `sleep:S`, `leakcheck <Scène> [n=2] [via=MenuScene]` (allers-retours ; affiche `no leak` ou les compteurs `gl` modifiés, noms sans suffixe `#id`), `log <regex> [n=10]`. `drag x1 y1 x2 y2 [--hold S]` : glisser complet au bouton gauche (appui en x1 y1, déplacement en 5 étapes pendant S secondes, 0,5 par défaut, relâchement ; remplace `input mouse` + `hold` + `release` + `sleep`). Exemple : `"drag 20 490 300 430 --hold 1s" "?console"`.
- Sortie : `ok` par étape réussie ; `?` devant une étape = réponse complète ; un échec affiche tout.
- Blocage : rien après `--timeout` s (20) → bloqué ; `wait-loaded` trop long → `BLOCKED` + état `gl`, arrêt. Jeu tué après `--max-duration` (300 s).
- `-D clé=valeur` (répétable) : propriété système donnée au jeu (ex. `-D mightylib.commands.access=user`).
- `wait-loaded` passe par la commande `wait loaded` : il attend la fin de tout changement de scène, demandé par `scene X` ou par le jeu (menu, touche simulée), puis la fin du chargement.
- `--strict` : échec ou nom inconnu arrête le jeu (sinon log `… its fallback is used` et `usingFallback` dans `resources` ; démo : `FallbackScene` sans `--strict`). `--attach` (jeu déjà lancé, ni lancé ni fermé), `--keep-open`.
- Souris jamais capturée (`-Dmightylib.input.noCursorCapture=true`, `MouseManager.NO_CAPTURE_PROPERTY` : curseur visible et libre pour l'utilisateur) : regard 3D testé par `input mouse`/`input axis`/`gamepad` ; `--capture-mouse` pour la capture.
- Fluidité d'un chargement : `python tools/scenario.py "scene GLLoading" "stats reset" wait-loaded stats` (`reset` après `scene` exclut le tick qui exécute `init`). Préchargement : `scene PreloadScene`, puis `resources batch <batch>` et `input ENTER`.
- Fuite à la main : `gl` sur une scène, allers-retours, `gl` à nouveau : compteurs et références identiques.

## Analyse statique (`tools/analyse.py`)
`python tools/analyse.py` : profil Maven `analyse` (`mvn -P analyse process-classes`, une sortie à part dans `target/static-analysis`, `target/classes` du jeu intact), environ 30 s. Error Prone s'exécute dans `javac` (forké, avec les `--add-exports` du JDK 17+ ; avertissements dans `target/static-analysis.log`), SpotBugs lit ensuite le bytecode (`spotbugsXml.xml`). Aucun constat ne fait échouer le build.
- Sortie : nombre de constats par motif et par zone (`lib`/`demo`), les motifs des catégories à risque de `bonnes-pratiques.md` (point 11) en premier (`*`). `--details MOTIF…` : `fichier:ligne | outil motif | message` (préfixe du nom) ; `--details-all` ; `--no-run` relit le dernier résultat.
- Filtres : `tools/spotbugs-exclude.xml` (SpotBugs) et les `-Xep:Nom:OFF` du profil dans `pom.xml` (Error Prone) ; chaque exclusion dit pourquoi. Première exécution : sans `-o` pour télécharger les plugins.

## Couverture de code (`tools/coverage.py`)
`python tools/coverage.py` : lance `mvn -P coverage test` (JaCoCo, profil Maven hors build normal, environ 20 s) et affiche lignes et branches couvertes par paquet. `--classes PARTIE` (partie du nom de paquet) : détail par classe ; `--lines CLASSE` : numéros des lignes non couvertes ; `--no-run` relit le dernier résultat ; rapport HTML dans `target/site/jacoco/index.html`.
- Exclus du rapport (liste commentée dans le profil `coverage` du `pom.xml`) : la démo et le code lié à GL, OpenAL ou GLFW (rendu, shaders, surfaces, éclairage, débogage graphique, `GenDeleteResources`, `Screenshot`, gestionnaire et sources de sons, moniteurs), qu'aucun test unitaire ne peut exécuter. Un nouveau code de ce genre s'ajoute à cette liste. Lire les chiffres **par paquet**, jamais comme un pourcentage global à atteindre.
- Usage : repérer la logique pure sans test (algorithmes, `physics`, `utils/math`, `resources/map`) et les branches d'erreur non exercées d'un code déjà testé.

## Profilage
- **JFR** : événements `mightylib.Frame`/`mightylib.Tick`. `jcmd <pid> JFR.start duration=30s filename=rec.jfr` (pid : `jcmd -l`) ou `-XX:StartFlightRecording=…` ; `jfr print --events mightylib.Frame rec.jfr`, ou JMC/VisualVM.
- **GPU** : RenderDoc ou Nsight Graphics (OpenGL 3.3 core).
- **Erreurs GL** : `EngineConfig.setOpenGLErrorCheck(true)` (`Logger.isGLErrorCheck()`) = `glGetError` après les appels sensibles, plus lent.

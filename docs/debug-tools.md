# Outils de debug et de mesure

## Commandes (registre de l'`Engine`, accès selon le niveau)
- **Accès** : en debug, tout (niveau `DEV`) : console en jeu (`²` ou F1), entrée standard et serveur de debug. En release, aucun par défaut (`EngineConfig.setCommandAccess`, `setMaxCommandAccess`, `setCheatCommand` ; option `-Dmightylib.commands.access=none|user|cheat|dev`, bornée par le plafond du build ; un jeu sans console du tout : `setMaxCommandAccess(null)`, l'option est alors ignorée). Détail : `architecture.md`, section **Commandes**. Démo : `-Ddemo.release=true` (release, accès `USER`, plafond `CHEAT`), `-Ddemo.commands.max=none|user|cheat|dev` ; avec `scenario.py` : `-D mightylib.commands.access=user -D demo.commands.max=cheat` (la console en jeu est au niveau joueur, le serveur reste `DEV` ; taper dans la console : `input toggle_player_console`, `input text "help"`, `input key ENTER`).
- `help` : identifiant et propriétaire (`engine`, `game`, `scene`, `window`) des commandes visibles par la source. Le serveur de debug, l'entrée standard et `api` sont au niveau `DEV` : ils voient tout.
- Découpage (`CommandLine.Split`) : espaces ; guillemets doubles pour un mot avec espaces ; `\` gardés (chemins Windows) ; guillemet non fermé = erreur. Dans `scenario.py` : `'screenshot "target/a b.png"'`.
- `Commands.submit(line, source)` depuis tout thread, exécutée au début du tick suivant (`processPendingCommands`) ; source (`ICommandSource` : `game`, `stdin`, `server#N`, `api` par défaut) donnée par `getCurrentSource()` et son niveau par `getCurrentLevel()` pendant l'exécution ; les `ICommandListener` reçoivent chaque commande soumise et son résultat (`CommandEcho` les écrit dans le journal de la console). Entrée standard lue dans un thread à part (mode debug).
- **Écrire une commande** :
  - `BaseCommand(Identifier, ECommandLevel)` : espace de noms du propriétaire (`mightylib`, le jeu, le mod) et niveau minimal obligatoire. Enregistrement : `IProjectLoading.registerCommands(registry)` (jeu), `Scene.addCommand` dans `init` (existe pendant le chargement), `WindowView.addCommand`. Identifiant déjà pris → `IllegalArgumentException`.
  - `execute(String[] args)` (`args[0]` = nom tapé) **renvoie** `CommandResult.ok(message, data JSON)`/`error(...)`, sans écrire en console ; résultat différé : `CommandResult.later(future)` (abandon après `Commands.COMMAND_TIMEOUT_SECONDS` = 30 s). Le `message` est une phrase lisible par le joueur ; les `data` sont le détail pour le développeur (journal : `DEV` seulement). `currentLevel()` permet d'adapter la réponse.
  - `completeArgument(args)` : valeurs du dernier mot inachevé (non filtrées acceptées) ; toute nouvelle commande l'implémente.
  - Sous-commande réservée : `requireLevel(ECommandLevel.DEV, mot)` (même erreur qu'un argument inconnu) et `hasLevel(...)` pour la masquer de la complétion (ex. `console log`, `stats` hors `fps`, chemin de `screenshot`).
  - Commande d'une scène : `requireLaunched(scène)` répond « Scene still loading » avant le `launch` ; une `CommandException` donne sa réponse d'erreur telle quelle.
- **Complétion** (Tab de la console) : `Commands.complete(début de ligne[, source])` → `CommandCompletion` (début du mot, choix triés sans casse, `replacement()` : le seul choix suivi d'une espace, sinon la partie commune). Noms (chemins, et identifiants des chemins partagés ou une fois `espace:` tapé) des commandes visibles, `help` en deuxième mot, puis `completeArgument`. Les commandes générales complètent leurs sous-commandes et valeurs (actions, axes, touches, boutons de manette, caméras, batchs, fenêtres, scènes trouvées dans le package des scènes, fichiers pour `exec`).
- Plusieurs ticks : `Commands.addTickTask` (comparer `Commands.getTick()`, une tâche peut être appelée plusieurs fois par tick).

## Serveur de debug
- `127.0.0.1:7777` (`EngineConfig.setDebugServerPort()`, `-1` = désactivé), sinon port libre suivant ; affiché (`--Debug server listening on …`) et écrit dans `-Dmightylib.debugServer.portFile=<fichier>` (utilisé par `scenario.py` : plusieurs jeux/scénarios simultanés, un `--log` chacun). `--attach`/`mighty.py` : `--port` si pas 7777.
- Protocole : une commande par ligne → une ligne JSON `{"success", "message", "data"}`. Client : `python tools/mighty.py <commande>` (`--wait N`, `--json`, sans argument = interactif).
- Suivi du journal : `console follow on|off` ; le client reçoit aussi, entre les réponses, `{"event": "log", "id", "type": OUT|ERR|COMMAND|RESULT|ERROR|MESSAGE, "source", "text"}` pour chaque ligne (file de 10 000 lignes par client et thread d'écriture à lui : un client lent ne bloque pas le jeu, l'excédent est perdu). `python tools/mighty.py --follow` : affiche tout le journal (sortie du programme, commandes de toutes les sources et résultats) et envoie les lignes tapées comme commandes.

## Commandes utiles
- `console` (mode : closed, overlay, detached) ; `console open|close|toggle|detach|attach|clear` ; `console log [n]` (dernières lignes du journal avec leur id et le niveau qui les voit, 20 par défaut) ; `console log since <id>` (lignes suivantes, pour interroger sans suivi) ; `console follow [on|off]` (voir **Serveur de debug**).
- `help` ; `cheats [on|off]` (si le jeu l'active : `EngineConfig.setCheatCommand`) ; `scene` (courante et `loading`) / `scene <Nom>` (relatif au package de la première scène, ex. `Platformer2D.PlatformerBox2D`) ; `wait <ticks>` / `wait loaded [délai]` ; `reload <all|Type> [noms,…] [re:regex]` (sélection vide = 0 donnée, pas une erreur) ; `resources [all|Type] [noms,…] [re:regex]` (détail des données choisies, 100 au plus) ; `resources batch <nom>` (ce que charge un batch : dépendances connues, chargées, mémoire CPU/GPU estimée) ; `resources preload|unpreload <batch>` (précharge un batch, ou annule) ; `watch [status|<all|Type> [noms,…] [re:regex]|mode poll|service [ms]|off]` (rechargement à chaud sur changement de fichier, éteint par défaut, voir `architecture.md`) ; `exit`. Détail de `resources` : `architecture.md`.
- `stats [champs…]` (chemins pointés, ex. `fps glObjects.Texture` ; sinon temps, appels de dessin, changements de shader/texture, uniforms, octets envoyés, objets GL, mémoire). Décrit la dernière seconde **complète** (attendre `sleep:1.5`). `stats reset` remet à zéro `maxFrameMsSinceReset`, `maxFrameIntervalMsSinceReset` (< 100 ms visé), `maxTickMsSinceReset`, `maxSwapMsSinceReset`.
- `gl` (objets GL vivants, éléments partagés et références) ; `gl summary` (par type `éléments/références`).
- `textureupload` (mode d'envoi des grosses textures à la carte et coût depuis le réglage) ; `textureupload direct|pbo` ; `textureupload bench` (compare les façons d'envoyer une texture sur cette carte, médiane de 5 essais, bloque ~1 s). Réglage au démarrage : `EngineConfig.setTextureUpload` ou `-Dmightylib.texture.upload=pbo`. Mesuré sur RTX 4080 SUPER : `pbo` n'est pas plus rapide (voir `decisions.md`).
- `screenshot [chemin]` (PNG de la frame suivante, défaut `screenshots/`) ; `scale 0.5` ; `rect x y l h` ou `corners x y x2 y2` (pixels fenêtre, origine en haut à gauche). Seulement si le texte ne suffit pas.
- `camera` (liste : position, direction/yaw/pitch/fov en 3D, zoom/rotation en 2D) ; `camera <id|nom>`. 3D : `camera main3D move x y z` / `lookat x y z`. 2D : `camera main2D move x y`, `zoom n` ou `zoom nx ny` (borné, garde le point de référence), `rotation degrés`. Une scène expose ses caméras par `registerCamera(camera, nom)` (`main3D`, `main2D` d'office).
- `monitors [full|modes]` : écrans (résolution, position ; `full` : zone de travail, fréquence ; `modes` : modes vidéo `LxH@Hz`), index de celui de la fenêtre. Choix de l'écran au démarrage (liste `--Monitors :` au journal) : `-Dmightylib.window.monitor=primary|secondary|largest|<index>|<nom>`, sinon `EngineConfig.setMonitorSelector(MonitorSelectors.Primary()|Secondary()|Index(i)|Name(t)|Largest())` ; introuvable → principal ; fenêtre centrée dans la zone de travail.
- **Plusieurs fenêtres** : `windows` (contextes, fenêtres avec id, titre, parent, `modal`, `blocked` = attend une fenêtre modale, focus, `mode` et `display` (réglages d'affichage), tailles, objets GL propres à la fenêtre ; `target` = celle des commandes) ; `window` (la cible), `window <id|titre|contexte>` (la choisir), `window main` (retour), `window close [réf]` (fermer en fin de frame), `window mode windowed|fullscreen|borderless [réf]` (changer le mode, la cible par défaut ; la réponse donne le mode appliqué et la taille). Exemple : `python tools/scenario.py "scene DisplayModesScene" wait-loaded "window mode fullscreen" "input key W" sleep:1 "?window mode fullscreen 2" "?windows" "window mode windowed"` (la seconde fenêtre passe en sans bordure : l'écran a déjà un plein écran exclusif ; plein écran = l'écran de l'utilisateur change de mode, le prévenir). La cible est celle de `input`, `screenshot`, `monitors`, `scene`, `camera`, `wait-loaded`, `exit` ; elle revient à la fenêtre principale quand elle est fermée. `gl` ajoute `glContexts` (VAO/FBO/RBO de chaque contexte GL, suppressions en attente). Exemple : `python tools/scenario.py "scene MultiWindowScene" wait-loaded "input key D" sleep:1 "?windows" "window Dialog" "screenshot scale 0.4" "input key ESCAPE"` (D : dialogue modal, T : fenêtre d'outils avec le renderer de la fenêtre principale, C : second contexte `second-1`).

## Simuler des entrées (`input`)
Appliqué par `InputManager.postUpdate()` au tick suivant, vu par tout ce tick (déterministe). Action ou axe = identifiant complet (`demo:enter`) ou chemin seul s'il est unique parmi les liés (`ENTER`, insensible à la casse) ; un chemin partagé par plusieurs espaces de noms est refusé avec la liste des identifiants.
- Actions : `input <ACTION> [ticks]`, `input hold|release <ACTION>`, `input list` (identifiants des actions et des axes liés).
- Souris (pixels fenêtre ; bouton `left|right|middle|<n>`) : `input mouse x y` (gardé jusqu'à un vrai mouvement), `input click [bouton] [x y]`, `input mouse hold|release [bouton]`, `input scroll y [x]`.
- Clavier (fin de `GLFW_KEY_…` ou nombre) : `input key <TOUCHE> [ticks]`, `input key hold|release <TOUCHE>`, `input text "texte"`. Passe par `KeyboardManager`/`MouseManager`, donc par les actions liées.
- Texte : lire `KeyboardManager.getTypedText()` (rappel `glfwSetCharCallback` + texte simulé), pas `getCorrespondingCharMainKeyPressed`.
- Axes : `input axis <AXE> <valeur> [ticks]`, `… hold <valeur>`, `… release` (remplace les liaisons ; ex. `input axis LOOK_RIGHT 2 30`).
- `input state` : ce que voit le tick (souris virtuelle, boutons, défilement, touches, texte, actions, axes non nuls, `cursorShown`, `cursorMode`).
- Manettes (`gamepad` ; boutons `A`, `DPAD_UP`, `START`… ; axes `LEFT_X`, `RIGHT_TRIGGER`…) : `gamepad list` (connectées, boutons tenus, axes hors zone morte, joueurs), `gamepad connect` / `disconnect <id>` (virtuelle 16+), `gamepad <id> button <B> [ticks]`, `gamepad <id> hold|release <B>`, `gamepad <id> axis <AXE> <valeur> [ticks]` / `hold <valeur>` / `release`, `gamepad assign <id> <joueur>`, `gamepad autoassign on|off`. Scène : `GamepadScene`.

## Scripts (`exec <fichier> [délai]`)
- Une commande par ligne, chemin relatif au répertoire de travail ; vides et `#` ignorées ; arrêt au premier échec. Réponse `{"lines": [{line, command, success, message, data}]}`. Scripts ponctuels dans `tools/scripts/` (ignoré par git) ; seul un script permanent est versionné, ailleurs.
- Les lignes s'enchaînent dans le même tick jusqu'à une réponse différée (`wait`, `screenshot`, `exec`). Entrée simulée vue au tick suivant (`input click`, `wait 1`, `input state`) ; après `scene X`, `wait loaded`.
- Chaque ligne s'exécute avec la source qui a lancé `exec` (son niveau), même les lignes jouées plus tard : un script ne s'élève pas.
- Délai par réponse différée : 30 s (`exec` 300 s). Script récursif refusé. Script long avec `scenario.py` : augmenter `--timeout` (`python tools/scenario.py --timeout 60 "?exec tools/scripts/x.txt"`).

## `scenario.py` (lancer et vérifier le jeu, Claude)
Une fenêtre s'ouvre chez l'utilisateur (sur l'écran secondaire, `--monitor` vide = choix du projet) : le prévenir. `--platform x11|wayland` impose la plateforme GLFW (Linux : tester ce qui touche aux fenêtres sous les deux ; sous Wayland, `--monitor` est sans effet). Les erreurs GLFW (`[LWJGL] … error`) comptent comme problèmes.
```bash
python tools/scenario.py "scene Scene2D" wait-loaded "?gl summary" "input ESCAPE" sleep:0.5 scene
```
- Compile (`--no-compile`), construit `target/classpath.txt`, lance (journal `target/scenario.log`), enchaîne, envoie `exit`, liste les lignes suspectes du journal (dédoublonnées `(xN)`). Code 0 si tout réussit.
- Étapes en plus : `wait-loaded` (fin de chargement de la scène du dernier `scene X`), `sleep:S`, `leakcheck <Scène> [n=2] [via=MenuScene]` (allers-retours ; affiche `no leak` ou les compteurs `gl` modifiés, noms sans suffixe `#id`), `log <regex> [n=10]`.
- Sortie : `ok` par étape réussie ; `?` devant une étape = réponse complète ; un échec affiche tout.
- Blocage : rien après `--timeout` s (20) → bloqué ; `wait-loaded` trop long → `BLOCKED` + état `gl`, arrêt. Jeu tué après `--max-duration` (300 s).
- `-D clé=valeur` (répétable) : propriété système donnée au jeu (ex. `-D mightylib.commands.access=user`).
- `wait-loaded` attend la scène du dernier `scene X` : après un changement de scène fait autrement (commande de jeu, touche), utiliser `wait loaded`.
- `--strict` : échec ou nom inconnu arrête le jeu (sinon log `… its fallback is used` et `usingFallback` dans `resources` ; démo : `FallbackScene` sans `--strict`). `--attach` (jeu déjà lancé, ni lancé ni fermé), `--keep-open`.
- Souris jamais capturée (`-Dmightylib.input.noCursorCapture=true`, `MouseManager.NO_CAPTURE_PROPERTY` : curseur visible et libre pour l'utilisateur) : regard 3D testé par `input mouse`/`input axis`/`gamepad` ; `--capture-mouse` pour la capture.
- Fluidité d'un chargement : `python tools/scenario.py "scene GLLoading" "stats reset" wait-loaded stats` (`reset` après `scene` exclut le tick qui exécute `init`). Préchargement : `scene PreloadScene`, puis `resources batch <batch>` et `input ENTER`.
- Fuite à la main : `gl` sur une scène, allers-retours, `gl` à nouveau : compteurs et références identiques.

## Profilage
- **JFR** : événements `mightylib.Frame`/`mightylib.Tick`. `jcmd <pid> JFR.start duration=30s filename=rec.jfr` (pid : `jcmd -l`) ou `-XX:StartFlightRecording=…` ; `jfr print --events mightylib.Frame rec.jfr`, ou JMC/VisualVM.
- **GPU** : RenderDoc ou Nsight Graphics (OpenGL 3.3 core).
- **Erreurs GL** : `EngineConfig.setOpenGLErrorCheck(true)` (`Logger.DO_CHECK`) = `glGetError` après les appels sensibles, plus lent.

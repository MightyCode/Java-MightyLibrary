# Outils de debug et de mesure — Java-MightyLibrary

Commandes, serveur de debug, lancement du jeu par Claude et profilage.

## Outils de debug et de mesure

### Commandes
- Une commande hérite de `BaseCommand` et implémente `CommandResult execute(String[] args)` (`args[0]` = nom). Elle **renvoie** son résultat (`CommandResult.ok(message, data JSON)` / `error(...)`), elle n'écrit pas dans la console. Résultat connu plus tard (ex. capture après la frame suivante) : `CommandResult.later(future)` ; l'appelant (console, serveur) abandonne après `Commands.COMMAND_TIMEOUT_SECONDS` (30 s).
- Découpage de la ligne (`CommandLine.Split`) : mots séparés par des espaces, un mot avec espaces entre guillemets doubles (`screenshot "target/a b.png"`), barres obliques inverses gardées telles quelles (chemins Windows) ; guillemet non fermé → erreur. Avec `scenario.py`, entourer l'étape de guillemets simples : `'screenshot "target/a b.png"'`.
- Les commandes générales sont enregistrées dans `ListGeneralCommand` ; une scène peut ajouter les siennes (`Commands.addCommand`, retirées au changement de scène, marquées `(scene)` dans `help`). Un nom déjà pris lève `IllegalArgumentException`.
- `Commands.submit(line)` est appelable depuis n'importe quel thread ; l'exécution a lieu sur le thread principal au début du tick suivant (`processPendingCommands`). La console est lue dans un thread à part : le jeu n'est jamais bloqué.
- Commandes disponibles uniquement en mode admin.

### Serveur de debug (piloter le jeu depuis un autre processus)
- En mode admin, le jeu écoute sur `127.0.0.1:7777` (`EngineConfig.setDebugServerPort()`, `-1` pour désactiver) ; si le port est pris (autre jeu ouvert), sur le suivant libre (7778, 7779…). Le port retenu est affiché (`--Debug server listening on …`) et écrit dans le fichier donné par la propriété système `-Dmightylib.debugServer.portFile=<fichier>` : `scenario.py` s'en sert (un fichier par exécution), donc plusieurs jeux et scénarios peuvent tourner en même temps (donner un `--log` différent à chaque scénario simultané). Pour `--attach` ou `mighty.py`, passer `--port` si le jeu visé n'est pas sur 7777. Protocole : une commande par ligne, une ligne JSON en réponse `{"success", "message", "data"}`.
- Client : `python tools/mighty.py <commande>` (`--wait N` pour attendre le démarrage, `--json` pour la réponse brute, sans argument = mode interactif).
- Commandes utiles : `help`, `stats [champs…]` (seulement les champs donnés, chemins pointés ex. `fps glObjects.Texture` ; sinon temps, appels de dessin, changements de shader/texture, uniforms, octets envoyés, objets GL vivants, mémoire), `scene` (scène courante et `loading`), `scene <Nom>` (nom relatif au package de la première scène, ex. `Platformer2D.Test2DPlatformerBox2D`), `screenshot [chemin]` (PNG de la frame suivante, par défaut dans `screenshots/` ; réduite avec `scale 0.5` (4 fois moins de pixels) ; une partie seulement avec `screenshot [chemin] rect x y largeur hauteur` ou `corners x y x2 y2`, en pixels de la fenêtre, origine en haut à gauche), `gl` (objets OpenGL vivants et éléments partagés avec leurs références ; `gl summary` : par type `éléments/références` seulement), `input` (voir ci-dessous), `camera` (voir ci-dessous), `wait <ticks>` / `wait loaded [délai]` (répond après des ticks de jeu, ou une fois la scène courante chargée), `exec` (voir ci-dessous), `reload`, `exit`.
- **Écrans** : au démarrage, avant la création de la fenêtre, le moteur liste les écrans dans le journal (`--Monitors :`) et choisit celui de la fenêtre : propriété `-Dmightylib.window.monitor=primary|secondary|largest|<index>|<partie du nom>` si elle est donnée, sinon `EngineConfig.setMonitorSelector(...)` du projet (`MonitorSelectors.Primary()`, `Secondary()`, `Index(i)`, `Name(texte)`, `Largest()` ou un `IMonitorSelector` maison) ; écran introuvable → écran principal. La fenêtre est centrée dans la zone de travail de l'écran. `monitors` liste les écrans (résolution, position ; `monitors full` ajoute zone de travail et fréquence) et l'index de celui qui affiche la fenêtre. `scenario.py` ouvre le jeu sur l'écran secondaire (`--monitor`, vide pour garder le choix du projet).
- **Caméras** : chaque caméra a un id propre (`getCameraId`) et un nom ; une scène les rend accessibles avec `registerCamera(camera, nom)` (`main3D` et `main2D` le sont d'office). `camera` les liste (position, direction/yaw/pitch/fov en 3D, zoom/rotation en 2D), `camera <id|nom>` en détaille une. 3D : `camera main3D move x y z`, `camera main3D lookat x y z`. 2D : `camera main2D move x y`, `zoom niveau` ou `zoom nx ny` (borné, garde le point de référence du zoom donc déplace la caméra), `rotation degrés`. Utile pour cadrer une capture d'écran.
- **Simuler des entrées** : `input SELECT_UP` (appui d'un tick), `input <ACTION> <ticks>`, `input hold <ACTION>` / `input release <ACTION>`, `input list` (actions et ids). Une action se désigne par son nom (insensible à la casse) ou son id. Les événements sont stockés dans `InputSimulation` et appliqués quand `InputManager.postUpdate()` calcule les entrées du tick suivant : un appui simulé est vu par tout ce tick, comme un vrai appui (déterministe).
  - Souris (positions en pixels de la fenêtre, origine en haut à gauche, comme `screenshot` ; bouton `left|right|middle|<n>`) : `input mouse x y` (curseur gardé jusqu'à ce que le vrai curseur bouge), `input click [bouton] [x y]`, `input mouse hold|release [bouton]` (glisser), `input scroll y [x]`.
  - Clavier (touche = fin d'un nom `GLFW_KEY_…` : `ENTER`, `BACKSPACE`, `A`, `LEFT_SHIFT`… ou un nombre) : `input key <TOUCHE> [ticks]`, `input key hold|release <TOUCHE>`, `input text "texte"`. Touches et boutons simulés passent par `KeyboardManager`/`MouseManager`, donc aussi par les actions qui y sont liées.
  - Texte : `KeyboardManager.getTypedText()` donne le texte tapé pendant le tick (rappel `glfwSetCharCallback` : disposition du clavier, accents et IME déjà appliqués) plus le texte simulé ; c'est la façon de lire du texte (champs, terminal), pas `getCorrespondingCharMainKeyPressed`.
  - `input state` : ce que voit le tick courant (souris en coordonnées virtuelles, boutons, défilement, touches, texte, actions).

### Scripts de commandes (`exec`)
- `exec <fichier> [délai]` : une commande par ligne, chemin relatif au répertoire de travail ; lignes vides et `#` ignorées ; arrêt à la première ligne en échec. Réponse : `{"lines": [{line, command, success, message, data}]}`. Exemple : [tools/scripts/menu-mouse.txt](../tools/scripts/menu-mouse.txt).
- Les lignes s'enchaînent dans le même tick jusqu'à une réponse différée (`wait`, `screenshot`, `exec`…) ; la suite reprend dans le tick où elle arrive. Une entrée simulée est vue au tick suivant : `input click` puis `wait 1` puis `input state`. Après `scene X`, `wait loaded`.
- Délais : chaque réponse différée devient une erreur après son délai (30 s par défaut, `exec` 300 s) ; console et serveur attendent donc toujours une réponse. Avec `scenario.py`, augmenter `--timeout` pour un script long : `python tools/scenario.py --timeout 60 "?exec tools/scripts/menu-mouse.txt"`.
- Un script qui se lance lui-même (directement ou non) est refusé. Côté code : `Commands.addTickTask` pour une commande qui s'étale sur plusieurs ticks (comparer `Commands.getTick()`, pas compter les appels : une tâche peut être appelée plusieurs fois par tick).
- **Traquer une fuite** : relever `gl` sur une scène, faire plusieurs allers-retours vers une autre scène, relever à nouveau sur la même scène. Les compteurs et les références doivent être identiques à chaque passage. Avec `scenario.py`, l'étape `leakcheck <Scène> [n] [via]` le fait seule et n'affiche que `no leak` ou les compteurs modifiés.

### Lancer et vérifier le jeu soi-même (Claude)
Un seul appel avec `tools/scenario.py` (une fenêtre s'ouvre sur l'écran de l'utilisateur : le prévenir) :
```bash
python tools/scenario.py "scene Test2DScene" wait-loaded gl "input ESCAPE" sleep:0.5 scene
```
- Compile (`--no-compile` pour sauter), construit `target/classpath.txt` si besoin, lance le jeu (journal dans `target/scenario.log`), enchaîne les étapes, envoie `exit`, puis liste les lignes suspectes du journal (exceptions, erreurs OpenGL). Code de sortie 0 si tout a réussi.
- Étapes en plus des commandes du jeu : `wait-loaded` (attend la fin du chargement et la scène demandée par le dernier `scene X`), `sleep:SECONDS`, `leakcheck <Scène> [n=2] [via=MenuScene]` (allers-retours puis seulement `no leak` ou les compteurs `gl` modifiés, noms sans leur suffixe `#id`), `log <regex> [n=10]` (dernières lignes du journal correspondantes).
- Sortie courte : une étape réussie n'affiche que `ok` (et le fichier d'une capture) ; préfixer par `?` pour voir toute la réponse (`"?gl summary"`) ; un échec affiche toujours tout. Le bilan du journal compte une seule fois les lignes identiques (`(xN)`).
- Blocages : sans résultat après `--timeout` secondes (20 par défaut : démarrage, réponse à une commande, `wait-loaded`), le jeu est considéré bloqué ; un `wait-loaded` trop long affiche `BLOCKED` avec l'état `gl` et arrête le scénario. Le jeu est tué après `--max-duration` secondes (300 par défaut) quoi qu'il fasse. Augmenter `--timeout` pour un chargement réellement long.
- `--attach` utilise un jeu déjà lancé (par l'utilisateur) sans le lancer ni le fermer ; `--keep-open` laisse le jeu ouvert.
- `stats` décrit la dernière seconde **complète** : attendre au moins une seconde de jeu (`sleep:1.5`) avant de la lire.
- Fluidité d'un chargement : `stats reset` remet à zéro les pires valeurs `maxFrameMsSinceReset` (travail d'une frame), `maxFrameIntervalMsSinceReset` (écart entre deux frames, à garder < 100 ms), `maxTickMsSinceReset` et `maxSwapMsSinceReset`. Ex. : `python tools/scenario.py "scene TestGLLoading" "stats reset" wait-loaded stats` (le `reset` après le changement de scène exclut le tick qui exécute `init`).
- Une capture (`screenshot <chemin>`) seulement si un rendu ne peut pas être vérifié par le texte.

### Profilage
- **JFR** : événements `mightylib.Frame` et `mightylib.Tick` (durée de chaque frame/tick), presque gratuits hors enregistrement. Enregistrer : `jcmd <pid> JFR.start duration=30s filename=rec.jfr` (pid via `jcmd -l`), ou lancer avec `-XX:StartFlightRecording=duration=30s,filename=rec.jfr`. Lire : `jfr print --events mightylib.Frame rec.jfr`, ou JDK Mission Control / VisualVM pour CPU, allocations et GC.
- **GPU** : RenderDoc ou NVIDIA Nsight Graphics (contexte OpenGL 3.3 core) pour inspecter une frame et compter les appels de dessin.
- **Erreurs OpenGL** : `returnOpenGLErrorCheckState()` à `true` active `glGetError` **et** un contexte de debug : le pilote signale les erreurs avec un message lisible (notifications filtrées).

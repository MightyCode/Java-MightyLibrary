# Bonnes pratiques

Points que le projet doit continuer à respecter. **Revue hebdomadaire** (skill `/revue-pratiques`) : quand l'utilisateur demande si le projet les respecte toujours, Claude vérifie chaque point avec sa vérification, puis répond point par point : **respecté**, ou **dérive** (avec la preuve : commande, fichier, chiffre) et l'action proposée. Les corrections ne se font qu'après accord. Ce fichier contient les règles, jamais l'état ni l'historique : l'état est dans la réponse de la revue.

## Méthode
1. **Une branche par sujet, un commit par changement logique, fusion `--no-ff` dans `dev`** (jamais de commit direct sur `dev` ni sur master). `dev` est la branche de travail ; `master` ne reçoit que des versions, par fusion `--no-ff` de `dev` sur demande de l'utilisateur. Branche fusionnée = branche supprimée ; une branche non fusionnée a une raison connue de l'utilisateur. **Exception** : un commit direct sur `dev` est admis pour les docs seules (`docs/`, `CLAUDE.md`, `README.md`, `licence.md` : ouverture ou fermeture d'un point, résultat d'une discussion sur les docs) et pour un tout petit commit (au plus 20 lignes, aucun fichier de `src/main`).
   *Vérification* : `git log --first-parent --oneline dev` depuis la dernière revue (seulement des fusions et des commits admis par l'exception, que `collect.py` marque) ; `git branch --merged dev` (vide hors dev et master) ; `git branch --no-merged dev` (chaque branche expliquée).
2. **Docs à jour dans le même commit que le code.** `current.md` / `later.md` = ce qui reste, sans historique ; `architecture.md` = l'état présent.
   *Vérification* : les commits de la semaine qui changent un comportement touchent aussi la doc concernée (`git log --since="1 week ago" --stat dev`) ; `current.md` ne contient aucune trace d'objectif terminé.
3. **Tests verts, et un test pour chaque bug corrigé** quand il peut s'écrire sans GL. La liste du code couvert dans `CLAUDE.md` est à jour.
   *Vérification* : `mvn -o -q test` ; pour chaque correctif de la semaine, le test qui le reproduit (ou la raison de son absence).
4. **Vérification en jeu** de ce que les tests ne couvrent pas (`tools/scenario.py`, journal sans problème), et description de la vérification manuelle restante.
   *Vérification* : les changements de rendu, d'entrées ou de fenêtre de la semaine ont été lancés en jeu.

## Cap
5. **La démo est le banc d'essai de la bibliothèque** : elle illustre chaque fonctionnalité nécessaire et l'utilise comme un tiers le ferait (module Maven séparé : seulement par l'API publique). Les priorités viennent d'un besoin réel : une scène de démo qui en manque, une mesure, un futur jeu de l'utilisateur.
   *Vérification* : chaque fonctionnalité ajoutée a sa scène de démo (`DemoScenes`) ; les points de `current.md` viennent d'un besoin réel (démo, mesure, jeu) plutôt que d'une envie de perfection ; la démo n'accède à rien de package-private (refusé à la compilation) ni d'un package `internal` (non exporté par le module : refusé à la compilation).
6. **`current.md` = un seul gros point, qu'on peut terminer.** Rien de conditionnel (« si les mesures l'exigent », « si un vrai jeu le demande ») : ces lignes vont dans `later.md`.
   *Vérification* : `grep -n -i -E "si les mesures|si un vrai jeu|seulement si" docs/current.md` est vide ; le point en cours avance d'une revue à l'autre.
7. **Surface de l'API décidée avant le premier jar** : chaque package de `mightylib` a son statut (`package-info`, `@API` : `STABLE`, `EXPERIMENTAL`, `INTERNAL`), toute classe publique concrète est `final` sauf les classes extensibles choisies (`ExtensibleClasses`), dont chaque accroche a sa Javadoc courte. Tout ce qui est public est un engagement. Vérification : `ApiStatusTest`, `ModuleDescriptorTest` et `ExtensionFieldsTest` ; une nouvelle classe publique est `final`, un nouveau package a son `package-info`, une nouvelle classe extensible entre dans `ExtensibleClasses` avec ses accroches documentées.
   *Vérification* : la classification couvre les packages ajoutés depuis la dernière revue. Les classes extensibles choisies n'ont aucun champ `protected` (`ExtensionFieldsTest`).
8. **Le code ancien gagne des tests quand on le touche** (`network/`, GUI, loaders maison, algorithmes) : c'est là que se cachent les bugs.
   *Vérification* : les fichiers anciens modifiés dans la semaine ont gagné un test ou une vérification en jeu.

## Qualité du code
9. **Exceptions** : jamais `printStackTrace()` ; exception inattendue gérée → `Logger.LogException` ; échec attendu d'une ressource → `ResourceException` ; `InterruptedException` → `Thread.currentThread().interrupt()` puis arrêt.
   *Vérification* : `grep -rn "printStackTrace()" */src` est vide ; pas de `catch` vide ou qui avale l'erreur sans la signaler.
10. **Fichiers et flux fermés** (try-with-resources), y compris en cas d'erreur.
    *Vérification* : `grep -rn -E "new (FileInputStream|FileReader|FileWriter|Scanner|BufferedReader)" */src`, chaque résultat dans un try-with-resources ou fermé dans un `finally`.
11. **Analyse statique régulière** : `python tools/analyse.py` (Error Prone + SpotBugs, environ 30 s, Claude peut le lancer) pendant la revue hebdomadaire (`/revue-pratiques`, avec la couverture `python tools/coverage.py`) ; export de l'inspection IntelliJ (*Code → Inspect Code*, export XML dans `target/analyse`, manuel : Claude ne peut pas l'obtenir lui-même) au moins une fois par mois pour le style que ces outils ne regardent pas (point 14). Les catégories à risque sont traitées : `DataFlowIssue`, `AutoCloseableResource`, `NonAtomicOperationOnVolatileField`, `EmptyStatementBody`, `ThrowablePrintStackTrace`, `UNCHECKED_WARNING`.
    *Vérification* : date de l'export de `target/analyse` (demander un nouvel export s'il a plus d'un mois ; un fichier XML plus ancien que les autres est une inspection désormais à zéro, donc obsolète : l'ignorer) ; nouvelles alertes de ces catégories.
14. **Rien de mécanique pour l'analyseur dans le code écrit** : pas d'import inutilisé (retirer ceux que le changement rend inutiles, y compris dans les tests), diamant `<>` et arguments de type inférés (pas de `new X<String>()` ni de `Collections.<T>emptySet()`), `isEmpty()` plutôt que `size() == 0` ou `equals("")`, pas d'initialiseur ou de redéfinition qui répète la valeur par défaut ou le parent, pas de variable locale qui ne fait que copier une autre, `Comparator.comparing`, `Arrays.fill`, `List.of` / `List.copyOf` (Java 11), `assertInstanceOf` / `assertEquals` plutôt que `assertTrue(x instanceof …)`, `final` sur un champ privé jamais réaffecté, `@SuppressWarnings` retiré quand il ne sert plus ; et ce que l'analyse a déjà relevé une fois : `@Override` sur toute redéfinition ou implémentation, un `default` à tout `switch` (même vide : « rien pour les autres valeurs »), `Map.entrySet()` quand la valeur est lue, des interfaces dans les signatures (`List`, `Map`, `Set`, jamais `ArrayList`/`HashMap`), un ensemble (`Set`) pour des identifiants uniques, `removeIf` plutôt qu'un `remove` sur une `List<Integer>`, `StringBuilder` (ou `charAt`) dans une boucle sur du texte, parenthèses quand `&&` et `||` se mêlent, aucun compteur flottant de boucle, aucun membre `protected` dans une classe `final` ni `public` dans une classe imbriquée privée, une constante `static final` en majuscules plutôt qu'un champ `final` d'instance, un compteur statique partagé `Atomic*`, un drapeau lu par un autre thread `volatile`, `Optional` plutôt qu'un `Boolean` nul, `Character.MAX_VALUE` plutôt que `(char) -1`, `java.time` plutôt que `Date`, `copy()` plutôt qu'un `clone()` qui n'appelle pas `super.clone()`, `<p>` après une ligne vide de Javadoc, aucun `catch` vide (une ligne de journal, ou un commentaire et une instruction qui disent pourquoi), une méthode qui peut rendre `null` doublée d'un accès qui l'exige (`requireMainWindow`). **Ce qui est voulu se déclare, avec sa raison, là où l'outil le lit** : profil `.idea/inspectionProfiles/Project_Default.xml` (IntelliJ, versionné), `//noinspection Nom` + commentaire pour un cas isolé, `tools/spotbugs-exclude.xml`, les `-Xep:Nom:OFF` du profil `analyse` du `pom.xml`, mots du projet dans `.idea/dictionaries/project.xml` (orthographe).
    *Vérification* : dans l'export `target/analyse`, `UNUSED_IMPORT`, `Convert2Diamond`, `RedundantTypeArguments`, `SizeReplaceableByIsEmpty`, `StringEqualsEmptyString`, `RedundantMethodOverride`, `EmptyMethod`, `UnnecessaryLocalVariable`, `ComparatorCombinators`, `ExplicitArrayFilling`, `FieldMayBeFinal`, `RedundantSuppression`, `SimplifiableAssertion`, `ArraysAsListWithZeroOrOneArgument` sont vides ; `python .claude/skills/analyse-intellij/summarize.py` les compte. `python tools/analyse.py` ne relève rien hors des filtres déclarés.
15. **Aucun champ public modifiable hors structures de données pures** : une classe à logique expose des méthodes (pas de champ public non `final`, pas de statique public non `final`, pas de collection publique) ; seule une structure de données pure (aucune logique, aucun invariant) garde ses champs publics (`decisions.md`).
    *Vérification* : `PublicFieldsTest` passe ; toute entrée ajoutée à sa liste de structures pures est justifiée (pas de logique dans la classe).
12. **Régressions de rendu** : tant que la comparaison d'images (`later.md`, « Kit de test : suites ») n'existe pas, toute modification de rendu 2D est vérifiée par une capture ciblée.
    *Vérification* : la comparaison d'images existe-t-elle ? Sinon, les changements de rendu de la semaine ont-ils eu leur capture ?

## Rythme
13. **Prendre du recul régulièrement et limiter les chantiers ouverts** : finir avant d'ouvrir. La cadence est élevée ; la revue sert aussi à vérifier que l'infrastructure ne passe pas avant les besoins réels (point 5).
    *Vérification* : nombre de branches non fusionnées et de lignes de `current.md` (pas en hausse sans raison) ; part des commits de la semaine qui ferment un point plutôt qu'en ouvrir un.

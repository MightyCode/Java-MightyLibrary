# Architecture

## Structure
```
src/io/github/mightycode/
  mightylib/       # bibliothèque (ne dépend PAS de mightylibdemo/)
    main/          # MainLoop (la boucle), Engine (services partagés, démarrage, arrêt), Context (scène + fenêtres), WindowContext (une fenêtre + ses entrées), WindowView, WindowConfig, DisplaySettings/EWindowMode (affichage d'une fenêtre), IView/Views (vue courante), Window, ContextManager, MainThread, Workers, GameTime
    scenes/        # Scene, SceneManager, SceneManagerInterface, TemplateSceneLoading, caméras 2D/3D
    resources/     # Resources (pipeline, une instance par Engine), DataType, ResourceLoader, batchs
    graphics/      # GLResources, GLElement, renderer/ (Shape, Renderer, _2D, _3D), shader/, text/, GUI/, lighting/
    console/       # Console (²/F2), ConsoleLog (journal), LogCapture (stdout/stderr), CommandLineEditor, ConsoleInput, rendu (ConsolePanel, ConsoleWindowView)
    inputs/        # InputRegistry (actions et axes), InputManager (liaisons), KeyboardManager, MouseManager, dispositions clavier
    registry/      # Identifier (namespace:path)
    sounds/        # SoundManager (OpenAL, une instance par Engine), arbre de gains
    physics/       # collisions maison, tweenings, B2Utils (JBox2D)
    algorithms/    # A*, Dijkstra, graphes, Wave Function Collapse (silencieux par défaut : `EVerbosity` NONE/ESSENTIAL/ALL passé en paramètre)
    utils/         # commandes, JSON, maths, Logger
  mightylibdemo/   # démo : Main, ProjectLoading, ActionId, AxisId, scènes de démo
resources/         # assets ; batchs/*.batch = groupes de ressources
```

## Démarrage
`Main` remplit un `EngineConfig` (setters enchaînables, seule la scène de départ est obligatoire) → `MainLoop.run(config)` crée l'`Engine`, l'installe comme vue courante et appelle `Engine.setup` : capture de la sortie (`LogCapture`, si console ou mode debug) → GLFW → contexte `"Main"` (fenêtre principale + entrées) → `ShaderManager.init` → `Resources` (loaders obligatoires + `IProjectLoading.loaders()`, liste figée ; dossier `EngineConfig.setResourcesFolder`) → `GLResources` → son (`SoundManager`) → `Commands` (commandes générales) → `SceneManager` (+ `Console`) → `registerCommands` (commandes du jeu) → `contextLoading(fenêtre)` (liaisons d'entrées, appelé de même pour chaque fenêtre ouverte ensuite) → `resources.init()` + `load()` (bloquant) → première scène. `MainLoop.run` fait ensuite la boucle, puis `Engine.shutdown` libère tout.

## Boucle (`MainLoop.run`)
Pas fixe découplé : chaque itération fait **soit** un tick (`Engine.update` : `update` de chaque contexte et de ses sous-fenêtres, son, entrées de toutes les fenêtres, puis `postUpdate`), **soit** une frame (`Engine.displayWindows` : chaque fenêtre est activée (`makeCurrent`) et affiche sa vue, puis `Engine.swapWindows` : `swapBuffers` de chacune, un seul `glfwPollEvents`, fermetures). Ticks en retard abandonnés, sans rattrapage (sous charge le jeu ralentit, le temps de jeu dérive du temps réel). Après les affichages, la frame (contexte GL de la fenêtre principale) traite dans l'ordre `Resources.processUntil`, `MainThread.process` et `GLResources.process` avec le reste de la frame (budget : voir « Ressources CPU »). Arrêt : fenêtre qui `closesEngine` fermée (la principale du contexte principal par défaut) ou `sceneManagerInterface.exit(status)` du contexte principal (fin du tick). `run` libère tout et **renvoie** le code (`ListError`) sans `System.exit` (`Main` fait `System.exit(MainLoop.run(config))`).

## Temps
`GameTime.DeltaTime()` : temps réel entre deux ticks (variable). `FixedDeltaTime()` : 1/TPS, **pour la physique**. Tests : `GameTimeControl` fixe la durée de la frame lue par `Timer` et les tweenings, sans attendre.

## Threads
- **Principal** (`MainThread`) : seul à avoir le contexte GL. Y revenir par `MainThread.execute`/`run`/`supply` (→ `CompletableFuture`, la tâche garde la vue courante de celui qui la poste) ou `thenAcceptAsync(…, MainThread.EXECUTOR)`. File vidée après chaque `display()` dans le reste de la frame (au moins une tâche), après `Resources.processUntil` et avant `GLResources.process`, puis entièrement à la sortie.
- **`Workers`** : pool de `EngineConfig.maxThreads` (`MightyLibrary-Worker-N`, daemon) pour I/O et calcul courts (`Workers.run`/`supply`), **sans GL**. Les étapes `THREAD_CONTEXT` de `Resources` y tournent.
- Boucles longues/bloquantes (réseau, `DebugServer` et ses clients, suivi du journal par un client (`DebugFollow`), entrée standard, encodage de `Screenshot`) : threads dédiés `MightyLibrary-…`, daemon.
- Avec `Logger.isGLErrorCheck()` (drapeau `volatile`, lisible de tout thread), `GenDeleteResources` lève une exception si un objet GL est créé/détruit hors du thread principal.

## Moteur et vue courante
- **`Engine`** (`main/`) : les services partagés, une instance par processus (GLFW et le périphérique son l'imposent), créée et pilotée par `MainLoop` : `resources()`, `glResources()`, `shaderManager()`, `soundManager()`, `contexts()` (fenêtres et entrées), `sceneManager()`, `config()`. Plus aucun singleton : `Resources`, `GLResources`, `ShaderManager`, `SoundManager`, `ContextManager` s'obtiennent par lui.
- **Vue** (`IView` : `engine()`, `context()`, `camera2D()`, `camera3D()`) : ce pour quoi le code s'exécute. `Scene` est une vue (caméras créées au `launch`) ; l'`Engine` l'est aussi hors de toute scène (démarrage, commandes, chargement), sans caméra.
- **Vue courante** (`Views.current()`, `Views.engine()`) : posée par le moteur autour de tout le code d'une vue (`Scene.initByManager`/`launchByManager`/`updateByManager`/`postUpdateByManager`/`displayByManager`/`unloadByManager`, `MainLoop.run`) par `try (Views.Scope s = Views.enter(vue))`. `MainThread.execute` la capture à la soumission et la rétablit à l'exécution. Sans vue courante (worker, avant `run`) : `IllegalStateException` explicite, jamais de repli sur une autre fenêtre.
- Ce qui est créé sans paramètre explicite appartient à la vue courante : `Renderer`/`Shape` (`resources`, `glResources`, caméras par défaut), `Text`, `Animation`, `Texture(String)`, `GUI()`, `ScrollList`, `Scene` (engine et contexte du créateur). Les objets déjà liés à un propriétaire le rendent : `DataType.resources()`, `ResourceLoader.resources()`, `GLElement.glResources()` ; une donnée construite par le code avant d'être ajoutée utilise `resourcesOrCurrent()`.
- Commandes : exécutées sur le thread principal sous la vue de leur propriétaire (l'`Engine` pour celles du moteur et du jeu), elles prennent leurs services par `Views.engine()` (voir **Commandes**).
- Gardés statiques, par nature de processus : `MainThread`, `Workers`, `GameTime`, `Logger.isGLErrorCheck()`, `MainLoop.getMode()`, `EngineStats`, `GenDeleteResources`, `Screenshot`, `TextureUploader`.

## Contextes et fenêtres
- **`Context`** = une scène (son `SceneManager`, ses changements de scène, son écran de chargement) et les fenêtres qui la montrent ; **`WindowContext`** = une fenêtre avec son `GLContext`, ses entrées (`InputManager`, `KeyboardManager`, `MouseManager`) et son presse-papiers. Un `Engine` a un contexte principal (`EngineConfig` : fermer sa fenêtre principale arrête le moteur) et autant d'autres que voulu (`Engine.openContext(nom, WindowConfig, Supplier<Scene>)` : la scène est créée avec le contexte pour vue ; fermer sa fenêtre principale, ou son `exit`, ne ferme que lui, et décharge les batchs de sa scène). Les ressources sont communes à tous.
- **Affichage** : `DisplaySettings` = le mode (`EWindowMode` : `WINDOWED`, `FULLSCREEN` exclusif, `BORDERLESS` = fenêtre sans bordure couvrant son écran à sa résolution) et les réglages fins de chaque mode, chacun avec sa valeur par défaut et ignoré hors de son mode (donc aucun ordre d'appel, et changer de mode n'en perd aucun) : écran (tous ; non donné : celui du parent, sinon celui de la fenêtre principale, elle-même sur l'écran de `EngineConfig.setMonitorSelector`), taille fenêtrée (1280x720), bordure, redimensionnable (fenêtré), résolution (celle de l'écran), fréquence (celle de l'écran) et réduction à la perte du focus (plein écran) et vsync (tous les modes, désactivé par défaut : intervalle d'échange du contexte GL de la fenêtre, commande `window vsync <true|false> [fenêtre]`). Raccourcis : `setWindowMode`, `setSize`/`setWindowSize` (taille fenêtrée), `setMonitor` sur `WindowConfig`/`EngineConfig`. Configs et fenêtres gardent leur copie. En cours de jeu : `WindowContext.setDisplay(...)`/`setWindowMode(...)`, appliqués aussitôt par `glfwSetWindowMonitor` et les attributs GLFW (la fenêtre, son contexte GL et ses callbacks restent ; la taille virtuelle ne change pas) ; une fenêtre réduite est d'abord restaurée, puis placée au frame suivant (le système lui rend sinon son ancien emplacement) ; la position fenêtrée est retenue pour y revenir. Un écran n'a qu'une fenêtre en plein écran exclusif : une deuxième passe en sans bordure (message `--`). `WindowInfo.size` suit la taille réelle (callback de framebuffer, relu à chaque fois) ; pendant la lecture des événements, le callback de rafraîchissement redessine la fenêtre (`Context.redrawWindow` : affichage de sa scène ou vue puis swap), car sous Windows la boucle attend dans `glfwPollEvents` tant qu'un bord est tiré : l'image suit le redimensionnement, les ticks attendent le relâchement ; `getWindowMode()` donne le mode appliqué. `MonitorInfo.getVideoModes()` : résolutions et fréquences de l'écran. Démo : `DisplayModesScene` (1/2/3 modes, B bordure, Z redimensionnable, L résolution 1280x720, W seconde fenêtre ; touches lues dans la fenêtre qui a le focus).
- **Sous-fenêtres** : `Context.openWindow(WindowConfig, WindowView, args…)` (`Scene.openWindow`), depuis le code d'une scène ou d'une vue. `WindowView` = petite scène sans changement de scène ni écran de chargement (`launch`, `update`, `postUpdate`, `display`, `unload`, caméras, surface virtuelle, `close()`) ; ses ressources doivent déjà être chargées (batchs de la scène qui l'ouvre). `WindowConfig` : titre, affichage (`DisplaySettings`, voir **Affichage**), taille virtuelle (non donnée : la taille de la fenêtre à sa création), disposition clavier, parent (défaut : fenêtre principale), `modal`, `persistent`, `closesEngine`, `projectInputs`.
- **Arbre des fenêtres** (`WindowTree`, sans GLFW, testé par `WindowTreeTest`) : fermer une fenêtre ferme d'abord ses enfants ; un parent est **bloqué** tant qu'un descendant modal est ouvert (`InputManager.setBlocked` : plus de touche, de bouton, de molette, de texte, d'action ni d'axe, curseur hors fenêtre ; les manettes ne sont pas concernées) ; une fenêtre appartient à la scène (ou vue) qui l'a ouverte, qui la ferme à son `unload` sauf `persistent`. Fenêtre fermée par l'utilisateur ou par `WindowContext.requestClose()` : traitée à la fin de la frame.
- **Natif** : une sous-fenêtre est centrée sur son parent et, sous Windows, a le parent pour propriétaire (`NativeWindowOwner` : `GLFWNativeWin32` + `User32.SetWindowLongPtr(GWL_HWNDPARENT)` : au-dessus du parent, masquée avec lui, sans entrée dans la barre des tâches) ; ailleurs, simple `GLFW_FLOATING`.
- **Plateforme GLFW** (`WindowPlatform`, journal `--GLFW platform : …`) : GLFW choisit (Wayland dans une session Wayland), `-Dmightylib.glfw.platform=x11|wayland|win32|cocoa|null` l'impose. Sous Wayland le compositeur place les fenêtres : ni position lue ou fixée (pas de centrage, pas de retour à la position fenêtrée, `monitors` ne connaît l'écran que d'une fenêtre en plein écran), ni `GLFW_FLOATING`, ni icône ; le moteur saute ces appels (`CanPlaceWindows`, `CanFloatWindows`, `CanSetWindowIcon`) au lieu de laisser GLFW lever `GLFW_FEATURE_UNAVAILABLE`.
- **Code d'une vue** : le moteur active le contexte GL de la fenêtre de la vue avant d'exécuter son code (`bindWindow` dans les `…ByManager` de `Scene` et `…ByContext` de `WindowView`) et le rend ensuite ; un objet créé dans une fenêtre (renderer, texte) peut être affiché dans une autre (VAO créé à la demande, voir « Contextes GL »), pas un `FrameBuffer`.
- Démo : `MultiWindowScene` (D : dialogue modal, T : fenêtre d'outils qui affiche le renderer de la fenêtre principale, C : second contexte avec `Scene2D`).

## Cycle de vie d'une scène
`init(args)` → (scène de chargement pendant les batchs) → `launch(args)` → `update()`/`postUpdate()`/`display()` → `unload()` → `release()`.
- Exemple commenté : `mightylibdemo/scenes/DocumentationScene` (batch `documentation`, `resources/data/documentationScene.json`, texture créée dans `init`, supprimée dans `release`).
- Paires : `launch` ↔ `unload` (seulement si `launch` a eu lieu, avec `super.unload()`) ; `init` ↔ `release` (toujours, même si quittée pendant le chargement).
- `init`/`launch` facultatifs, **sans `super`** : le moteur (`initByManager`/`launchByManager`) crée la scène de chargement, puis caméras et framebuffer virtuel avant `launch`. `init` déclare (ressources préchargées), `launch` crée les renderers.
- Activation des composants GUI (`GUI`, `GUIList`, `ScrollList`, `TextField` : voir **Rendu**, GUI) : chaque `GUI` a un déclencheur (`setTrigger(EInputState)`, `Pressed` par défaut ou `Released`) et `isActivated(inputManager, actions...)` ; `GUIList.getActivated()` et `ScrollList.getActivated()` renvoient l'élément activé à ce tick après `setupActivationActions(actions...)`. `InputManager.isInput(id, EInputState)` choisit Press, Release, Pressed ou Released par une valeur d'enum. Le menu de la démo : voir **Rendu**.
- Scène de chargement : `EngineConfig.setLoadingScene` (défaut `DefaultLoadingScene`, fond gris) ou `createLoadingScene(args)` (`null` = rien) ; elle reçoit le `sceneManagerInterface` de la scène chargée et peut changer de scène (démo : Échap → menu, la scène en cours de chargement est déchargée). Surface virtuelle : `createVirtualSceneBindable()`.
- Ressources : surcharger `getInvolvedBatch()` (fichiers de `resources/batchs/`). Changement de scène (`SceneManager.changeScene`) : `unload` de l'ancienne scène, `loadBatch` de la nouvelle, puis `unloadBatch` de l'ancienne et annulation du préchargement : ce que les deux partagent (données et éléments GL) n'est jamais libéré entre-temps. `Scene.unload` n'appelle `unload` qu'une fois par objet (ajouté comme updatable et displayable).
- `display()` : `setVirtualScene(); clear(); …; setAndDisplayRealScene();`. Changer de scène : `sceneManagerInterface.setNewScene(new XScene(), args)`. `postUpdate()` remet à zéro les états pressed/released.

## Ressources CPU (`Resources`)
- Type = `DataType` + `ResourceLoader`. Les loaders sont donnés à la construction de `Resources` : obligatoires (shaders, icônes, textures, animations, polices, JSON, batchs) puis ceux du projet (`IProjectLoading.loaders()`, démo : `ProjectLoading`), dans cet ordre ; la liste ne change plus ensuite (lue par `loaders()`, package-private), un loader par type de donnée (doublon → `IllegalArgumentException`). **Dossier** : `resources.folder()` (`EngineConfig.setResourcesFolder`, `"resources/"` par défaut, normalisé avec `/` final), `final` et donné au constructeur, donc lisible par les workers et l'observateur sans synchronisation ; les loaders le lisent par `resources()`, `ShaderManager` le reçoit à sa construction, `SoundManager` y lit l'arbre des gains. Deux `Resources` sur deux dossiers ne se voient pas (`ResourcesFolderTest`). Accès : `resources.getResource(TextureData.class, "nom")` (`resources` : champ de `Scene`, `Views.engine().resources()` ailleurs). Nom = fichier sans extension → **unique par type**.
- États : créé → **preload** (`initWithFile` : disque, dépendances) → **load** (`internLoad`, dépendances chargées) → unload (`internUnload`, ou `internCancelPreload`).
- `TYPE_SET_UP` : `THREAD_CONTEXT` (workers, ≤ `maxThreads`), `MAIN_CONTEXT` (thread principal, dans le budget de la frame), `THREAD_PRELOAD_MAIN_LOAD` (lecture par un worker, calcul sur le thread principal : `Shader`), `IMMEDIATELY_IN_CURRENT_CONTEXT` (dans l'appel, ex. descriptions de batchs). Unload toujours sur le thread principal. Une étape en file est vérifiée **au moment de démarrer** (`stepStillNeeded`) : donnée plus voulue (scène quittée, copie abandonnée) ou à relire → sautée (`skippedSteps` dans `resources`), puis `update` la vide ou la relance ; voulue à nouveau entre-temps → étape gardée. Un chargement peut se faire en plusieurs étapes : `internLoad` renvoie `true` et `loadContinues()` aussi, `Resources` relance alors `internLoad` comme une nouvelle étape (les autres étapes passent entre deux) ; `Shader` compile vertex, fragment, geometry puis lie, une étape chacun ; abandonné en route, il est libéré par `internCancelPreload`. Une étape commencée va au bout (ou s'arrête à `checkCancelled()`). Sons : un `SoundDecoder` par format (`resources/sound/decoder` : ogg = STB Vorbis, wav = `javax.sound.sampled`, mp3 = JLayer (LGPL), flac = `FlacStream` écrit pour le moteur ; `SoundLoader.addDecoder` en ajoute, le dernier ajouté gagne pour une extension) ; les noms de ressource sont ceux des fichiers sans extension (deux fichiers de même nom : avertissement). `SoundDataType.readVorbis` décode par morceaux (`DECODE_CHUNK_SAMPLES`) avec `checkCancelled()` entre deux ; le PCM est en mémoire native (`SoundLoadInfo`, construit avec son buffer et son drapeau natif, en lecture seule ensuite), libéré par `SoundLoadInfo.release()` après l'envoi à OpenAL ou par `SoundData.internCancelPreload`.
- **Priorités** : une donnée voulue maintenant (batch chargé, code, dépendance d'une donnée voulue) est *urgente* ; celle qui n'a que des références `preload:` passe après (file à deux niveaux dans `ResourceScheduler`, promue en O(1) quand elle devient urgente ; un worker reste libre pour les urgentes). `finishedCurrentLoading` ne compte que l'urgent : un écran de chargement n'attend pas le préchargement. API : `Resources.preloadBatch`/`cancelPreloadBatch`, `SceneManagerInterface.preloadScene` (scène `PreloadScene`) ; `loadBatch` après un préchargement ne recharge rien.
- **Budget de frame** : `MainLoop` donne une échéance commune à `Resources.processUntil`, `MainThread` et `GLResources` ; sous un écran de chargement le chargement a toute la frame, sinon `EngineConfig.setInGameLoadingShare` (30 % par défaut, pour `Resources` et `GLResources` ; `MainThread` garde toute la frame). Chaque file fait au moins une étape par frame.
- **Poids et progression** : `DataType.estimatedCpuBytes`/`estimatedGpuBytes`, pour le debug seulement (taille décodée une fois lue : pixels des textures, échantillons des sons, tableaux des modèles ; avant lecture, taille des fichiers × un ratio par format : 4 pour les textures, 10 pour OGG/MP3, 2 pour FLAC ; sur la carte, les textures seules), commande `resources batch <nom>`, `Resources.wantedProgress()` ({fait, total} des données voulues maintenant ; l'écran de chargement de la démo affiche « LOADING x / n »).
- **Propriétaire unique** : seul le thread principal change références et états ; les appels d'autres threads (`addOwnedResource` depuis un loader, `addPreLoadedResource` depuis `internLoad`) passent par une file vidée par `process`. Un worker ne fait que lire/calculer. Une donnée ne lit aucun `Resources` global à sa construction : celui qui l'enregistre (création par les loaders, découverte, fallback, `addResourceAndSetUp`, `addPreLoadedResource`, `addOwnedResource`, copie de rechargement) s'y attache (`DataType.attachTo`), une seule fois ; `DataType.resources()` le rend, et échoue (`IllegalStateException`) tant que la donnée n'est pas enregistrée. `Model` ajoute et libère ses textures possédées auprès de ce même `Resources`.
- **Découpage de `Resources`** (façade, cycle d'état `update`/`startStep`/`endStep`/`fail`) : `ResourceScheduler` (files à deux niveaux, workers, échéance), `DependencyGraph` (dépendances, attentes), `ReloadManager` (rechargement à chaud), `BatchManager` (lots), `FallbackRegistry` (données de repli), `ResourceDescriber` (JSON de debug). Tous package-private, thread principal.
- **Réconciliation** (`Resources.update`) : voulue = référencée (sauf suppression/sortie). Une donnée dont une étape tourne n'est jamais modifiée ; à la fin, voulu/état est recomparé.
- **Dépendances** : une donnée voulue et préchargée référence les siennes (`dependency:<Type>:<nom>`, pas à lister dans le batch, gardées tant qu'elle est chargée ; `onlyAsDependency` dans `resources`) ; elle est réveillée quand l'une est chargée.
- **Échec** (`Resources.fail`, exception du loader, `internLoad` → `false`) : retour à l'état initial, dépendances rendues, pas de nouvel essai tant que voulue (sauf `reloadAllOfType`). Ceux qui attendent prennent le placeholder du type, sinon échouent en chaîne. Échec **attendu** (fichier manquant/illisible, format inconnu, contenu mal formé) : le loader lève `ResourceException` (sans pile ; `FileMethods.readFileAsString`/`readJSONObject`, `IconLoader`, `FontFile.load` le font) → une ligne ; toute autre exception = bug → pile complète (`Logger.LogException`). Une icône en échec laisse l'icône par défaut.
- **Placeholders** (`ResourceLoader.createFallback`, nommés `error`, générés, chargés au démarrage, jamais déchargés/rechargés ; un placeholder en échec lève une exception) pour les types primaires : texture (damier magenta/noir, + version rectangle), son (bip), shader (magenta), police (carrés), animation (une image), modèle (cube). Types complexes (JSON, CSV, tilemaps, tilesets, batchs…) : `null`, plantage accepté. `Resources.usable(type, donnée)` = donnée si chargée, sinon placeholder (échec **ou chargement en cours**) ; `getResourceOrFallback` pour un nom inconnu (signalé une fois). Les utilisateurs (`Texture`, `SoundSource`, `Shape`, `Text`, `Animation`, `ModelRenderer`) résolvent à l'usage : une donnée chargée plus tard ou relue avec succès remplace le placeholder. Placeholder signalé une fois, à l'échec ; `resources` liste `usingFallback`.
- **Mode strict** (`EngineConfig.setStrictResources`, `-Dmightylib.resources.strict=true`, `scenario.py --strict`, debug seulement) : échec ou nom inconnu → exception.
- Références par nom (batch, `preload:<batch>` pour un préchargement, `"manually"`, `"all"` pour `loadAllOfType`, `dependency:<Type>:<nom>`, propriétaire) ; liste, doublons permis.
- **Rechargement à chaud** (`Resources.reload(donnée)`, `reloadAllOfType`, commande `reload`) :
  - donnée **chargée** jamais vidée : `DataType.createReloadCopy` → copie lue à part (`reloading` dans `resources`), puis `swapContent` (identité et références gardées), la copie décharge l'ancien contenu. **Échec = version précédente gardée** (exception en strict). Nouveau `reload` pendant la lecture : nouvelle copie lue tout de suite, l'ancienne abandonnée (plus voulue : son étape en cours s'arrête au prochain `checkCancelled()` du loader, sinon va au bout et son résultat est jeté ; si elle attendait ses dépendances, libérée aussitôt) ;
  - **annulation** : `update` pose le drapeau `cancelled` d'une donnée dont l'étape en cours est inutile (plus voulue, relecture demandée) ; le loader l'interroge par `checkCancelled()` (`CancellationException`, silencieuse, comptée dans `skippedSteps`), à placer avant la phase coûteuse ;
  - **copies bornées** (`Resources.setMaxReloadCopies`, 32 par défaut) : au-delà, la donnée reste utilisable avec l'ancien contenu et attend une place (`ReloadManager.mustWait`/`wakeDeferred`) ;
  - `DataType.getVersion()` augmente à chaque changement ; les utilisateurs comparent leur version (`Texture`, `TileMapRenderer`, `Text`, `ModelRenderer`), pas d'écouteurs ;
  - les `dependents` (via `DependencyGraph.acquire`) sont relus en chaîne (texture → tileset → tilemap, atlas → police), chacun attend ses dépendances (`DependencyGraph.allReady`) : un seul calcul par donnée lors d'un `reload all` ;
  - non relues : sans source (`hasSource()` faux), préchargées par le code, placeholders ; recalculées (sauf placeholders) si une dépendance change. Une donnée en échec ou en premier chargement est relue sur place ;
  - type sans copie (`createReloadCopy` → `null` : mods, sous-types) : vidé puis relu sur place (signalé une fois). Un sous-type n'hérite pas de la copie du parent ;
  - batch : `loadBatch` garde sa liste, `unloadBatch` libère exactement celle-là ; description relue pendant qu'il est chargé → ajouts chargés, retraits libérés ; description citant une donnée inconnue non appliquée (vaut aussi pour un batch préchargé) ;
  - **observateur de fichiers** (`Resources.watcher()`, `ResourceWatcher`) : **éteint par défaut**, démarré explicitement par le code (`watchAll()`, `watchType(...)`, `watch(ResourceSelection)`), la commande `watch` ou `-Dmightylib.resources.watch=poll|service` (`EngineConfig.setWatchResources`, intervalle `…watch.interval` en ms). Une `ResourceSelection` (réutilisable ailleurs, ex. batchs) = tout, ou un type, + noms et/ou regex sur le nom (nom dans la liste OU regex) ; les sélections s'additionnent. Seules les données chargées (ou en échec) avec fichier (`DataType.sourcePaths()`), ni placeholders ni créées par le code. Modification ou création → `Resources.reload` (les dépendants suivent) ; suppression ignorée (version gardée, une ligne). Changement rapporté quand le fichier est stable 200 ms (éditeurs qui écrivent en plusieurs temps). Détection (`FileChangeDetector`, thread démon) : **scrutation** date/taille à chaque intervalle (défaut 1 s, marche partout) ou **WatchService** (moins coûteux, non récursif : un enregistrement par dossier, repli sur la scrutation d'un dossier non enregistrable). Liste des fichiers suivis rafraîchie chaque seconde. **Regroupement** : les changements d'une même donnée (description + sources écrites l'une après l'autre) sont rechargés une seule fois, 300 ms après le dernier. **Fichiers nouveaux** : les dossiers de `resources/` sont suivis aussi (date du dossier / `WatchService`) ; un dossier modifié lance `Resources.discoverNewFiles` (thread du détecteur, `ResourceLoader.discover`, par défaut `create`) puis enregistre sur le thread principal les données absentes que la sélection accepte, et rafraîchit les batchs chargés (motifs). `TextureDataLoader.discover` ajoute les images de `textures/` absentes de `textures.json`, avec les paramètres par défaut de `TextureData` (realistic, 2D) et un avertissement. Limite : fichier déposé dans un sous-dossier créé il y a moins d'une seconde, vu au prochain changement de dossier. Tests : `FileWatchTest` ;
  - nouveau type : implémenter `createReloadCopy` (copier les réglages donnés par le code, ex. `TextureData.copySettingsFrom`) et `swapContent` (échanger tout ce que lisent `initWithFile` et `internLoad`).
- Commande `resources` : par type, chargées/préchargées/référencées, mémoire estimée (`cpuBytes`/`gpuBytes`, totaux), chargées sans référence (fuite), référencées non chargées, état du pipeline (dont `wantedDone`/`wantedTotal`, étapes de préchargement) ; `resources batch <nom>`, `resources preload|unpreload <batch>`. Tests : `Resources*Test` (base `ResourcesTestBase` ; batchs, annulation, dépendances, échecs et repli, ressources manuelles, rechargement, préchargement, cycles aléatoires).

## Ressources GPU (`GLResources` / `GLElement`)
- Objets GL partagés et comptés, clé = classe + nom : `addElementOrReturnIfPresent()` ajoute une référence urgente (à équilibrer par `releaseResource()`) ; `getResource()` cherche sans référencer. Libérer plus que référencé (objet déchargé deux fois) est refusé avec une ligne d'erreur.
- **Éléments des batchs** : une donnée listée directement dans un batch fait envoyer son élément GL pendant le chargement (`DataType.glElementType`/`glElementName`/`createGLElement` : `TextureData` → `Texture` de même nom, `TileMap` → texture de son atlas `tilemap:<carte>`, celle de `TileMapRenderer`) ; une entrée de batch s'en exclut par `"gpu": false` (ex. textures de tilesets dans `init.batch`, qui ne servent qu'à construire l'atlas) ; une dépendance n'est pas envoyée. `BatchManager` tient une référence par chargement de batch (via `IGLElementSink`, implémenté par `GLResources` et donné à `Resources` par `MainLoop` ; absent dans les tests de `Resources`), rendue par `unloadBatch`/`cancelPreloadBatch` ou une nouvelle description. Les renderers trouvent l'élément déjà chargé : `launch` n'envoie que ce qui n'est pas dans les batchs.
- **Urgence** : un élément est urgent s'il a une référence urgente (renderer, batch chargé) ; sinon préchargé (`preload:<batch>`). Deux files ordonnées (`LinkedHashSet`, passage de l'une à l'autre en O(1)) : `process` passe les urgents puis les préchargés ; `hasElementsToLoad` ne compte que les urgents (`gl summary` : `waitingToLoad`/`waitingToPreload`). À la sortie, `unload` supprime aussi les éléments encore référencés.
- **Jamais bloquant** : l'ajout met en file ; après chaque `display()`, `GLResources.process(deadline)` avec l'échéance du chargement (toute la frame sous un écran de chargement, part `setInGameLoadingShare` sinon), au moins une étape ; plafond `EngineConfig.setMaxGLUploadMillisecondsPerFrame`. `GLElement.load(ms)` renvoie `false` tant qu'il n'a pas fini. Une étape peut libérer d'autres éléments (`releaseResource` les retire des files en cours de parcours). Tests : `GLResourcesTest` (sans GL).
- `Texture` : > 4 Mio (2D) envoyée par bandes `glTexSubImage2D` (256 Kio–4 Mio selon débit mesuré et temps restant). Non chargée (en cours/échec) → `bind` du placeholder de même type (1×1 transparent tant que le placeholder n'est pas envoyé) ; `hasElementsToLoad` ignore les échecs. Donnée rechargée (version différente au `bind`) → renvoyée dans une seconde texture GL (`GLElement.requestReload`/`reload`, même budget) qui remplace l'ancienne une fois complète. `getWidth/getHeight` = taille affichée ; ce qui en dépend attend `Texture.isUpToDate()` (ex. `TileMapRenderer` garde ses tuiles, animations en pause).
- `ModelRenderer` : une version = un `MeshSet` (une `Shape` par mesh, ses textures), un mesh par frame ; une nouvelle version remplace l'affichée une fois complète. La `Shape` de base ne sert qu'au shader.
- Atlas d'une `TileMap` (`TileSetAtlas`, texture `tilemap:<carte>`) = contenu de la carte construit dans `internLoad`, échangé au rechargement.
- Son rechargé : `SoundData.internUnload` détache le buffer des sources (`Resources.detachSoundBuffer`, branché sur `SoundManager` par son constructeur) avant suppression. À l'arrêt, `Engine.shutdown` supprime les sources après le déchargement des scènes (qui peuvent encore arrêter leurs sources) et avant les buffers, et `unloadSoundSource` vide la liste des sources : le détachement ne touche plus de source supprimée (sinon `AL_INVALID_NAME`). Sources : par défaut, `SoundManager.lateUpdate` supprime une source dès qu'elle s'arrête (son ponctuel, aucune référence à garder). Une source possédée (`SoundSourceCreationInfo.owned` : ambiance, musique) n'est supprimée qu'après `SoundSource.release()`, que son créateur appelle (une scène, dans `unload()` : rien n'arrête un son au changement de scène) ; arrêtée par le rechargement de son son, elle rejoue dès que le nouveau buffer est chargé. `isReady()` dit quand ses réglages sont valides (source créée après le délai, pas encore libérée).
- Chargement de scène : l'écran de chargement reste tant que `GLResources` a des éléments urgents (ceux des batchs de la scène et ce que `launch` a demandé) ; avertissement après 10 s.
- Renderers 2D utilisables dès le constructeur ; géométrie envoyée au premier `display()` puis après chaque modification.
- **Toujours** `GenDeleteResources` (VAO, VBO, EBO, textures, FBO, RBO ; VAO, FBO et RBO sont supprimés dans le contexte qui les a créés), jamais `glGen*`/`glDelete*` (`PrintAll()` au changement de scène).
- **Contextes GL** (`graphics/GLContext`, thread principal) : un contexte racine caché (créé avec la première fenêtre, détruit après la dernière) crée le groupe de partage ; chaque `Window` a son `GLContext` et partage ses objets avec lui. **Partagés** (créés une fois, utilisables dans toutes les fenêtres) : textures, VBO, EBO, PBO, programmes (`Shader`) → `Resources`/`GLResources` restent uniques. **Propres à un contexte** : VAO, FBO, RBO, programme lié (`currentProgram`). `GenDeleteResources.Gen*` enregistre un VAO/FBO/RBO dans le contexte courant ; sa suppression prend le contexte propriétaire (`DeleteVertexArrays(owner, id)`) : immédiate s'il est courant, au prochain `makeCurrent` sinon, ignorée si sa fenêtre est détruite. `Count`/`PrintList` additionnent les contextes vivants. `Window.bindWindow()` = `GLContext.makeCurrent()` (fait aussi `GL.setCapabilities`). `GLResources.process` termine par `glFlush` quand plusieurs fenêtres existent (ce qui est envoyé n'est visible des autres contextes qu'une fois les commandes émises).
- **`Shape`** a un VAO **par contexte**, créé au premier `bind()` dans ce contexte et reconstruit depuis la description des attributs (`vbosVertexSize`, `vbosInteger`, `vbosEnable`, EBO) quand elle change (`layoutVersion`) : un renderer s'affiche dans n'importe quelle fenêtre du groupe. `FrameBuffer` reste lié au contexte qui l'a créé (`bindFrameBuffer` le vérifie sous `Logger.isGLErrorCheck()`). Une création de fenêtre qui échoue est signalée par le callback d'erreur GLFW et la fenêtre reste « non créée ».

## Rendu
- `Shape` = VAOs (un par contexte GL) + VBOs (+ EBO) + `Shader` ; canaux 0 position, 1 UV, 2 normales. `Renderer` = `Shape` + transform (→ `model`) + `ShaderValue` envoyées à chaque `display()`.
- `Shader.sendValueToShader` ne renvoie qu'une valeur changée ; uniform absent du programme signalé une fois et ignoré.
- Uniforms génériques : `projection`, `view`, `model`, `color` (`ShaderManager`). Shaders listés dans `resources/shaders/<3_30|1_40>/shaders.json` ; **un nouveau shader existe dans les deux versions**.
- 2D/3D décidé par le shader (`isDimension2DShader`), qui bascule le depth test à chaque dessin.
- Textes dessinés (`DrawnTexts`, thread principal) : chaque `Text.display()` enregistre son texte, la position de son premier caractère (espace de sa caméra), sa taille et son corps dans des entrées réutilisées (aucune allocation une fois les frames stables) ; `MainLoop` appelle `beginFrame` avant `Engine.displayWindows`, et la commande `gl text` lit la dernière frame complète, triée de haut en bas puis de gauche à droite (toutes fenêtres confondues).
- **Retour à la ligne** : `Text.setMaxWidth(largeur)` (0 = aucun, défaut ; padding non compté) coupe aux espaces avec `TextWrap` (sans GL, mesure injectée) : le saut de ligne est ajouté **après** l'espace qui finit un mot, donc `text()` reste le texte donné et chaque caractère garde son indice (`getPositionOfChar`) ; un mot plus long que la ligne est coupé là où elle est pleine (un caractère au moins), les sauts de ligne du texte sont gardés. `fitText` et la coupe par caractère de la console sont à part. Scène : `TextPaddingScene`.
- **GUI** (`graphics/GUI`) : `GUI` (composants sélectionnables : survol, `forceSelect`), `GUIList` (navigation haut/bas entre composants, activation), sliders, sélecteurs, `BackgroundlessButton`. `TextField` (un `GUI`) : une ligne de texte, prend le focus de sa fenêtre au clic dedans (`InputFocus`) et le rend au clic dehors (le clic reste pour la scène), Échap, Entrée, Haut ou Bas ; édite avec les touches de la ligne de saisie de la console (`console/LineEditKeys` : curseur, mots, Début/Fin, Retour arrière/Suppr, sélection Maj, Ctrl+A/C/X/V, partagées avec `ConsoleInput`) ; texte d'invite gris, curseur clignotant, ligne défilée autour du curseur. La logique est `TextFieldModel` (sans GL, testée) ; la scène appelle `update()` puis lit `isChanged()`, `isSubmitted()`, `getLeftWith()` (touche qui a rendu le focus). Un seul champ est prévu (focus par composant, Tab et plusieurs champs : `later.md`). `ScrollList` : liste à molette, une ligne sélectionnée en permanence (`ListSelection`, sans GL : sélection, première ligne montrée, `setItems` qui garde l'élément sélectionné s'il existe encore, sinon la première) ; haut/bas par `setupKeyboardActions` ou `moveSelection(±1)` (`false` aux extrémités, sans boucle), la molette fait défiler sans changer la sélection, le survol la déplace quand la souris bouge, un déplacement au clavier ou de nouveaux éléments cachent le survol jusqu'au prochain mouvement de souris ; `getActive()` = ligne survolée sinon sélectionnée, `getActivated()` = clic sur la ligne survolée ou action d'activation sur la sélectionnée. Scène : `TextFieldScene2D`.
- **Menu de la démo** (`MenuScene`, `SceneChoices` sans GL) : un champ filtre (contient, casse ignorée, sur le nom court), la liste des scènes, un panneau de description, Quit. La liste vient de la complétion de la commande `scene` (`Commands.complete("scene ")`), triée par nom affiché ; le nom affiché est le nom court (`PlatformerBox2D`), le nom relatif (`Platformer2D.PlatformerBox2D`) seulement si deux scènes ont le même nom court (le nom relatif reste celui de la commande et la clé du JSON). `resources/data/menuScenes.json` (batch `menu`) : `hidden` (scènes non proposées), `descriptions` (par nom relatif), `defaultDescription`. Un choix lance `Commands.execute("scene <nom relatif>")`, Quit et Échap (la scène a le focus) `execute("exit")` : démonstration d'une commande lancée par le code, sur la fenêtre de la scène ; un échec s'écrit en rouge dans le panneau et dans le journal. Navigation : haut/bas (W/S) champ → liste → Quit, Entrée choisit (dans le champ : commence la saisie ; Entrée pendant la saisie lance la première scène de la liste). Aucune liste de scènes à maintenir : une nouvelle scène du paquet apparaît seule.

## Entrées
- **Actions et axes enregistrés** : `InputRegistry.action("demo:move_right")` / `axis(...)` renvoie une poignée typée (`InputAction` / `InputAxis`) portant un `Identifier` unique `namespace:path` (`registry/`, minuscules `[a-z0-9_.-]`, `/` permis dans le chemin) ; un identifiant déjà pris (action ou axe) est refusé. Registre statique, global à toutes les fenêtres, rempli à l'initialisation des classes de constantes (pas de phase ni de gel : cf. `later.md`). Moteur : `EngineActions.TOGGLE_CONSOLE` (`²`, `GLFW_KEY_GRAVE_ACCENT`, touche à gauche de 1 quelle que soit la disposition), `DETACH_CONSOLE` (F2) et `RELOAD_TEXTURE` (F5, mode debug), espace `mightylib`, liées dans tout `InputManager`. Projet : `ActionId`/`AxisId` + liaisons `ActionInput(action, IAction)` dans `ProjectLoading.contextLoading`. Toute l'API (`getState`, `getValue`, `isInput`, `getAxis`, GUI, composants caméra) prend les poignées ; `null` = pas d'action. Recherche par texte (`findAction`/`findAxis`, commandes) : identifiant complet, ou chemin seul sans casse s'il est unique ; l'`index()` interne n'est valable que pendant le lancement. Disposition clavier : `EngineConfig.setKeyboardLanguage()` (QWERTY par défaut, et pour un contexte créé sans `WindowCreationInfo`).
- **Manettes** : un `GamepadManager` commun (`Engine.contexts().getGamepadManager()`, ou `InputManager.getGamepadManager()`), mis à jour par `ContextManager.postUpdate` avant les entrées des fenêtres (chaque fenêtre a son `InputManager`) ; GLFW (`glfwGetGamepadState`, disposition Xbox, SDL_GameControllerDB intégrée, `addMappings`, et `resources/gamecontrollerdb.txt` du projet lu au démarrage s'il existe : `loadMappingsFile`) derrière `IGamepadSource` (fausse source en tests).
  - Emplacements 0–15 = joysticks GLFW, 16+ = 8 virtuelles. Connexions appliquées dans `postUpdate` (ensemble stable par tick ; `connectedThisTick()`/`disconnectedThisTick()` durent un tick).
  - Joueurs : plus petit libre, repris à la reconnexion s'il est libre ; `setAutoAssign(false)` + `assignPlayer` pour « appuyez pour rejoindre ». Sans mapping : connectée sans joueur.
  - `Gamepad` : ids GLFW ; sticks -1..1 (y vers le bas), zone morte radiale remise à l'échelle ; gâchettes 0..1.
  - Actions : `InputGamepadButton(bouton[, joueur])`, `InputGamepadAxis(axe, POSITIVE|NEGATIVE[, seuil, joueur])`, `InputSimple(bouton, EInputType.Controller)` ; sans joueur = `ANY_PLAYER`.
- **Valeur** : `InputManager.getValue(action)` 0..1 (1 pour touche/bouton/simulé, progressive pour `InputGamepadAxis` sans seuil ; `InputOr` = max, `InputAnd` = min). Déplacement : `getValue(droite) - getValue(gauche)`, longueur limitée à 1 (cf. `MovingCameraComponent`).
- **Axes** (`AxisInput(axe, IAxis)`, `inputManager.init(actions, axes)`, `getAxis(axe)`) : valeur signée non bornée, sens donné par la liaison (cf. `AxisId`).
  - Liaisons : `AxisGamepad(axe[, joueur])`, `AxisMouse(X|Y|SCROLL_X|SCROLL_Y)` (pixels de fenêtre pendant le tick, `MouseManager.deltaX/Y`, indépendant de la taille virtuelle), `AxisButtons(nég, pos)` (sans double comptage via `InputOr`), `AxisSum(...)`.
  - Réglages, dans l'ordre : `curve(exposant)` (signe gardé ; 2 = précis près du centre), `scale(facteur)` (négatif = inversion), `perSecond()` (× durée du tick : vitesse → déplacement). `scale` sur `AxisSum` = sensibilité commune : regard de la démo = `AxisSum(souris px, stick × 3000 px/s).scale(0.05 °/px)`.
- **Caméra 3D** : `Camera3D` ne lit pas les entrées (`rotate(dYaw, dPitch)` en degrés, droite et haut positifs, tangage ±89°). `FreeCamera3DComponent` (`addUpdatable`) la pilote par axes (déplacement -1..1 × `camera.getSpeed()`, regard en degrés, × `quickFactor` avec `QuickSpeed`) et met la vue à jour avant le code de la scène ; `setLookLocked` bloque le regard.
- **Texte et touches tapées** : `KeyboardManager.getTypedText()` (texte du tick, disposition et IME du système) et `getKeyEvents()` (touches appuyées ou répétées par le système, dans l'ordre, avec modificateurs `KeyEvent` ; touches simulées comprises) pour l'édition de texte. `KeyEvent.letter()` est la lettre que la touche produit dans la disposition du système (`glfwGetKeyName(touche, scancode)` lu dans le callback, minuscule, `0` sans nom ; touches simulées : `glfwGetKeyName(touche, 0)`) : les raccourcis Ctrl+lettre comparent cette lettre, pas la position physique (Ctrl+A en AZERTY est la touche physique Q), et ignorent Ctrl+Alt (AltGr sous Windows, qui tape des caractères : AltGr+L = « ł » en polonais) ; les touches non imprimables (flèches, Début…) restent comparées par code.
- **Focus** (`InputManager.focus()`, `InputFocus`) : qui lit les entrées d'une fenêtre. Pile de détenteurs (objets quelconques), vide = la scène. Tant qu'elle n'est pas vide, la scène ne voit plus touches, texte, souris (curseur hors fenêtre, ni bouton, ni molette, ni mouvement), actions ni axes, **sauf les actions de l'espace `mightylib`** ; lu à chaque requête, donc immédiat. `request(détenteur)` empile (ou remonte) un détenteur, `release(détenteur)` le retire où qu'il soit : la console ouverte par-dessus un `TextField` rend le focus au champ en se fermant. Le sommet (`isCurrent`) lit les valeurs brutes (`getRawKeyEvents`, `getRawTypedText`, `getRawKeyState`, `getRawMouseScroll`, `MouseManager.getRawPos`/`getRawVirtualPos` (pixels de la fenêtre / coordonnées virtuelles), `getRawButton`, `rawButtonPressed`/`rawButtonReleased`, qui suivent la simulation de `input mouse`). **Pas de fuite d'appui** : un changement du sommet efface pour tous, jusqu'au tick suivant, les appuis et relâchements, le texte tapé et la molette du tick en cours (la touche qui rend le focus n'est pas un appui pour le détenteur suivant : Échap qui sort d'un champ ne quitte pas le menu) ; `releaseForClick` (clic ailleurs) garde l'appui de la souris pour la scène, qui reçoit le clic sur un autre composant. L'état des boutons de la souris est calculé à chaque tick quel que soit le focus (seules les lectures publiques le masquent) : un bouton tenu quand le focus est rendu ne compte pas comme un nouvel appui. Distinct du blocage modal (`setBlocked`), qui masque tout, actions du moteur comprises. Un détenteur doit rendre son focus en quittant la scène (`TextField.unload` le fait).

## Commandes
- **Registre** (`utils/enginecommand/Commands`, `Engine.commands()`) : un par `Engine`, créé dans `Engine.setup` avec les commandes générales (`ListGeneralCommand`) ; le `SceneManager` du contexte principal traite les commandes en attente à chaque tick (`updateMain` → `processPendingCommands`). Les commandes générales visent la fenêtre `Engine.targetWindow()` (et son contexte) : celle choisie par `window` (`Engine.commandWindow()`) pour une commande venue de la console, de l'entrée standard, du serveur de debug ou de `submit` ; celle de la vue courante (`Views.current().context()`) quand le code d'une vue appelle `Commands.execute(ligne)` ou `complete(début)` hors d'une commande (`Commands.getCallerWindow()`, rétablie ensuite ; une commande lancée par une autre garde la cible). Les commandes lisent leur cible par `targetWindow()`/`targetContext()`/`ListGeneralCommand.targetScenes()`, jamais par `commandWindow()` (réservé à `window`/`windows`). Appelé depuis le code, `execute` a la source `api` (niveau `DEV`) : il marche aussi quand le build n'a aucun accès aux commandes (`setMaxCommandAccess(null)` borne le niveau de la session, pas les appels du code).
- **Syntaxe déclarée** (`utils/enginecommand/syntax`) : chaque commande déclare son arbre dans `BaseCommand.syntax(CommandNode)` (littéraux, arguments typés `ArgumentType`, options `Option`, handler par branche, description, niveau et condition par nœud ou option). `Commands.executeNow` trouve la commande (nom ou identifiant), vérifie son niveau, puis `BaseCommand.run` appelle `CommandParser.parse` sous le propriétaire : littéraux avant arguments, options `--nom valeur`/`--nom=valeur`/drapeaux valables dans le sous-arbre du nœud qui les déclare, `--` termine les options ; une branche ou option hors niveau, ou dont la condition silencieuse est fausse, donne l'erreur d'un mot inconnu ; sinon l'erreur est précise (« Expected an integer between 1 and 100 for <count>, got ->abc<- ») suivie de l'usage de la branche atteinte. Le handler reçoit un `CommandContext` de valeurs typées et renvoie un `CommandResult`. Le même arbre produit la complétion (`CommandParser.complete`, appelée par `Commands.completeNow`), l'aide (`CommandHelp` : usage par branche, arguments, options, descriptions) et son JSON ; `--help` est une option ajoutée à toute commande. Un schéma incohérent est refusé à l'enregistrement. `resources/ResourceArguments` fournit la sélection de ressources aux commandes qui en prennent. `as` et `complete` (`DEV`) exécutent une ligne ou complètent un début de ligne avec un niveau abaissé.
- **Propriétaires** (`CommandOwner`) : le moteur (`ENGINE`), le jeu (`GAME`), ou une vue (`CommandOwner.Of(vue, "scene"|"window")`, égal par identité de la vue). `register(commande, propriétaire)`, `registryFor(propriétaire)` (interface étroite `CommandRegistry`), `removeOwnedBy(propriétaire)` ; une commande n'est enregistrée qu'à un endroit à la fois (retirée, elle peut l'être à nouveau : scène réutilisée). Jeu : `IProjectLoading.registerCommands(registry)` (méthode par défaut vide, appelée une fois dans `setup` après `init`), commandes gardées tout le programme. Scène : `Scene.addCommand` (dans `init` : la commande existe pendant le chargement), retirées par `Scene.unloadByManager` à côté de `closeWindowsOpenedBy`, donc même si la scène est quittée pendant son chargement ; `WindowView.addCommand`, retirées dans `unloadByContext`.
- **Exécution sous le propriétaire** : la commande d'une vue (et sa complétion) s'exécute sous cette vue (`Views.enter`) avec le contexte GL de sa fenêtre, rétabli ensuite : elle crée des objets comme le code de la scène. Une commande de scène déclare l'état dont elle dépend : `Scene.isLaunched()`, `requires(CommandCondition.launched(scène))` sur sa racine → « Scene still loading » (`camera` fait de même). Une `CommandException` devient la réponse d'erreur, sans « Command X failed ».
- **Identifiants** (`BaseCommand(Identifier, ECommandLevel, description)`, `registry/Identifier`) : générales dans `mightylib`. Résolution comme les actions : identifiant complet ou chemin seul sans casse s'il est unique parmi les commandes **visibles** ; nom ambigu refusé avec la liste des identifiants visibles ; identifiant déjà pris → `IllegalArgumentException`, sauf entre deux vues différentes (même scène ou `WindowView` dans deux fenêtres) : la vue visée l'exécute (`Commands.setViewChooser`, branché par l'`Engine` : vue de `commandWindow()`, sinon la seule de son contexte), sans vue visée la commande est refusée en demandant `window`. Complétion : chemins, plus les identifiants des chemins partagés (tous une fois `espace:` tapé).
- **Niveaux** (`ECommandLevel` : `USER` < `CHEAT` < `DEV`, chacun inclut les précédents ; pas une sécurité) : obligatoire dans le constructeur. `USER` : `help`, `console` (sauf `log`/`follow`), `screenshot` (dossier par défaut seulement), `stats fps`, `cheats` ; `CHEAT` : commandes de triche du jeu ; `DEV` : le reste. Une commande au-dessus du niveau de la source n'existe pas pour elle : absente de `help`, de `help <nom>` et de la complétion, refusée avec **exactement** le message d'une commande inconnue, ignorée par la résolution et l'ambiguïté. Branche ou option : `.level(niveau)` (même refus, absente de la complétion, de l'aide et du JSON), `CommandContext.currentLevel()` pour adapter la réponse.
- **Sources** (`ICommandSource.name()`, `level()`) : console en jeu `game` (niveau de la session, relu à chaque commande), `stdin` et `server#N` (`DEV`, n'existent qu'en debug), `api` (`DEV`, défaut, appel direct). `Commands.getCurrentLevel()` ; `execute(ligne, source)` et `complete(début, source)` s'exécutent comme la source. Scripts (`CommandScript`) : la source de `exec` est capturée et rétablie pour chaque ligne, différées comprises.
- **Accès** : `EngineConfig.setCommandAccess(niveau|null)` (niveau de la session au départ ; `null` : aucun, pas de console ; défaut `DEV` en debug, aucun en release), `setMaxCommandAccess` (plafond du build, défaut `DEV` en debug, `USER` en release ; `null` : aucun accès, jamais, l'option de lancement est ignorée avec une ligne au journal), `-Dmightylib.commands.access=none|user|cheat|dev` (mode développeur d'un jeu publié, borné par le plafond). `Commands.setSessionLevel(niveau)` (le jeu active la triche par ses propres moyens) est borné par le plafond. `EngineConfig.setCheatCommand(true)` enregistre `cheats on|off` (`USER`, bascule `USER`/`CHEAT`, sans effet en `DEV`) si le plafond permet `CHEAT`. Le moteur n'impose aucune règle de sauvegarde.
- Démo : `demo:menu` (jeu, `USER`), `CommandsScene2D` et `demo:spawn` (scène, `CHEAT` : `spawn <nombre 1..100> [--color] [--size] [--at x y] [--shape]`, `spawn clear`, `spawn list` en `DEV`, condition `launched`), `cheats` activée ; options `-Ddemo.release=true` (release, accès `USER`, plafond `CHEAT`) et `-Ddemo.commands.max=none|user|cheat|dev`.
- Tests : `CommandsTest`, `CommandLevelsTest`, `CommandScriptTest`, `main/CommandAccessTest`, `syntax/CommandParserTest`, `syntax/CommandHelpTest`, `resources/ResourceSelectionTest` (sélection et `ResourceArguments`).

## Console
- **`Console`** (`console/`, `Engine.console()`, `null` sans accès aux commandes) : moteur, indépendante des scènes. Existe quand `EngineConfig.getCommandAccess()` n'est pas `null` (voir **Commandes**) ; `setConsoleFont` (défaut `bahnschrift`, à charger au démarrage, sinon police de repli), `setConsoleLogCapacity` (5000 lignes). `print(texte[, niveau])` : message du jeu au joueur (`MESSAGE`, `USER` par défaut).
- **Touches** : `²` (`TOGGLE_CONSOLE`) ouvre et ferme à tout niveau ; un jeu la relie comme toute action (plusieurs touches avec `InputOr`).
- **Modes** : `CLOSED` ; `OVERLAY` (`²`, ou `console open`) : bande en bas de la fenêtre principale (45 % de la hauteur, fond noir à 55 %), dessinée en pixels réels après la scène (`Context.displayWindows`/`redrawWindow` → `Engine.displayConsoleOverlay`), y compris pendant un chargement ; la console prend le focus de la fenêtre principale (curseur montré, rendu à la fermeture). Échap ou la touche d'ouverture ferment ; le focus est rendu aussitôt, la touche qui ferme n'est pas vue par la scène (voir **Focus**). `DETACHED` (F2 console ouverte, `console detach`) : sous-fenêtre « Console » (`ConsoleWindowView`, persistante, ouverte sous la vue `Engine`, sans les entrées du projet), fond noir et texte blanc ; F2 dans cette fenêtre la refusionne (overlay ouvert, focus rendu), sa fermeture ferme la console ; la touche d'ouverture dans la principale lui donne le focus.
- **Tick** : `Console.update()` au début d'`Engine.update`, avant les scènes : lit les entrées brutes de la fenêtre de la console (`ConsoleInput` : texte, ←/→, Ctrl+←/→, Début/Fin, Retour arrière/Suppr, Ctrl+Retour arrière (mot), Maj+←/→/Début/Fin et Ctrl+Maj+←/→ étendent la sélection de la saisie, Ctrl+A/C/X/V (voir **Sélection**), ↑/↓ historique avec brouillon, Entrée, PageHaut/PageBas, Maj+↑/↓ (une rangée), Ctrl+Début/Fin (plus ancienne ligne / fin), molette, souris (voir **Souris**), Ctrl+L vide la console (voir `clear(niveau)` dans **Journal**), Tab style bash : partie commune, puis liste des choix au second Tab ; la même liste n'est pas réécrite tant que rien n'a été écrit après elle (`CompletionListing`) : la ligne de saisie s'éclaire 150 ms à la place, comme un bip visuel) ; une ligne validée part par `Commands.submit(ligne, game)` et s'exécute dans le même tick ; la complétion se fait au niveau de la session.
- **Journal** (`ConsoleLog`, `Engine.consoleLog()`, présent si console ou mode debug) : anneau thread-safe de lignes `{id croissant, type OUT|ERR|COMMAND|RESULT|ERROR|MESSAGE, source, texte, niveau minimal pour la voir}`, `version()`, `version(niveau, types cachés)` (ne change qu'avec ce que ce niveau voit : le panneau ne se refait pas pour une ligne cachée), `last(n)`, `last(n, niveau)` (lignes visibles, sans celles effacées pour ce niveau), `upTo(id, n, niveau, filtre)`, `after(id, n, niveau, filtre)`, `between(de, à, niveau, filtre)` (lecture par id), `since(id)`, écouteurs ; `clear()` oublie tout, `clear(niveau)` (Ctrl+L, `console clear`) en `DEV` aussi, en dessous seulement pour ce niveau et ceux du dessous (le développeur garde le journal : `console log`, serveur de debug). Niveaux : sortie du programme (`OUT`/`ERR`) `DEV` ; commande et `message` de la réponse au niveau de la source quand la commande s'exécute (le même pour les deux, même si elle change ce niveau : `cheats off`) ; `data` (JSON) `DEV` ; autres lignes `USER` par défaut. `LogCapture` remplace `System.out`/`err` dès `Engine.setup` par des flux qui écrivent dans les vrais et donnent chaque ligne complète au journal (retiré à la fin de `shutdown`) ; `rawOut()`/`rawErr()` écrivent sans copie (réponses de l'entrée standard, déjà au journal). `CommandEcho` y écrit chaque commande soumise (`[source] > ligne`) et son résultat, quelle que soit la source (jeu, stdin, client du serveur), au niveau de la source, ou à son niveau d'après quand la commande l'a baissé (`cheats off` reste visible du joueur repassé `USER`). Le serveur de debug (`DEV`) voit tout.
- **Mise en page et défilement** (`ConsoleLayout`, sans GL : la largeur des caractères est injectée, `charAdvance` du `Text` en jeu) : coupe les lignes à la largeur (une rangée = un morceau, au moins un caractère), choisit les rangées visibles et convertit un point du panneau en position du journal et inversement. Le défilement est **ancré sur une ligne du journal** : `null` = suit la fin, sinon `Anchor(id de la ligne du bas, rangées de cette ligne cachées en dessous)` ; les nouvelles lignes ne déplacent donc pas une vue remontée. Une ligne d'ancre cachée par le filtre : la vue se cale sur la ligne visible précédente, l'ancre ne change pas ; ligne oubliée par l'anneau : la plus ancienne gardée ; journal vidé : la fin. Chaque panneau (overlay, fenêtre détachée) a sa mise en page et son ancre. Le travail ne dépend que de ce qui est affiché, pas de la taille du journal (`ConsoleLog.upTo`/`after`/`between`, recherche dichotomique). Entrée et validation ramènent à la fin.
- **Indicateur** : quand la vue n'est pas en bas, « v N lines » (N = lignes visibles sous la vue, filtre et niveau appliqués, une ligne coupée par le bas de la vue compte pour une, « 999+ » au-delà ; la police n'a pas de flèche) est dessiné sur la droite de la dernière rangée ; un clic dessus ramène à la fin. Le compte est refait seulement quand le journal ou l'ancre changent.
- **Filtre** : la console (pas le journal) garde un ensemble de types cachés, partagé par l'overlay et la fenêtre détachée ; `console logs off|on` (`DEV`) cache ou montre `OUT`/`ERR`, état initial `EngineConfig.setConsoleLogsShown` ou `-Dmightylib.console.logs=shown|hidden`. Le panneau ne se refait pas pour une ligne cachée par le filtre (`ConsoleLog.version(niveau, types cachés)`).
- **Sélection** : une seule à la fois, dans la saisie (`CommandLineEditor` : ancre, `selectionStart/End`) ou dans le journal (`LogSelection` : bornes `LogPosition(id de ligne, caractère du texte affiché)`, tabulations = 4 espaces). Ctrl+A : la saisie, puis (2e appui, ou saisie vide) tout le journal visible ; Ctrl+C copie la sélection (rien sans sélection), Ctrl+X coupe dans la saisie et copie dans le journal ; ←/→ sans Maj sur une sélection de la saisie vont à son début/fin ; taper, coller, effacer ou valider efface la sélection du journal. Copie du journal = le texte affiché, lignes d'origine jointes par un saut de ligne sans les coupures dues à la largeur, lignes cachées (filtre, niveau) non copiées (`LogSelection.CopyText`, aussi pour `console copy`). Ctrl+V de plusieurs lignes : une commande par ligne complète (au niveau de la session), la dernière reste dans la saisie. Presse-papiers par `ConsoleInput.IClipboard` (`SystemInfo` de la fenêtre).
- **Souris** (`ConsoleInput.handleMouse`, état du bouton gauche en coordonnées du panneau) : clic dans la saisie place le curseur, glisser sélectionne, Maj+clic étend ; dans le journal, glisser sélectionne ; double clic = un mot (séparateurs de Ctrl+←/→), triple clic = la ligne (du journal, pas la rangée) ; glisser après un double ou triple clic garde le mot ou la ligne ; glisser au-dessus ou au-dessous du journal le fait défiler d'une rangée toutes les 50 ms. Nombre de clics par `ClickCounter` (4 px, 500 ms). Un appui au-dessus de l'overlay (sur le jeu) n'est pas pour la console.
- **Rendu** (`ConsolePanel`, sous une `ConsoleView` : vue à caméra 2D en pixels réels de la fenêtre, `Text` exigeant une caméra) : ne fait que dessiner ce que donne `ConsoleLayout` ; seules les lignes visibles au niveau de la session ; un `Text` par rangée visible (couleur par type, `ConsoleColors`), refaits seulement si le journal, le défilement ou la taille changent : le panneau compare `ConsoleLayout.buildCount()` au compte de son dernier dessin (une lecture qui recalcule, souris ou défilement, ne cache donc pas un calcul au panneau) ; mesure linéaire `Text.measureWidth`/`charAdvance`, pas `fitText`. Surlignage de la sélection : un rectangle par rangée sélectionnée, d'une réserve réutilisée d'une image à l'autre, libérée dans `unload` (les rangées qui finissent une ligne sélectionnée ont 4 px de plus pour qu'une ligne vide se voie). Ligne de saisie défilée horizontalement autour du curseur, sélection dessinée derrière le texte.
- **Couleurs** (`ConsoleColors`, en attendant un thème) : `OUT` gris terne, `ERR` orange terne, `COMMAND` jaune, `RESULT` blanc, `ERROR` rouge vif, `MESSAGE` cyan clair ; sélection bleue translucide.
- **Démo** : `ConsoleFeedScene` écrit une ligne de chaque type à intervalle réglable (↑/↓), pour essayer l'ancre, le filtre, la sélection et l'indicateur pendant que le journal avance. Objets de l'overlay créés à la première ouverture, libérés par `Console.unload` à l'arrêt ; ceux de la fenêtre à sa fermeture.

## Pièges connus (non corrigés)
- Sous Wayland, une sous-fenêtre n'est liée à son parent ni par la position ni par l'empilement (GLFW n'expose pas `xdg_toplevel.set_parent`) : un dialogue peut passer derrière la fenêtre principale ; `BORDERLESS` ne choisit pas son écran.
- Une `TileMap` relue perd les changements faits par le code (`setTileType`).
- **Padding du texte** : `Text.setPadding(gauche, haut, droite, bas)` écarte le texte des bords de son rectangle, qui l'inclut : `size()`, `leftUpPosition()`, la référence (`setReference`) et la position portent sur le rectangle avec padding, l'alignement des lignes sur la largeur du texte seul. Scène : `TextPaddingScene`.
- 2D sans batching : chaque `Shape2DRenderer`/`Animation2DRenderer`/`Text` a VAO/VBO/EBO et draw call, avec `glUseProgram`, uniforms et depth test à chaque dessin.
- `Shape.updateVbo` réutilise le buffer à taille égale (`glBufferSubData`), sinon réalloue ; les `calculate*()` allouent un `float[]` à chaque appel.
- `TileMapRenderer` : une animation de tuile ne réécrit que ses UV, mais toute modification de carte (`hasBeenUpdated()`) reconstruit tout.
- `Shape2DRenderer` alloue en `STATIC_STORE` même pour des VBO modifiés.

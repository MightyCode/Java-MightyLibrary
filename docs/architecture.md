# Architecture

## Structure
Projet Maven à sept poms, chacun hérite du précédent (résolution par `relativePath`, sans `install`) ; chaque module ne déclare que ce qu'il utilise :
- **`bom/`** (`mightylib-bom`) : seulement les versions (propriétés, `dependencyManagement` : BOM LWJGL importé, `mightylib` et `mightylib-test` en `${mightylib.version}`, json, joml, jbox2d, opensimplex, jlayer, apiguardian, junit). Pas de plugin ni de profil : un jeu qui a déjà son parent l'importe (`scope` `import`).
- **`base-parent/`** (`mightylib-base-parent`, parent : le BOM) : `maven.compiler.release` 11 (un jeu peut le relever), UTF-8, `pluginManagement` (compiler, surefire avec `useModulePath=false`, jar, assembly, exec), `default-testCompile` sur le classpath, les six profils d'OS (`lwjgl.natives` : `natives-windows`, `-windows-arm64`, `-linux`, `-linux-arm64`, `-macos`, `-macos-arm64` ; macOS non testé) et le profil `analyse` (Error Prone et SpotBugs), réglé par les propriétés `mightylib.errorprone.args` (options `-Xep:…:OFF`) et `mightylib.spotbugs.exclude` (fichier d'exclusions), vides par défaut.
- **`game-parent/`** (`mightylib-game-parent`, parent : `base-parent`) : le parent d'un jeu. Les natives de la machine des six modules LWJGL du moteur (`runtime`, `${lwjgl.natives}`), le profil `all-natives` (les six plateformes, pour un jar complet multiplateforme), `exec` et le jar complet (`jar-with-dependencies`, `Main-Class`), tous deux à partir de la propriété `mightylib.mainClass` que le jeu fixe. Le jar complet est dans un profil `game-jar`, actif seulement si `src/main` existe (pas dans ce pom lui-même). Il déclare le kit de test `mightylib-test` en portée `test` (jamais dans le jar du jeu). Il ne déclare pas `mightylib` : le jeu le déclare, la version vient du BOM ; les natives d'un module LWJGL ajouté par le jeu se déclarent chez lui, avec `${lwjgl.natives}`.
- **Racine** (`mightylib-parent`, parent : `base-parent`) : l'agrégateur et le parent de la bibliothèque ; le profil `coverage`, les options `-Xlint` du module du moteur et les valeurs d'analyse du moteur (`tools/spotbugs-exclude.xml`, liste `-Xep`).
- **`mightylib/`**, **`mightylib-test/`** et **`demo/`** ci-dessous. La démo hérite de `game-parent` (et non de la racine) : elle valide à chaque build le parent des jeux, et répète donc les valeurs d'analyse du moteur dans son pom.
- **`mightylib/`** (artifactId `mightylib`) : la bibliothèque, un jar léger (aucune dépendance embarquée, pas de classe principale). Seulement les jars Java de LWJGL ; les natives viennent de l'application (`game-parent`), et ici en portée `test` (STB et la mémoire de LWJGL pour les décodeurs de son). Les aides de ses tests unitaires (`MainThreadTestAccess`, `WorkersTestAccess`, `TestWindows`, `GameTimeControl`, `ResourcesTestBase`…) restent dans ses sources de test, non publiées.
- **`mightylib-test/`** (artifactId `mightylib-test`, parent : la racine) : le kit de test des jeux (voir « Kit de test »). Dépend de `mightylib` et, en `optional`, de `junit-jupiter-api` ; sans `module-info` (classpath seulement : ses ponts vivent dans des packages du moteur). Ses tests (`src/test/java`) sont ceux du kit et ceux qui demandent le moteur entier (le kit dépend de la bibliothèque : les tests de `mightylib` ne peuvent pas l'utiliser).
- **`demo/`** (artifactId `mightylib-demo`) : la démo, une application de la bibliothèque comme un jeu le serait. Dépend de `mightylib`, reçoit de `game-parent` le kit de test (portée `test`), les natives LWJGL (`runtime`), le jar exécutable (`jar-with-dependencies`) et `exec`, et fixe `mightylib.mainClass` et les arguments d'`exec` (`-f false`).
- **Modules Java** : chaque module a son `module-info.java` (`io.github.mightycode.mightylib`, `io.github.mightycode.mightylibdemo` ; voir « API publique ») ; le build compile en `--release 11`. Les tests se compilent et s'exécutent sur le **classpath** (`useModulePath=false` pour `testCompile` et Surefire) : accès package-private conservé, et les ponts du kit de test (`KitEngineAccess`, `KitTimeAccess`) partagent les packages du moteur (paquet coupé, refusé sur le chemin de modules).
- Sources en `src/main/java`, tests en `src/test/java` dans chaque module (mêmes packages que le code testé). Les fichiers des tests de la bibliothèque sont dans `mightylib/src/test/resources` et se lisent par le classpath (`TestFiles.path("sounds/selectogg.ogg")`), indépendamment du dossier de travail ; un fichier absent exprès (`missing.ogg`) se résout dans ce dossier.
- Le dossier de travail de Surefire est celui du module (les tests de la démo lisent leurs sources depuis `src/main/java`) ; le jeu se lance depuis la **racine**, où il lit `resources/`.
- `mvn package` depuis la racine compile et teste la démo contre le jar de la bibliothèque (`mightylib/target/mightylib-1.1-SNAPSHOT.jar`), pas contre ses classes : c'est la vérification que la bibliothèque se suffit (`compile` seul résout `mightylib/target/classes`). Dans le réacteur, le jar du kit n'existe qu'une fois `mightylib-test` empaqueté : `compile` et `test` résolvent ses classes, `package` son jar. Avec `-pl <module>` seul, Maven prend les autres modules dans le dépôt local (un `install` ancien serait périmé) : ajouter `-am`.

## Démarrage
`Main` remplit un `EngineConfig` (setters enchaînables, seule la scène de départ est obligatoire ; `addPlugin` pour le contenu du jeu) → `MainLoop.run(config)` crée l'`Engine`, l'installe comme vue courante et appelle `Engine.setup`, en deux parties. **Cœur sans GL** (`setupCore`) : capture de la sortie (`LogCapture`, si console ou mode debug) → **enregistrement des plugins** (`EngineRegistry.Collect` : `EnginePlugin` puis les plugins dans l'ordre d'`addPlugin`, registre gelé ; une erreur arrête avant toute fenêtre, code `ListError.PLUGIN_REGISTRATION_FAIL`, et ferme les sources déjà déclarées) → **pile des sources de ressources** (`Registrations.resourceSources` : voir « Ressources CPU », Sources ; donnée au `ContextManager` pour les mappings de manettes ; une source déclarée deux fois arrête avec le même code et ferme toutes les sources) → `GameTime.setFixedDeltaTime` → `Resources` (loaders du registre, liste figée ; la pile ; pas encore chargées) → `Commands` (commandes des plugins, chacune à son plugin, puis gelées) → **services** (voir **Services** ; dont `mightylib:shaders`, qui lit `shaders/shaders.json` dans la pile, avant le chargement des ressources ; un échec sans repli arrête, code `ListError.SERVICE_FAIL`) → `resources.setSoundBuffers(son)`. **Partie fenêtre** (`setupWindow`) : GLFW → contexte `"Main"` (fenêtre principale, liaisons par défaut du registre) → `GLResources`, puits des éléments GL de `Resources` → gestionnaire de scènes du contexte principal (fabrique du registre) → `resources.init()` + `load()` (bloquant) → crochets `onStarted` → première scène → entrée standard et serveur de debug (mode debug) → icône. `Engine.setupHeadless(puits)` (kit de test, plus tard un serveur dédié) fait le cœur seul puis le chargement, les éléments GL allant au puits donné : ni scène (`sceneManager()` nul, `scenes()` disponible ; `EngineConfig` n'exige alors aucune scène de départ), ni console (elle s'affiche dans la fenêtre principale), ni entrées (`KeyboardManager` et `MouseManager` posent leurs callbacks GLFW sur une fenêtre), ni serveur de debug ; les commandes s'exécutent pour le moteur (pas de choix de vue). `shutdown` ne libère que ce qui a été créé. `MainLoop.run` fait ensuite la boucle, puis `Engine.shutdown` libère tout.

La démo se lance sur le classpath (`-cp`, jar `jar-with-dependencies`) ou comme module (`--module-path … --add-modules ALL-MODULE-PATH --module io.github.mightycode.mightylibdemo/…Main`, `scenario.py --modulepath`) : les natives LWJGL sont des modules (`org.lwjgl.natives`, `org.lwjgl.glfw.natives`…) que rien ne requiert, `ALL-MODULE-PATH` (ou un `--add-modules` de chacun) les résout.

## Boucle (`MainLoop.run`)
Pas fixe découplé : chaque itération fait **soit** un tick (`MainLoop.tick(engine)`, appelé aussi par le kit de test (`Engine.update` : `update` des services (la console), `update` de chaque contexte et de ses sous-fenêtres, `lateUpdate` des services (le son), entrées de toutes les fenêtres, puis `postUpdate`), **soit** une frame (`MainLoop.frame(engine, échéance)`, appelée aussi par le kit ; sans fenêtre, ni affichage ni GL ni échange : `Engine.displayWindows` : chaque fenêtre est activée (`makeCurrent`) et affiche sa vue, puis `Engine.swapWindows` : `swapBuffers` de chacune, un seul `glfwPollEvents`, fermetures). Ticks en retard abandonnés, sans rattrapage (sous charge le jeu ralentit, le temps de jeu dérive du temps réel). Après les affichages, la frame (contexte GL de la fenêtre principale) traite dans l'ordre `Resources.processUntil`, `MainThread.process` et `GLResources.process` avec le reste de la frame (budget : voir « Ressources CPU »). Arrêt : fenêtre qui `closesEngine` fermée (la principale du contexte principal par défaut) ou `sceneManager().exit(status)` du contexte principal (fin du tick). `run` libère tout et **renvoie** le code (`ListError`) sans `System.exit` (`Main` fait `System.exit(MainLoop.run(config))`).

## Temps
`GameTime.DeltaTime()` : temps réel entre deux ticks (variable). `FixedDeltaTime()` : 1/TPS, **pour la physique**. Le temps est lu par une horloge (`LongSupplier` de nanosecondes, `System::nanoTime` par défaut) que seuls les tests changent, par des accès package-private : `setClock` (le temps repart de l'horloge donnée), `setDeltaTime`, `reset`. Tests de la bibliothèque : `GameTimeControl` fixe la durée de la frame lue par `Timer` et les tweenings ; kit de test : horloge manuelle (`KitTimeAccess`).

## Kit de test (`mightylib-test`)
Un jeu teste son code (loaders, commandes, services, scènes) avec JUnit sans lancer le jeu : package `io.github.mightycode.mightylib.test`, `@API(status = EXPERIMENTAL)`, classpath seulement, jamais dans le jar de production (`game-parent` le donne en portée `test`).
- **`MightyTest.headless(config)`** → `TestEngine` : `Engine.setupHeadless` sur la configuration du jeu (mêmes plugins), éléments GL seulement enregistrés (`glElementRequests`) ; les commandes qui lisent une fenêtre, sa scène, ses entrées ou GL (`gl`, `windows`, `window`, `screenshot`, `scene`, `camera`, `monitors`, `input`) répondent « No window » (`CommandCondition.window()`), `stats` compte zéro objet GL, `services` ne décrit aucun gestionnaire. **`MightyTest.withWindow(config)`** : le démarrage complet, fenêtres créées cachées (`Window.setHiddenWindows`), affichage forcé en fenêtre sans vsync (jamais le plein écran du jeu), scène de départ remplacée par `EmptyTestScene` ; sans écran ou sans contexte OpenGL 3.3 core, `start` lève `GLUnavailableException`.
- **`TestEngine`** : `addSource(dossier)` avant `start` (un plugin du kit, enregistré en dernier, empile le dossier au-dessus des sources du jeu), `start`, `step()`/`step(n)` (le temps avance d'un tick, puis `MainLoop.tick` et `MainLoop.frame` sans attente), `frames(n)` (frames seules), `advance(secondes)`, `execute(commande)`, `loadUntilDone([délai])` (ressources, tâches du thread principal, scènes et éléments GL urgents), `resources()`, `engine()`, `close()`. Forcé par le kit : son muet, ni entrée standard ni serveur de debug, **périphériques réels ignorés** (clavier, souris, molette et manettes de la machine : seules les entrées simulées comptent, `RealDevices` par le pont `inputs/KitInputAccess`, remis à la fermeture), ressources strictes quel que soit le mode (`allowResourceFailures()` pour tester un échec). Le kit modifie la configuration donnée : une par moteur (une seconde utilisation est refusée avec un message clair). Un seul moteur de test à la fois par JVM ; `close` (sûr même après une erreur) libère tout et remet l'état statique à zéro (`MainThread`, `Workers`, `Views`, horloge, `LogCapture`, mode, vérification GL, `TextureUploader`, fenêtres cachées). **Dossier du joueur** : si la configuration garde `EngineConfig.DEFAULT_PLAYER_DATA_FOLDER`, `start` crée un dossier temporaire (`mightylib-player-…`, dossier temporaire du système) qui reçoit ce que `ConfigData.set`/`remove` écrivent, supprimé par `close` après l'arrêt des workers (un échec écrit une ligne `--`) ; un dossier donné par `setPlayerDataFolder` (un `@TempDir` à relire après écriture) est utilisé et gardé ; `playerDataFolder()` le rend (aussi après `close`).
- **`SceneRunner`** (`TestEngine.scenes()`) : `start(nom | fournisseur, args)`, `untilLoaded()`, `toEmptyScene()`, `frames(n)`, entrées de la fenêtre principale par les mêmes appels que la commande `input` (`press`/`hold`/`release` d'une action typée ou nommée, `key`, `keyHold`/`keyRelease`, `text`, `mouse`, `click`, `scroll`), `execute`. Fuites : `leakSnapshot()` (compteurs de `gl` sans `#id`, ressources référencées par type, `sounds` `owned`) et `assertNoLeak(avant)` (échec qui nomme chaque compteur changé).
- **JUnit 5** (les tests d'un même moteur `@MightySceneTest` partagent son dossier du joueur : un test qui change une configuration la remet) : `@MightyEngineTest(config = …)` donne un `TestEngine` sans GL démarré par test, fermé après. `@MightySceneTest(config = …)` (méta-annoté `@Tag("gl")`) donne un `SceneRunner` (et son `TestEngine`) d'un moteur avec fenêtre gardé entre les tests de la même configuration (fermé en fin d'exécution, ou dès qu'un autre moteur de test démarre : un test ne suppose donc pas qu'aucun moteur ne tourne à son début, l'ordre des classes dépendant du système de fichiers, alphabétique sous Windows, pas sous Linux comme sur la CI) ; avant chaque test, scène vide et instantané ; après, scène vide et comparaison. Sans GL, le test est ignoré avec la raison, ou échoue avec `-Dmightylib.test.requireGL=true` (la CI). `-DexcludedGroups=gl` écarte les tests GL, `-Dgroups=gl` ne lance qu'eux.
- Exemples : `demo/src/test/java` (`DemoTestConfig`, `DemoHeadlessTest`, `Scene2DTest`, `LayeredTextureLoaderTest`).

## Threads
- **Principal** (`MainThread`) : seul à avoir le contexte GL. Y revenir par `MainThread.execute`/`run`/`supply` (→ `CompletableFuture`, la tâche garde la vue courante de celui qui la poste) ou `thenAcceptAsync(…, MainThread.EXECUTOR)`. File vidée après chaque `display()` dans le reste de la frame (au moins une tâche), après `Resources.processUntil` et avant `GLResources.process`, puis entièrement à la sortie.
- **`Workers`** : pool de `EngineConfig.maxThreads` (`MightyLibrary-Worker-N`, daemon) pour I/O et calcul courts (`Workers.run`/`supply`), **sans GL**. Les étapes `THREAD_CONTEXT` de `Resources` y tournent.
- Boucles longues/bloquantes (réseau, `DebugServer` et ses clients, suivi du journal par un client (`DebugFollow`), entrée standard, encodage de `Screenshot`) : threads dédiés `MightyLibrary-…`, daemon.
- Avec `Logger.isGLErrorCheck()` (drapeau `volatile`, lisible de tout thread), `GenDeleteResources` lève une exception si un objet GL est créé/détruit hors du thread principal.

## Moteur et vue courante
- **`Engine`** (`main/`) : les services partagés, une instance par processus (GLFW et le périphérique son l'imposent), créée et pilotée par `MainLoop` : `resources()`, `glResources()`, `contexts()` (fenêtres et entrées), `sceneManager()` (`ISceneManager` du contexte principal), `config()` ; les services : `service(clé)` (clé absente → `IllegalArgumentException`), `hasService(clé)`, `services()` (créés, dans l'ordre), raccourcis `shaders()`, `sound()` et `console()` (`null` sans accès aux commandes). Plus aucun singleton : `Resources`, `GLResources`, `ContextManager` et les services s'obtiennent par lui.
- **Vue** (`IView` : `engine()`, `context()`, `camera2D()`, `camera3D()`) : ce pour quoi le code s'exécute. `Scene` est une vue (caméras créées au `launch`) ; l'`Engine` l'est aussi hors de toute scène (démarrage, commandes, chargement), sans caméra.
- **Vue courante** (`Views.current()`, `Views.engine()`) : posée par le moteur autour de tout le code d'une vue (`Scene.initByManager`/`launchByManager`/`updateByManager`/`postUpdateByManager`/`displayByManager`/`unloadByManager`, `MainLoop.run`) par `try (Views.Scope s = Views.enter(vue))`. `MainThread.execute` la capture à la soumission et la rétablit à l'exécution. Sans vue courante (worker, avant `run`) : `IllegalStateException` explicite, jamais de repli sur une autre fenêtre.
- Ce qui est créé sans paramètre explicite appartient à la vue courante : `Renderer` (`resources`, `glResources`, caméras par défaut), `Text`, `Animation`, `Texture(String)`, `GUI()`, `ScrollList`, `Scene` (engine et contexte du créateur). Les objets déjà liés à un propriétaire le rendent : `DataType.resources()`, `ResourceLoader.resources()`, `GLElement.glResources()` ; une donnée construite par le code avant d'être ajoutée utilise `resourcesOrCurrent()`.
- Commandes : exécutées sur le thread principal sous la vue de leur propriétaire (l'`Engine` pour celles du moteur et du jeu), elles prennent leurs services par `Views.engine()` (voir **Commandes**).
- Gardés statiques, par nature de processus : `MainThread`, `Workers`, `GameTime`, `Logger.isGLErrorCheck()`, `MainLoop.getMode()`, `EngineStats`, `GenDeleteResources`, `Screenshot`, `TextureUploader`.

## Plugins et registre
- **Point d'injection unique** : `IPlugin` (`namespace()`, `register(EngineRegistry)`), ajouté par `EngineConfig.addPlugin`. Une seule phase, au début d'`Engine.setup` (avant GLFW) : `EnginePlugin` (package-private, espace `mightylib` : loaders obligatoires dont celui des shaders, commandes générales, touches de la console, services du son et de la console, fabriques des gestionnaires de scènes et d'entrées) puis les plugins dans l'ordre d'ajout ; le registre est ensuite gelé (tout appel → `IllegalStateException`) et l'`Engine` lit le résultat, `Registrations` (`engine.registrations()`). Collecteur de données pur, sans GL ni `Engine` (`EngineRegistryTest`).
- **Sections** : `resources()` (loaders, clé = type de donnée, sans espace ; un plugin peut remplacer un loader obligatoire, shaders compris ; sources de fichiers : `source(IResourceSource)`, `classpath()` = `assets/<espace du plugin>/` lu avec le chargeur de classes du plugin, `folder(chemin)`, dans l'ordre des appels, `registrations.sources(plugin)`), `commands()`, `inputs()` (actions et axes, liaisons par défaut), `scenes()` (identifiant, classe, fabrique, description → `SceneRegistry`, `engine.scenes()`), `services()` (voir **Services**), `lifecycle()` (crochets). `registry.id(chemin)` donne un identifiant de l'espace du plugin.
- **Règles** : un plugin par espace (`mightylib` réservé) ; un plugin n'enregistre que des identifiants de son espace (sinon `IllegalArgumentException`) ; un identifiant (ou un type de loader) déjà pris → `IllegalStateException` nommant les deux plugins ; `replace(...)` remplace l'entrée d'un plugin précédent, de tout espace et du moteur (une ligne `--… replaced by …`), une entrée absente → erreur. Le remplaçant possède l'entrée (commande : son propriétaire).
- **Scènes** : enregistrement facultatif (le code crée toujours la scène qu'il veut) ; la commande `scene` et les menus lisent le `SceneRegistry` ; aucune réflexion dans la bibliothèque. `scene` sans argument donne l'identifiant de la scène courante si sa classe est enregistrée (premier identifiant de la classe), sinon sa classe. `EngineConfig.setStartScene`/`setLoadingScene` restent au jeu.
- **Crochets** (`LifecycleHooks`, `registrations.lifecycle()`, `engine.lifecycle()`) : `onStarted` (après `resources.load()`, avant la première scène), `onSceneChanged(contexte, ancienne ou null, nouvelle)` (dans chaque contexte, une fois la nouvelle scène chargée, première frame complète : détecté par `SceneManager.display` ; l'ancienne = la dernière scène chargée de ce contexte, déjà déchargée), `onShutdown` (début d'`Engine.shutdown`, avant toute libération), `onWindowOpened`/`onWindowClosed` (fenêtre principale de chaque contexte et fenêtres des vues ; fermeture avant destruction). Thread principal, ordre des plugins ; un crochet qui lance une exception est rapporté (`Logger.LogException`) et les suivants sont appelés, relancée en mode strict (`EngineConfig.setStrictResources`) ; sauf pour `onShutdown` et `onWindowClosed`, jamais relancés pour que tout soit libéré : en mode strict, leur échec donne le code de sortie `ListError.LIFECYCLE_HOOK_FAIL`.

## Services
- **Service** (`services/`) : système unique du moteur, choisi une fois au démarrage, jamais pendant le jeu. Un contrat (`IEngineService` et son interface : `IShaderService`, `ISoundService`, `IConsoleService`) désigné par une clé typée `ServiceKey<T>` (`Identifier` + contrat, égalité par identifiant) ; `engine.service(clé)` le rend sans cast. Clés du moteur (`EngineServices`) : `SHADERS` (`mightylib:shaders`, toujours, sans repli : `ShaderService`, voir « Shader »), `SOUND` (`mightylib:sound`, toujours : OpenAL, repli muet), `CONSOLE` (`mightylib:console`, seulement si le joueur a accès aux commandes : un plugin qui s'en sert déclare `after(CONSOLE)` et teste `hasService`).
- **Enregistrement** (`registry.services()`) : `register(clé, fabrique)` (clé de l'espace du plugin) ou `replace(clé, fabrique)` (tout espace, même contrat, sinon `IllegalArgumentException`) rendent la déclaration (`ServiceDeclaration`) où chaîner `requires(clés)` (obligatoire : absente → erreur à l'enregistrement ; échouée → service non créé), `after(clés)` (ordre seulement, si présente) et `fallback(fabrique)`. Le remplaçant déclare ses propres dépendances et son repli. `IServiceFactory.create(engine)` lit les services dont il dépend par `engine.service`. Démo : `demo:tick_counter` (`DemoPlugin`, `TickCounterService`), montré par `EngineServices2D`.
- **Ordre** (`ServiceOrder`, au gel du registre, code `PLUGIN_REGISTRATION_FAIL`) : tri topologique stable sur `requires` et les `after` présents (ex aequo : ordre d'enregistrement, moteur d'abord ; un remplacé garde sa place) ; un cycle est une erreur qui le liste (`ServiceOrderTest`). `registrations.services()` = la liste triée.
- **Création** (`ServiceSet`, dans `Engine.setup` après `Resources`, `GLResources`, `Commands`, avant les gestionnaires de scènes) : dans l'ordre ; une fabrique qui lance une exception ou une `LinkageError` (bibliothèque native absente) ou rend `null` → son repli (une ligne `--Service … fallback to …`) ; sans repli, les services qui la requièrent ne sont pas créés, les autres si, et le moteur s'arrête (`ListError.SERVICE_FAIL`) après avoir libéré ceux créés. `ServiceSet.override` remplace la fabrique d'une clé quel que soit son plugin (`-Dmightylib.sound=silent`).
- **Phases** (`default` vides, thread principal) : `update` (avant les contextes) et `lateUpdate` (après eux, avant leur `postUpdate`) dans l'ordre de création ; `displayOverlay` après les vues, sur la fenêtre principale liée (`Engine.displayOverlays`, appelé par `Context`), par couche (`overlayLayer()`, console 1000 au-dessus de tout) puis ordre de création ; à l'arrêt, `unload` après `contexts.unloadViews()`, fenêtre principale liée, avant `resources.unload()` (sources, GL de la console), et `terminate` après `glfwTerminate` (périphérique son ; pas `close`, nom laissé aux services : la console ferme son overlay), tous deux en ordre inverse, l'échec d'un service n'empêchant pas les autres (`ServiceSetTest`).
- **Gestionnaires par contexte et par fenêtre** : fabriques remplaçables dans la même section, `sceneManager(ISceneManagerFactory)` et `inputManager(IInputManagerFactory)` (le moteur donne `SceneManager::new` et `InputManager::new`, le dernier plugin gagne, une ligne `--… replaced by …`), pilotées comme avant par `Context`/`ContextManager`.
- **Commande** `services` (`DEV`) : ordre, clé, contrat, implémentation, plugin, plugin remplacé, `requires`/`after`, repli utilisé, couche d'overlay, et les gestionnaires de scènes et d'entrées.

## Contextes et fenêtres
- **`Context`** = une scène (son `ISceneManager`, ses changements de scène, son écran de chargement) et les fenêtres qui la montrent ; **`WindowContext`** = une fenêtre avec son `GLContext`, ses entrées (`IInputManager`, `KeyboardManager`, `MouseManager`) et son presse-papiers. Un `Engine` a un contexte principal (`EngineConfig` : fermer sa fenêtre principale arrête le moteur) et autant d'autres que voulu (`Engine.openContext(nom, WindowConfig, Supplier<Scene>)` : la scène est créée avec le contexte pour vue ; fermer sa fenêtre principale, ou son `exit`, ne ferme que lui, et décharge les batchs de sa scène). Les ressources sont communes à tous.
- **Fenêtre principale et registres avant le démarrage** : `ContextManager.getMainWindow()` vaut `null` tant que le moteur n'a pas ouvert sa fenêtre ; le code qui ne tourne qu'après le démarrage (services, boucle, scènes) prend `requireMainWindow()`, qui lève une `IllegalStateException` explicite au lieu d'un `null`. De même `Engine.scenes()` refuse d'être lu avant le démarrage.
- **Affichage** : `DisplaySettings` = le mode (`EWindowMode` : `WINDOWED`, `FULLSCREEN` exclusif, `BORDERLESS` = fenêtre sans bordure couvrant son écran à sa résolution) et les réglages fins de chaque mode, chacun avec sa valeur par défaut et ignoré hors de son mode (donc aucun ordre d'appel, et changer de mode n'en perd aucun) : écran (tous ; non donné : celui du parent, sinon celui de la fenêtre principale, elle-même sur l'écran de `EngineConfig.setMonitorSelector`), taille fenêtrée (1280x720), bordure, redimensionnable (fenêtré), résolution (celle de l'écran), fréquence (celle de l'écran) et réduction à la perte du focus (plein écran) et vsync (tous les modes, désactivé par défaut : intervalle d'échange du contexte GL de la fenêtre, commande `window vsync <true|false> [fenêtre]`). Raccourcis : `setWindowMode`, `setSize`/`setWindowSize` (taille fenêtrée), `setMonitor` sur `WindowConfig`/`EngineConfig`. Configs et fenêtres gardent leur copie. En cours de jeu : `WindowContext.setDisplay(...)`/`setWindowMode(...)`, appliqués aussitôt par `glfwSetWindowMonitor` et les attributs GLFW (la fenêtre, son contexte GL et ses callbacks restent ; la taille virtuelle ne change pas) ; une fenêtre réduite est d'abord restaurée, puis placée au frame suivant (le système lui rend sinon son ancien emplacement) ; la position fenêtrée est retenue pour y revenir. Un écran n'a qu'une fenêtre en plein écran exclusif : une deuxième passe en sans bordure (message `--`). `WindowInfo.size` suit la taille réelle (callback de framebuffer, relu à chaque fois) ; pendant la lecture des événements, le callback de rafraîchissement redessine la fenêtre (`Context.redrawWindow` : affichage de sa scène ou vue puis swap), car sous Windows la boucle attend dans `glfwPollEvents` tant qu'un bord est tiré : l'image suit le redimensionnement, les ticks attendent le relâchement ; `getWindowMode()` donne le mode appliqué. `MonitorInfo.getVideoModes()` : résolutions et fréquences de l'écran. Démo : `DisplayModesScene` (1/2/3 modes, B bordure, Z redimensionnable, L résolution 1280x720, W seconde fenêtre ; touches lues dans la fenêtre qui a le focus).
- **Sous-fenêtres** : `Context.openWindow(WindowConfig, WindowView, args…)` (`Scene.openWindow`), depuis le code d'une scène ou d'une vue. `WindowView` = petite scène sans changement de scène ni écran de chargement (`launch`, `update`, `postUpdate`, `display`, `unload`, caméras, surface virtuelle, `close()`) ; ses ressources doivent déjà être chargées (batchs de la scène qui l'ouvre). `WindowConfig` : titre, affichage (`DisplaySettings`, voir **Affichage**), taille virtuelle (non donnée : la taille de la fenêtre à sa création), disposition clavier, parent (défaut : fenêtre principale), `modal`, `persistent`, `closesEngine`, `projectInputs`.
- **Arbre des fenêtres** (`WindowTree`, sans GLFW, testé par `WindowTreeTest`) : fermer une fenêtre ferme d'abord ses enfants ; un parent est **bloqué** tant qu'un descendant modal est ouvert (`InputManager.setBlocked` : plus de touche, de bouton, de molette, de texte, d'action ni d'axe, curseur hors fenêtre ; les manettes ne sont pas concernées) ; une fenêtre appartient à la scène (ou vue) qui l'a ouverte, qui la ferme à son `unload` sauf `persistent`. Fenêtre fermée par l'utilisateur ou par `WindowContext.requestClose()` : traitée à la fin de la frame.
- **Natif** : une sous-fenêtre est centrée sur son parent et, sous Windows, a le parent pour propriétaire (`NativeWindowOwner` : `GLFWNativeWin32` + `User32.SetWindowLongPtr(GWL_HWNDPARENT)` : au-dessus du parent, masquée avec lui, sans entrée dans la barre des tâches) ; ailleurs, simple `GLFW_FLOATING`.
- **Plateforme GLFW** (`WindowPlatform`, journal `--GLFW platform : …`) : GLFW choisit (Wayland dans une session Wayland), `-Dmightylib.glfw.platform=x11|wayland|win32|cocoa|null` l'impose. Sous Wayland le compositeur place les fenêtres : ni position lue ou fixée (pas de centrage, pas de retour à la position fenêtrée, `monitors` ne connaît l'écran que d'une fenêtre en plein écran), ni `GLFW_FLOATING`, ni icône ; le moteur saute ces appels (`CanPlaceWindows`, `CanFloatWindows`, `CanSetWindowIcon`) au lieu de laisser GLFW lever `GLFW_FEATURE_UNAVAILABLE`.
- **Code d'une vue** : le moteur active le contexte GL de la fenêtre de la vue avant d'exécuter son code (`bindWindow` dans les `…ByManager` de `Scene` et `…ByContext` de `WindowView`) et le rend ensuite ; un objet créé dans une fenêtre (renderer, texte) peut être affiché dans une autre (VAO créé à la demande, voir « Contextes GL »), pas un `FrameBuffer`.
- Démo : `MultiWindowScene` (M : dialogue modal, T : fenêtre d'outils qui affiche le renderer de la fenêtre principale, C : second contexte avec `Scene2D`).

## Cycle de vie d'une scène
`init(args)` → (scène de chargement pendant les batchs) → `launch(args)` → `update()`/`postUpdate()`/`display()` → `unload()` → `release()`.
- Exemple commenté : `mightylibdemo/scenes/DocumentationScene` (batch `documentation`, `resources/data/documentationScene.json`, texture créée dans `init`, supprimée dans `release`).
- Paires : `launch` ↔ `unload` (seulement si `launch` a eu lieu, avec `super.unload()`) ; `init` ↔ `release` (toujours, même si quittée pendant le chargement).
- Champs de `Scene` privés : la scène lit son état par `context()`, `resources()`, `glResources()`, `camera2D()`/`camera3D()` (à partir de `launch`), `sceneManager()` et `args()`. Les aides (`setVirtualScene`, `clear`, `setClearColor`, `addUpdatable`…) sont `final`.
- `init`/`launch` facultatifs, **sans `super`** : le moteur (`initByManager`/`launchByManager`) crée la scène de chargement, puis caméras et framebuffer virtuel avant `launch`. `init` déclare (ressources préchargées), `launch` crée les renderers.
- Activation des composants GUI (`GUI`, `GUIList`, `ScrollList`, `TextField` : voir **Rendu**, GUI) : chaque `GUI` a un déclencheur (`setTrigger(EInputState)`, `Pressed` par défaut ou `Released`) et `isActivated(inputManager, actions...)` ; `GUIList.getActivated()` et `ScrollList.getActivated()` renvoient l'élément activé à ce tick après `setupActivationActions(actions...)`. `InputManager.isInput(id, EInputState)` choisit Press, Release, Pressed ou Released par une valeur d'enum. Le menu de la démo : voir **Rendu**.
- Scène de chargement : `EngineConfig.setLoadingScene` (défaut `DefaultLoadingScene`, fond gris) ou `createLoadingScene(args)` (`null` = rien) ; elle reçoit le `sceneManager()` de la scène chargée et peut changer de scène (démo : Échap → menu, la scène en cours de chargement est déchargée). Surface virtuelle : `createVirtualSceneBindable()`.
- Ressources : surcharger `getInvolvedBatch()` (fichiers `batchs/*.batch` des sources). Changement de scène (`SceneManager.changeScene`) : `unload` de l'ancienne scène, `loadBatch` de la nouvelle, puis `unloadBatch` de l'ancienne et annulation du préchargement : ce que les deux partagent (données et éléments GL) n'est jamais libéré entre-temps. `Scene.unload` n'appelle `unload` qu'une fois par objet (ajouté comme updatable et displayable).
- `display()` : `setVirtualScene(); clear(); …; setAndDisplayRealScene();`. Changer de scène : `sceneManager().setNewScene(new XScene(), args)`. `postUpdate()` remet à zéro les états pressed/released.

## Ressources CPU (`Resources`)
- Type = `DataType` + `ResourceLoader`. Les loaders sont donnés à la construction de `Resources` : ceux du registre (`registry.resources()` : les obligatoires du moteur — shaders, icônes, textures, animations, polices, JSON, batchs, `LibraryLoaders.mandatory(fournisseur du service des shaders)` ; le `ShaderLoader` lit le service `mightylib:shaders`, créé après l'enregistrement, quand il travaille — puis ceux des plugins ; facultatifs de la bibliothèque : `LibraryLoaders.all()` ou un par un, démo : `DemoPlugin`), dans cet ordre ; la liste ne change plus ensuite (lue par `loaders()`, package-private), un loader par type de donnée (doublon → `IllegalArgumentException`). Les fichiers sont lus dans la **pile des sources** (`resources.sources()`, voir Sources), `final` et donnée au constructeur, donc lisible par les workers et l'observateur sans synchronisation ; les loaders la lisent par `resources()`, le service des shaders y lit `shaders.json`, le service de son y lit l'arbre des gains (`EngineConfig.setGainTreePath`, chemin logique). Deux `Resources` sur deux piles ne se voient pas (`ResourcesSourcesTest`). Accès : `resources.getResource(TextureData.class, "nom")` (`resources` : champ de `Scene`, `Views.engine().resources()` ailleurs) ; un type sans loader → `IllegalStateException` nommant le loader à enregistrer. Nom = fichier sans extension → **unique par type**.
- **Sources** (`resources/source`, `EXPERIMENTAL`) : `IResourceSource` = une racine de fichiers (`name`, `exists`, `isFolder`, `open`, `size`, `list` des enfants directs, `localFile` : le fichier disque d'un chemin, existant ou non, vide pour un jar ; sans état modifiable, lue par tout thread ; `close` à l'arrêt) ; `FolderSource` (dossier, absent = vide), `ClasspathSource(chargeur, préfixe)` (dossier du classpath, ou jar ouvert en système de fichiers zip, réutilisé s'il est déjà ouvert, fermé par celle qui l'a ouvert ; préfixe absent = vide ; préfixe **unique**, tenu par un seul jar, qui doit contenir les entrées de ses dossiers). `ResourceSources` = la pile **immuable**, de la plus basse à la plus haute : source classpath du moteur (`assets/mightylib/`, déclarée par `EnginePlugin` ; `-Dmightylib.resources.engine=<dossier>` ou `EngineConfig.setEngineResourcesFolder` la remplace par un dossier) < dossier du jeu (`EngineConfig.setResourcesFolder`, `"resources/"` par défaut, propriétaire `GAME_OWNER`) < sources des plugins dans l'ordre d'`addPlugin` puis des appels ; fermée par `Engine.shutdown` après les ressources. `resolve` (la plus haute qui a le chemin, fichier ou dossier), `open`/`readString`/`readBytes`/`readNative` (buffer natif à libérer par l'appelant : STB, OpenAL), `size` et `localFile` lisent la plus haute qui l'a **en fichier** (un dossier plus haut au même chemin ne le cache pas), `list` (union, la plus haute gagne pour un même nom), `layers` (toutes celles qui l'ont, de bas en haut), `localCandidates` (fichier disque du chemin dans chaque source sur disque), `owner`. Tests : `FolderSourceTest`, `ClasspathSourceTest` (dossier du classpath et jar écrit par le test), `ResourceSourcesTest`.
- **Source du moteur** (`mightylib/src/main/resources/assets/mightylib/`, dans le jar) : les shaders que la bibliothèque nomme et les shaders de base (`shaders/` : `shaders.json` et fichiers GLSL, dont `utils/colorsManipulation.glsl`), les atlas des polices `engineSans` (interface) et `engineMono` (console) et leurs variantes Bold, Italic, BoldItalic (`textures/fonts/` : `fonts.json`, `.fnt`, `_0.png`, licence `OFL.txt` ; `textures/textures.json`), le batch `batchs/mightylib.batch` et `gamecontrollerdb.txt` (mappings de manettes). Les noms sont les constantes d'`EngineResources` (`resources`, `final`), seul endroit où la bibliothèque les écrit ; pas d'espace de noms (les identifiants `mightylib:nom` iront avec le modding). **Le batch du moteur** (`EngineResources.ENGINE_BATCH` = `mightylib`) est chargé par `Resources.load()` avant le premier batch du jeu, avec les deux méthodes de chargement, et n'est jamais déchargé ; il liste les shaders du moteur et les deux polices Regular (les 6 autres sont déclarées mais chargées par le jeu qui les veut : environ 4 Mo de carte chacune). Batch absent (source du moteur remplacée par un dossier incomplet) : une ligne d'erreur et le jeu se charge sans, exception en mode strict. **Remplacer une ressource du moteur** : un jeu ou un plugin déclare le même nom (entrée de `shaders.json`, `fonts.json`, `textures.json`, fusion par entrée) ou met un fichier au même chemin dans une source plus haute ; un batch `mightylib` d'une source plus haute ajoute ses entrées à celui du moteur (listes réunies). Les atlas sont des versions modifiées des polices Liberation 2.1.4 (SIL OFL 1.1 : un changement de format en est une), donc sans le nom réservé « Liberation » : les `.ttf`, leur licence, les `.bmfc` et `generate.py` qui les régénère (BMFont ; chasse fixe de la console corrigée) sont dans `mightylib/fonts/`, hors du jar. Tests : `EngineResourcesTest` (contenu de la source du moteur), `ResourcesEngineBatchTest` (chargement du batch), `EngineSourcesTest`.
- **Chemins logiques** : relatifs, `/`, sans `.` ni `..` ni partie absolue (`ResourceSources.normalize` : un chemin absolu ou avec `..` → `IllegalArgumentException`, une source ne sort jamais de sa racine ; écrit dans une description → `ResourceException`). `path()`/`sourcePaths()` des données en sont ; résolus à chaque lecture (un fichier ajouté plus haut est pris à la lecture suivante). `FileMethods.readString`/`readJSONObject(sources, chemin)` lisent dans la pile (lignes finies par `\n`, `ResourceException` si absent ou illisible). **Exploration** (`ResourceLoader.exploreResourcesFile(data, dossier logique)`, `""` = racine) : `list` de la pile, un chemin présent dans plusieurs sources donné une fois ; même nom, chemins différents, dans deux sources → celle de la plus haute gagne, une ligne `--<Type> <nom>: <chemin> (<source>) overrides …`, exception en mode strict ; décidé avant `fileDetected` : le loader ne reçoit jamais le fichier qui perd ; dans une même source, le loader décide (le dernier détecté en général). Cubemaps et calques de la démo listent leurs dossiers dans toutes les sources (une face absente plus haut est lue plus bas). Modèles : Assimp lit le fichier disque de la source (`localFile`) ; un modèle dans un jar → `ResourceException` ; textures du `.mtl` en chemins logiques (dossier du modèle). Mappings de manettes : `gamecontrollerdb.txt` à la racine de la pile, facultatif, la plus haute gagne (`ContextManager.ReadMappings`, `GamepadManager.addMappings`). Configurations réseau : `networkConfigs/` de la pile.
- **Listes fusionnées par entrée** (de bas en haut, chaque couche lue dans sa propre source : `FileMethods.readJSONObjectLayers`) : `textures/textures.json` (une couche après l'autre, une texture de même nom remplacée en entier, même dans un autre dossier de la liste), `textures/fonts/fonts.json` et `shaders/shaders.json` (`FileMethods.mergeEntries` : entrée de même nom remplacée en entier, autres clés de la plus haute), batchs (même description dans plusieurs sources : listes `files` et `regex` réunies sans doublon, par type et drapeau `gpu` ; `BatchLoader.Merge`). Une source plus haute ajoute ou remplace, ne retire pas. Le batch est relu entier quand une couche change. Tests : `ListMergeTest`, `ResourceLoaderExploreTest`, `CubeMapLoaderTest`, `ShaderPreprocessorTest` (include remplacé plus haut).
- États : créé → **preload** (`initWithFile` : lecture des sources, dépendances) → **load** (`internLoad`, dépendances chargées) → unload (`internUnload`, ou `internCancelPreload`).
- `TYPE_SET_UP` : `THREAD_CONTEXT` (workers, ≤ `maxThreads`), `MAIN_CONTEXT` (thread principal, dans le budget de la frame), `IMMEDIATELY_IN_CURRENT_CONTEXT` (dans l'appel, ex. descriptions de batchs). Unload toujours sur le thread principal. Une étape en file est vérifiée **au moment de démarrer** (`stepStillNeeded`) : donnée plus voulue (scène quittée, copie abandonnée) ou à relire → sautée (`skippedSteps` dans `resources`), puis `update` la vide ou la relance ; voulue à nouveau entre-temps → étape gardée. Une donnée n'a pas de GL : ce qui va sur la carte est son `GLElement` (voir **Ressources GPU**). Une étape commencée va au bout (ou s'arrête à `checkCancelled()`). Sons : un `SoundDecoder` par format (`resources/sound/decoder` : ogg = STB Vorbis, wav = `javax.sound.sampled`, mp3 = JLayer (LGPL), flac = `FlacStream` écrit pour le moteur ; `SoundLoader.addDecoder` en ajoute, le dernier ajouté gagne pour une extension) ; les noms de ressource sont ceux des fichiers sans extension (deux fichiers de même nom : avertissement). `SoundDataType.readVorbis` décode par morceaux (`DECODE_CHUNK_SAMPLES`) avec `checkCancelled()` entre deux ; le PCM est en mémoire native (`SoundLoadInfo`, construit avec son buffer et son drapeau natif, en lecture seule ensuite), libéré par `SoundLoadInfo.release()` après l'envoi à OpenAL ou par `SoundData.internCancelPreload`.
- **Priorités** : une donnée voulue maintenant (batch chargé, code, dépendance d'une donnée voulue) est *urgente* ; celle qui n'a que des références `preload:` passe après (file à deux niveaux dans `ResourceScheduler`, promue en O(1) quand elle devient urgente ; un worker reste libre pour les urgentes). `finishedCurrentLoading` ne compte que l'urgent : un écran de chargement n'attend pas le préchargement. API : `Resources.preloadBatch`/`cancelPreloadBatch`, `SceneManagerInterface.preloadScene` (scène `PreloadScene`) ; `loadBatch` après un préchargement ne recharge rien.
- **Budget de frame** : `MainLoop` donne une échéance commune à `Resources.processUntil`, `MainThread` et `GLResources` ; sous un écran de chargement le chargement a toute la frame, sinon `EngineConfig.setInGameLoadingShare` (30 % par défaut, pour `Resources` et `GLResources` ; `MainThread` garde toute la frame). Chaque file fait au moins une étape par frame.
- **Poids et progression** : `DataType.estimatedCpuBytes`/`estimatedGpuBytes`, pour le debug seulement (taille décodée une fois lue : pixels des textures, échantillons des sons, tableaux des modèles ; avant lecture, taille des fichiers × un ratio par format : 4 pour les textures, 10 pour OGG/MP3, 2 pour FLAC ; sur la carte, les textures seules), commande `resources batch <nom>`, `Resources.wantedProgress()` ({fait, total} des données voulues maintenant ; l'écran de chargement de la démo affiche « LOADING x / n »).
- **Propriétaire unique** : seul le thread principal change références et états ; les appels d'autres threads (`addOwnedResource` depuis un loader, `addPreLoadedResource` depuis `internLoad`) passent par une file vidée par `process`. Un worker ne fait que lire/calculer. Une donnée ne lit aucun `Resources` global à sa construction : celui qui l'enregistre (création par les loaders, découverte, fallback, `addResourceAndSetUp`, `addPreLoadedResource`, `addOwnedResource`, copie de rechargement) s'y attache (`DataType.attachTo`), une seule fois ; `DataType.resources()` le rend, et échoue (`IllegalStateException`) tant que la donnée n'est pas enregistrée. `Model` ajoute et libère ses textures possédées auprès de ce même `Resources`.
- **Découpage de `Resources`** (façade, cycle d'état `update`/`startStep`/`endStep`/`fail`) : `ResourceScheduler` (files à deux niveaux, workers, échéance), `DependencyGraph` (dépendances, attentes), `ReloadManager` (rechargement à chaud), `BatchManager` (lots), `FallbackRegistry` (données de repli), `ResourceDescriber` (JSON de debug). Tous package-private, thread principal.
- **Réconciliation** (`Resources.update`) : voulue = référencée (sauf suppression/sortie). Une donnée dont une étape tourne n'est jamais modifiée ; à la fin, voulu/état est recomparé.
- **Dépendances** : une donnée voulue et préchargée référence les siennes (`dependency:<Type>:<nom>`, pas à lister dans le batch, gardées tant qu'elle est chargée ; `onlyAsDependency` dans `resources`) ; elle est réveillée quand l'une est chargée.
- **Échec** (`Resources.fail`, exception du loader, `internLoad` → `false`) : retour à l'état initial, dépendances rendues, pas de nouvel essai tant que voulue (sauf `reloadAllOfType`). Ceux qui attendent prennent le placeholder du type, sinon échouent en chaîne. Échec **attendu** (fichier manquant/illisible, format inconnu, contenu mal formé) : le loader lève `ResourceException` (sans pile ; `FileMethods.readString`/`readJSONObject`, `IconLoader`, `FontFile.load` le font) → une ligne ; toute autre exception = bug → pile complète (`Logger.LogException`). Une icône en échec laisse l'icône par défaut.
- **Placeholders** (`ResourceLoader.createFallback`, nommés `error`, générés, chargés au démarrage, jamais déchargés/rechargés ; un placeholder en échec lève une exception) pour les types primaires : texture (damier magenta/noir, + version rectangle), son (bip), shader (magenta, sources générées par `FallbackShaderData`), police (carrés), animation (une image), modèle (cube), cubemap (six damiers). Types complexes (JSON, CSV, tilemaps, tilesets, batchs…) : `null`, plantage accepté. `Resources.usable(type, donnée)` = donnée si chargée, sinon placeholder (échec **ou chargement en cours**) ; `getResourceOrFallback` pour un nom inconnu (signalé une fois). Les utilisateurs (`Texture`, `OpenALSoundSource`, `Renderer`, `Text`, `Animation`, `ModelRenderer`) résolvent à l'usage : une donnée chargée plus tard ou relue avec succès remplace le placeholder. Placeholder signalé une fois, à l'échec ; `resources` liste `usingFallback`.
- **Élément GL d'un placeholder** : déclaré par sa donnée comme pour toute donnée (`glElementType`/`createGLElement`) ; `Resources` donne à la fin du premier chargement les replis par type de loader (`IGLElementSink.fallbackDataLoaded`), `GLResources` crée leurs éléments, les range **par type de donnée**, hors de la table par nom (deux replis d'un même type d'élément, tous nommés `error`, ne se gênent pas), et les référence tout le programme. Envoyé aux frames suivantes, ou chargé pendant l'appel quand la donnée le déclare (`DataType.glElementNeededBeforeDrawing()`, vrai pour `FallbackShaderData` seulement : un échec arrête alors le programme, rien ne pourrait le remplacer) ; un repli différé qui échoue est un élément en échec, ses utilisateurs gardent le placeholder GL. `GLResources.fallback(type de donnée)` rend l'élément du type ou de son plus proche parent avec repli (même règle que `getFallback`) ; `acquire` d'une donnée de repli rend cet élément. Un type ajouté par un projet a ainsi son propre élément de repli sans toucher à `GLResources` (démo : `LayeredTextureData`, rayures bleues, au lieu du damier). Les renderers prennent une texture par son nom avec `Renderer.acquireTexture` (sa `TextureData` ou le repli, puis `acquire`) : tous les noms inconnus partagent l'élément de repli des textures.
- **Configurations en couches** (`resources/config`, `ConfigData`, loader obligatoire `ConfigDataLoader`) : chaque `configs/<nom>.json` d'une source est une couche ; le nom est le chemin sous `configs/` sans extension (`mightylib/display`). Les couches des sources sont fusionnées en profondeur (objets fusionnés, autre valeur remplace, la plus haute source gagne), puis la **couche du joueur** : `EngineConfig.setPlayerDataFolder` (`EngineConfig.DEFAULT_PLAYER_DATA_FOLDER` = `data/` par défaut, dossier temporaire dans un moteur de test du kit) exposé par une `FilteredSource` (`configs/` seulement) au sommet de la pile (propriétaire `ResourceSources.PLAYER_OWNER`, `kind: player` dans `resources sources`), donc listé et observé comme les autres sources ; `configs/` est ignoré par `exploreResourcesFile`. Lecture typée avec défaut (`getFloat/getInt/getBoolean/getString("a.b", défaut)`, copies `values()`/`playerValues()`/`defaultValues()`) ; `set`/`remove` changent la couche du joueur à l'instant et l'écrivent sur un worker (`Workers`, fichier temporaire puis renommage, seule la dernière version est écrite, la future rendue complète à la fin). Une couche illisible est ignorée avec une ligne (`invalidLayers`, `resources ConfigData`) et les autres gardent leurs valeurs ; une couche du joueur illisible n'est jamais réécrite. Un fichier modifié recharge la donnée (`getVersion`). Config du moteur `configs/mightylib/display.json` (batch `mightylib`). Tests : `ConfigDataLayersTest`, `ConfigMergeTest`, `FilteredSourceTest`.
- **Données multi-fichiers** (`MultiSourceDataType`) : chemins fixes (liste immuable) ; lecture sautée sans chemin ou avec un chemin vide (donnée générée, `hasSource()` faux) ; état par fichier remis à zéro par `ResourceLoader.read` avant chaque lecture, marqué par le loader (`markSourceRead`) ; une lecture qui laisse des fichiers non lus échoue en les nommant (`not read: …`) ; `resources <Type> <nom>` montre `sourceFiles` (chemin, source qui le sert, `read`). Un fichier modifié relit toute la donnée. Utilisateurs : `CubeMapData`, `LayeredTextureData` (démo). Tests : `MultiSourceDataTest`.
- **Mode strict** (`EngineConfig.setStrictResources`, `-Dmightylib.resources.strict=true`, `scenario.py --strict`, debug seulement) : échec ou nom inconnu → exception.
- Références par nom (batch, `preload:<batch>` pour un préchargement, `"manually"`, `"all"` pour `loadAllOfType`, `dependency:<Type>:<nom>`, propriétaire) ; liste, doublons permis.
- **Rechargement à chaud** (`Resources.reload(donnée)`, `reloadAllOfType`, commande `reload`) :
  - donnée **chargée** jamais vidée : `DataType.createReloadCopy` → copie lue à part (`reloading` dans `resources`), puis `swapContent` (identité et références gardées), la copie décharge l'ancien contenu. **Échec = version précédente gardée** (exception en strict) ; la donnée reçoit la copie échouée (`DataType.reloadFailed`, vide par défaut) pour garder ce qu'elle a appris (`ShaderData` : les fichiers à surveiller). Nouveau `reload` pendant la lecture : nouvelle copie lue tout de suite, l'ancienne abandonnée (plus voulue : son étape en cours s'arrête au prochain `checkCancelled()` du loader, sinon va au bout et son résultat est jeté ; si elle attendait ses dépendances, libérée aussitôt) ;
  - **annulation** : `update` pose le drapeau `cancelled` d'une donnée dont l'étape en cours est inutile (plus voulue, relecture demandée) ; le loader l'interroge par `checkCancelled()` (`CancellationException`, silencieuse, comptée dans `skippedSteps`), à placer avant la phase coûteuse ;
  - **copies bornées** (`Resources.setMaxReloadCopies`, 32 par défaut) : au-delà, la donnée reste utilisable avec l'ancien contenu et attend une place (`ReloadManager.mustWait`/`wakeDeferred`) ;
  - `DataType.getVersion()` augmente à chaque changement ; les utilisateurs comparent leur version (`Texture`, `TileMapRenderer`, `Text`, `ModelRenderer`), pas d'écouteurs ;
  - les `dependents` (via `DependencyGraph.acquire`) sont relus en chaîne (texture → tileset → tilemap, atlas → police), chacun attend ses dépendances (`DependencyGraph.allReady`) : un seul calcul par donnée lors d'un `reload all` ;
  - non relues : sans source (`hasSource()` faux), préchargées par le code, placeholders ; recalculées (sauf placeholders) si une dépendance change. Une donnée en échec ou en premier chargement est relue sur place ;
  - type sans copie (`createReloadCopy` → `null` : mods, sous-types) : vidé puis relu sur place (signalé une fois). Un sous-type n'hérite pas de la copie du parent ;
  - batch : `loadBatch` garde sa liste, `unloadBatch` libère exactement celle-là ; description relue pendant qu'il est chargé → ajouts chargés, retraits libérés ; description citant une donnée inconnue non appliquée (vaut aussi pour un batch préchargé) ;
  - **observateur de fichiers** (`Resources.watcher()`, `ResourceWatcher`) : **éteint par défaut**, démarré explicitement par le code (`watchAll()`, `watchType(...)`, `watch(ResourceSelection)`), la commande `watch` ou `-Dmightylib.resources.watch=poll|service` (`EngineConfig.setWatchResources`, intervalle `…watch.interval` en ms). Une `ResourceSelection` (réutilisable ailleurs, ex. batchs) = tout, ou un type, + noms et/ou regex sur le nom (nom dans la liste OU regex) ; les sélections s'additionnent. Seules les données chargées (ou en échec) avec fichier (`DataType.sourcePaths()`), ni placeholders ni créées par le code ; chaque chemin logique est suivi dans **chaque source sur le disque** (`localCandidates`, fichier existant ou non : un fichier créé dans une source plus haute recharge la donnée, qui le lit alors) ; une source classpath dans un jar n'est jamais suivie. Modification ou création → `Resources.reload` (les dépendants suivent) ; suppression ignorée (version gardée, une ligne). Changement rapporté quand le fichier est stable 200 ms (éditeurs qui écrivent en plusieurs temps). Détection (`FileChangeDetector`, thread démon) : **scrutation** date/taille à chaque intervalle (défaut 1 s, marche partout) ou **WatchService** (moins coûteux, non récursif : un enregistrement par dossier, repli sur la scrutation d'un dossier non enregistrable). Liste des fichiers suivis rafraîchie chaque seconde. **Regroupement** : les changements d'une même donnée (description + sources écrites l'une après l'autre) sont rechargés une seule fois, 300 ms après le dernier. **Fichiers nouveaux** : les dossiers de chaque source sur le disque sont suivis aussi (date du dossier / `WatchService`) ; un dossier modifié lance `Resources.discoverNewFiles` (thread du détecteur, `ResourceLoader.discover`, par défaut `create`) puis enregistre sur le thread principal les données absentes que la sélection accepte, et rafraîchit les batchs chargés (motifs). `TextureDataLoader.discover` ajoute les images de `textures/` (toutes sources) absentes de `textures.json`, avec les paramètres par défaut de `TextureData` (realistic, 2D) et un avertissement. Limite : fichier déposé dans un sous-dossier créé il y a moins d'une seconde, vu au prochain changement de dossier. Tests : `FileWatchTest` ;
  - nouveau type : implémenter `createReloadCopy` (copier les réglages donnés par le code, ex. `TextureData.copySettingsFrom`) et `swapContent` (échanger tout ce que lisent `initWithFile` et `internLoad`) ; au besoin `reloadFailed` (garder ce que la copie échouée a trouvé).
- Commande `resources sources [chemin]` (`DEV`) : la pile (nom, propriétaire, `engine`/`game`/`plugin`, disque/classpath en dossier/jar/préfixe absent, observable) ; avec un chemin, les sources qui l'ont (taille) et celle qui le sert (`Resources.describeSources`). Démo : `DemoPlugin` déclare `assets/demo/` (`demo/src/main/resources`), `ResourceSourcesScene2D` (texture du dossier du jeu remplacée au même chemin, texture ajoutée par le `textures.json` de la démo, batch dans la source de la démo, couches de chaque fichier).
- Commande `resources` : par type, chargées/préchargées/référencées, mémoire estimée (`cpuBytes`/`gpuBytes`, totaux), chargées sans référence (fuite), référencées non chargées, état du pipeline (dont `wantedDone`/`wantedTotal`, étapes de préchargement) ; `resources batch <nom>`, `resources preload|unpreload <batch>`. Tests : `Resources*Test` (base `ResourcesTestBase` ; batchs, annulation, dépendances, échecs et repli, ressources manuelles, rechargement, préchargement, cycles aléatoires).

## Ressources GPU (`GLResources` / `GLElement`)
- Objets GL partagés et comptés, clé = classe + nom : `addElementOrReturnIfPresent()` ajoute une référence urgente (à équilibrer par `releaseResource()`) ; `getResource()` cherche sans référencer. Libérer plus que référencé (objet déchargé deux fois) est refusé avec une ligne d'erreur.
- **Éléments des batchs** : une donnée listée directement dans un batch fait envoyer son élément GL pendant le chargement (`DataType.glElementType`/`glElementName`/`createGLElement` : `TextureData` → `Texture` de même nom, `ShaderData` → `Shader` (programme) de même nom, `TileMap` → texture de son atlas `tilemap:<carte>`, celle de `TileMapRenderer`) ; une entrée de batch s'en exclut par `"gpu": false` (ex. textures de tilesets dans `init.batch`, qui ne servent qu'à construire l'atlas) ; une dépendance n'est pas envoyée. `BatchManager` tient une référence par chargement de batch (via `IGLElementSink`, implémenté par `GLResources` et donné à `Resources` par `MainLoop` ; absent dans les tests de `Resources`), rendue par `unloadBatch`/`cancelPreloadBatch` ou une nouvelle description. Les renderers trouvent l'élément déjà chargé : `launch` n'envoie que ce qui n'est pas dans les batchs.
- **Urgence** : un élément est urgent s'il a une référence urgente (renderer, batch chargé) ; sinon préchargé (`preload:<batch>`). Deux files ordonnées (`LinkedHashSet`, passage de l'une à l'autre en O(1)) : `process` passe les urgents puis les préchargés ; `hasElementsToLoad` ne compte que les urgents (`gl summary` : `waitingToLoad`/`waitingToPreload`). À la sortie, `unload` supprime aussi les éléments encore référencés.
- **Jamais bloquant** : l'ajout met en file ; après chaque `display()`, `GLResources.process(deadline)` avec l'échéance du chargement (toute la frame sous un écran de chargement, part `setInGameLoadingShare` sinon), au moins une étape ; plafond `EngineConfig.setMaxGLUploadMillisecondsPerFrame`. `GLElement.load(ms)` renvoie `false` tant qu'il n'a pas fini. Une étape peut libérer d'autres éléments (`releaseResource` les retire des files en cours de parcours). `addElementAndLoadNow` charge un élément pendant l'appel (petits éléments nécessaires avant tout dessin). Tests : `GLResourcesTest`, `GLResourcesFallbackTest` (sans GL).
- **État partagé par type d'élément** (`IGLSharedState`, `GLResources.shared(classe, fabrique)`) : un par classe, créé à la première demande, `loadingIdle` quand les files sont vides, `delete` à la libération de `GLResources`. `GLResources` ne connaît aucun type d'élément : `TexturePlaceholders` (1×1 transparent, damier en `GL_TEXTURE_RECTANGLE` à la demande ; libère les PBO de `TextureUploader` à `loadingIdle` et `delete`, enregistré par la texture qui envoie des bandes), `CubeMapPlaceholders` (cubemap transparente 1×1).
- **Échecs** : `load` lève `ResourceException` pour un échec attendu (après avoir supprimé ce qu'il a créé) → élément **en échec** (`hasFailed`) : retiré des files (ni boucle, ni écran de chargement bloqué), une ligne de journal, ses utilisateurs prennent le repli ; `gl summary` le liste dans `failed`. Il n'est réessayé que quand une de ses données est rechargée : `Resources` appelle `IGLElementSink.dataReloaded(donnée)` (thread principal) à chaque fin de chargement d'une donnée qui n'en est pas à sa première version, et `GLResources` remet en file ses éléments en échec qui en dépendent. `reload` qui lève `ResourceException` : l'élément garde sa version chargée (une ligne, pas d'échec). Un élément dont une **donnée** a échoué n'est pas en échec : il attend dans sa file sans bloquer l'écran de chargement (`blockedByFailure`).
- **`Shader`** (programme, `GLElement`) fait de `ShaderData` (sources prétraitées, lues par un worker ; tag 2D/3D) : compilé puis lié par étapes (vertex, fragment, géométrie, liaison) à partir d'une copie des sources et de leur version prise au départ, recommencé si la version change entre deux étapes. GLSL qui ne compile pas : au premier chargement, élément en échec (repli magenta) ; au rechargement, l'ancien programme reste (version rejetée, pas réessayée tant que la donnée ne change pas). Donnée rechargée → `Shader.use` voit la nouvelle version et demande un `reload` : nouveau programme, échangé une fois lié. Les valeurs envoyées (`lastValues`), emplacements et uniforms signalés absents appartiennent au programme : vidés avec chaque nouveau programme. Supprimer un programme appelle `GLContext.forgetProgram` (l'id peut être réutilisé). Repli : `FallbackShader` (de `FallbackShaderData`, `glElementNeededBeforeDrawing`), **lié tout de suite** par `GLResources.fallbackDataLoaded`, lu par `GLResources.fallback(ShaderData.class)` et gardé en cache par chaque `Renderer` (`getShader`), uniforms absents non signalés ; ses matrices partent de l'identité puis reçoivent celles de chaque renderer (valeurs optionnelles), gardées jusqu'au suivant : un quad déjà en coordonnées écran (`VirtualSceneRenderer`) s'y réduit à quelques pixels, l'écran reste noir plutôt que magenta, y compris aux premières frames, avant la liaison de `postProcessing`. Les programmes liés passent par `GenDeleteResources.GenProgram`/`DeleteProgram` (compteur `Program`) ; les étapes, supprimées dès la liaison, ne sont pas comptées.
- `Texture` : > 4 Mio (2D) envoyée par bandes `glTexSubImage2D` (256 Kio–4 Mio selon débit mesuré et temps restant). Non chargée (en cours/échec) → `bind` de l'élément de repli de `fallbackDataType()` (type de sa donnée par défaut ; une texture d'une image possédée par une autre donnée donne le type du propriétaire), 1×1 transparent tant que celui-ci n'est pas envoyé ; même cible pour une texture rectangle (damier rectangle) ; `hasElementsToLoad` ignore les échecs. Donnée rechargée (version différente au `bind`) → renvoyée dans une seconde texture GL (`GLElement.requestReload`/`reload`, même budget) qui remplace l'ancienne une fois complète. `getWidth/getHeight` = taille affichée ; ce qui en dépend attend `Texture.isUpToDate()` (ex. `TileMapRenderer` garde ses tuiles, animations en pause).
- **Cubemaps** (`resources/cubemap/`, loader optionnel `CubeMapLoader`) : `resources/cubemaps/<nom>/right|left|top|bottom|front|back.png` (ordre de `GL_TEXTURE_CUBE_MAP_POSITIVE_X` à `NEGATIVE_Z`), une donnée par dossier, sans JSON ; `CubeMapData` (`MultiSourceDataType`, six faces décodées par STB, carrées et de même taille ; face manquante ou mauvaise → échec qui la nomme). Convention des cubemaps (celle des images de skybox courantes) : vue de l'intérieur, une face latérale apparaît en miroir, le dessus et le dessous retournés. Élément `CubeMapTexture` : une face par étape, rechargement dans une seconde texture échangée une fois complète ; non chargé → repli `FallbackCubeMapData` (six damiers, son propre élément), sinon `CubeMapPlaceholders`. Tests : `CubeMapLoaderTest`.
- **Skybox** (`SkyboxRenderer`, `_3D`) : cube vu de l'intérieur, programme `skybox` (tag 3D, ne garde que la rotation de la vue : `mat4(mat3(view))`), dessiné en premier sans test ni écriture de profondeur, culling désactivé ; lie lui-même sa `CubeMapTexture` (prise par `acquire`, la cubemap doit être listée par un batch de la scène). Démo : `TerrainGeneration3D` (batch `skybox`, ciel `sky` généré par `tools/generate_skybox.py`, nom de chaque face écrit dessus).
- `ModelRenderer` : une version = un `MeshSet` (un `Mesh` par mesh du modèle, ses textures), un mesh par frame ; une nouvelle version remplace l'affichée une fois complète. `ModelRenderer extends Renderer` (pas de `Mesh` de base) : le programme est utilisé une fois, `draw()` lie les textures puis dessine chaque mesh.
- Atlas d'une `TileMap` (`TileSetAtlas`, texture `tilemap:<carte>`) = contenu de la carte construit dans `internLoad`, échangé au rechargement.
- Son : les buffers des sons passent par le service de son (`ISoundBuffers`, donné aux ressources par `Resources.setSoundBuffers` au démarrage ; sans service, un son ne se charge pas) : `SoundData` y crée son buffer et l'y supprime ; `OpenALSoundService.deleteBuffer` détache d'abord le buffer des sources (relecture d'un son). Le service muet (`SilentSoundService`, aucun appel OpenAL : repli quand aucun périphérique ne s'ouvre, ou `-Dmightylib.sound=silent`) donne des numéros de buffers, garde les réglages et l'état des sources (une source non possédée finit au tick suivant) et lit le vrai arbre des gains. À l'arrêt, la phase `unload` du service supprime les sources après le déchargement des scènes (qui peuvent encore arrêter leurs sources) et avant les buffers, et vide leur liste : le détachement ne touche plus de source supprimée (sinon `AL_INVALID_NAME`) ; `terminate` ferme le périphérique. Sources : une source attend son délai avec ses réglages de création (la source OpenAL est créée à la fin du délai ; sans donnée pour son son, ni repli, elle est supprimée sans jouer) ; au changement de scène, `clearAwaitedSong` retire les sources encore en attente, jamais créées. Par défaut, `lateUpdate` supprime une source dès qu'elle s'arrête (son ponctuel, aucune référence à garder). Une source possédée (`SoundSourceCreationInfo.owned` : ambiance, musique) n'est supprimée qu'après `ISoundSource.release()`, que son créateur appelle (une scène, dans `unload()` : rien n'arrête un son au changement de scène) ; arrêtée par le rechargement de son son, elle rejoue dès que le nouveau buffer est chargé. `isReady()` dit quand ses réglages sont valides (source créée après le délai, pas encore libérée).
- Chargement de scène : l'écran de chargement reste tant que `GLResources` a des éléments urgents (ceux des batchs de la scène et ce que `launch` a demandé) ; avertissement après 10 s.
- Renderers 2D utilisables dès le constructeur ; géométrie envoyée au premier `display()` puis après chaque modification.
- **Toujours** `GenDeleteResources` (VAO, VBO, EBO, textures, FBO, RBO, programmes, gardés dans des ensembles : retrait en temps constant, même avec des milliers d'objets ; VAO, FBO et RBO sont supprimés dans le contexte qui les a créés), jamais `glGen*`/`glDelete*` (`PrintAll()` au changement de scène).
- **Contextes GL** (`graphics/internal/GLContext`, thread principal) : un contexte racine caché (créé avec la première fenêtre, détruit après la dernière) crée le groupe de partage ; chaque `Window` a son `GLContext` et partage ses objets avec lui. **Partagés** (créés une fois, utilisables dans toutes les fenêtres) : textures, VBO, EBO, PBO, programmes (`Shader`) → `Resources`/`GLResources` restent uniques. **Propres à un contexte** : VAO, FBO, RBO, état GL (`GLContext.state()` : programme lié, capacités, blend, textures liées). `GenDeleteResources.Gen*` enregistre un VAO/FBO/RBO dans le contexte courant ; sa suppression prend le contexte propriétaire (`DeleteVertexArrays(owner, id)`) : immédiate s'il est courant, au prochain `makeCurrent` sinon, ignorée si sa fenêtre est détruite. `Count`/`PrintList` additionnent les contextes vivants. `Window.bindWindow()` = `GLContext.makeCurrent()` (fait aussi `GL.setCapabilities`). `GLResources.process` termine par `glFlush` quand plusieurs fenêtres existent (ce qui est envoyé n'est visible des autres contextes qu'une fois les commandes émises).
- **`Mesh`** a un VAO **par contexte**, créé au premier `bind()` dans ce contexte et reconstruit depuis la description des attributs (canal, taille, type et activation de chaque VBO, EBO) quand elle change (`layoutVersion`) : un renderer s'affiche dans n'importe quelle fenêtre du groupe. `FrameBuffer` reste lié au contexte qui l'a créé (`bindFrameBuffer` le vérifie sous `Logger.isGLErrorCheck()`). Une création de fenêtre qui échoue est signalée par le callback d'erreur GLFW et la fenêtre reste « non créée ».

## Rendu
- `Mesh` = géométrie seule : VAOs (un par contexte GL) + VBOs (+ EBO) + mode de dessin ; chaque VBO a un **canal** (location de l'attribut), le suivant libre par défaut ou donné (`addVboFloat(canal, …)`, `IllegalArgumentException` si pris) ; canaux usuels 0 position, 1 UV, 2 normales ; `enableVbo`/`disableVbo` prennent un canal. Point d'accroche : `draw()`. `Renderer` (abstraite, sans `Mesh`) = transform (→ `model`), son `Material` (`material()`, `setMaterial` ; `getShader()` = le programme du matériau s'il est lié, sinon celui de repli : toujours un programme lié), ses valeurs (surcharges), visibilité, caméra de référence. `display()` = `applyRenderState()`, programme utilisé, `updateShader()`, `draw()` (abstraite) ; ce sont les points d'accroche. `RenderState` = test de profondeur, écriture de profondeur, culling, blend, appliqués à chaque dessin par le cache d'état (défauts lus dans le tag du shader : `2D`/`none` sans profondeur, sinon avec ; culling désactivé) ; la caméra par défaut (2D ou 3D) vient du même tag. `MeshRenderer extends Renderer` = un `Mesh` qu'il retient (`unload` le rend ; constructeurs `(shaderName, useEbo)`, `(Material, useEbo)`, `(Mesh, shaderName)` et `(Mesh, Material)`) + les textures de son matériau ; les renderers concrets (formes 2D, `Text`, `TileMapRenderer`, `CubeRenderer`…) en héritent. `Mesh`, `Renderer`, `MeshRenderer`, `Shape2DRenderer`, `VectorShape2DRenderer` n'ont aucun champ `protected` (`ExtensionFieldsTest`). `Renderer.setX`/`setY`/`setZ` passent par le hook `setPosition(Vector3f)` : une sous-classe qui suit la position (`Text` et sa boîte `leftUpPosition()`) voit tous les déplacements.
- **Formes 2D** (`graphics/renderer/_2D/shape`) : `RectangleRenderer` = sprites (quad texturé ou coloré, sans anticrénelage). Les **formes vectorielles** héritent de `VectorShape2DRenderer` (extensible, sous-classe de `Shape2DRenderer`) : même API de position, taille, point de référence, rotation ; remplissage = couleur de `setColorMode` (blanc par défaut, alpha 0 = contour seul) ou texture principale teintée par la couleur (`setColorMode(c, false)` la garde ; posée sur le rectangle par `setTexturePosition`) ; contour `setStrokeWidth` (0 = aucun, défaut), `setStrokeColor` (noir, copiée), `setStrokeAlignment` (`EStrokeAlignment` `INNER`, `CENTERED` par défaut, `OUTER`), `setStrokeUnit` (`EStrokeUnit.WORLD` par défaut : suit le zoom ; `SCREEN_PIXELS` : même largeur à tout zoom) ; `setAntialiasing(false)` : bords nets. **Formes par distance signée** sur un quad : `RoundedRectangleRenderer` (rayon commun ou par coin, référence en haut à gauche), `CircleRenderer`, `EllipseRenderer`, `TriangleRenderer` (sommets en 0..1 du rectangle), `ArcRenderer` (rapport du rayon intérieur, angle de départ, ouverture : arc épais, secteur, anneau), `RegularPolygonRenderer` (3 à 64 côtés, boîte englobante étirée sur la taille), `HexagonRenderer` (6 côtés, `STRETCH_RATIO`), `PointsRenderer` (N points ronds ou carrés, `EPointShape`, un quad par point, un appel), `GridRenderer` (lignes périodiques tracées avec le contour : pas, origine). Le vertex shader commun (`2D/shape/shape2DV.glsl`, include `utils/shape2DVertex.glsl`) élargit le quad de la partie extérieure du contour + 1 pixel (+ `extraMargin()`) et passe au fragment shader la position dans le **repère de la forme** (origine au centre, unités du monde, axes de la forme) : juste au zoom et sous toute rotation de la forme ou de la caméra ; le corps de chaque forme du moteur est une fonction de `utils/shapeKinds2D.glsl` qui rend sa distance (`roundedRectangleDistance()`, `circleDistance()`…, la grille compose sa couleur : `gridColor(pixel, fill)`), appelée par le fragment shader de la forme seule (`2D/shape/<forme>2DF.glsl`) et par le programme de lot commun (Lot de dessins 2D) ; la distance va à `shapeColor` (include `utils/shape2D.glsl` : fonctions `sd*`, couverture d'un pixel par `smoothstep` dans l'alpha, contour par-dessus le remplissage, `discard` à couverture nulle ; mélange dans le mode de couleur du dessin), qui vaut `shapeColorWith(d, shapeFragmentPixel(), shapeFillColor())` : dérivées et texture lues par l'appelant, hors de tout branchement. Tous les paramètres passent par des `out` (le lot les donne par instance : voir Lot de dessins 2D). Uniforms des formes optionnels (`putOptionalValue`) : une forme qui n'en lit qu'une partie n'est pas signalée. Une forme d'un projet = un fragment shader déclaré dans `shaders.json` + une sous-classe (`writeShapeParameters` vers `shapeData0/1`, `extraMargin`) ; pour être regroupée, son entrée a `"batch"` vers **son propre programme de lot** `2D/shape/shape2DInstancedV.glsl` + son fragment shader (tags `2D`, `batch2D`), enregistré avec `BatchFormats.SHAPE` (`registry.shaders().batchFormat` ; - **Les valeurs d'uniform appartiennent au `Material` et au `Renderer`, pas au programme** : ce que le matériau partage (programme, valeurs communes, textures, état) est dans le `Material` (`addShaderValue`, `putOptionalValue`) ; ce qui est propre au renderer (matrices génériques, couleur, valeurs ajoutées par `Renderer.addShaderValue`) est dans ses **surcharges**, qui gagnent sur celles du matériau (comme le `MaterialPropertyBlock` d'Unity). Au dessin le matériau envoie ses valeurs (sauf celles que le renderer surcharge) puis le renderer les siennes, à chaque dessin (le programme saute les valeurs inchangées), car le programme peut changer à tout moment (repli, rechargement à chaud). Les valeurs **optionnelles** (`putOptionalValue` : matrices génériques, samplers de `ModelRenderer`) ne sont envoyées que si le programme courant a l'uniform, sans signalement. Ce qui dépend du programme (matrices génériques, texture spéculaire et brillance de `ModelRenderer`) est décidé au dessin (`hasUniform`), jamais au constructeur. **Locations entières** : `UniformValues` (package-private) trouve la location de chaque valeur une fois par programme (`Shader.location`, `Shader.programStamp()` change à chaque nouveau programme : première liaison, rechargement ; le repli a son propre jeu) puis l'envoie par `Shader.sendValue(location, valeur)`, dernier envoi mémorisé par location ; plus de recherche par nom à chaque dessin. `Shader.sendValueToShader(valeur)` (par nom) reste pour une valeur envoyée à la main, valable pour le programme courant seulement. `IUniformTarget` (`Material`, `Renderer`) : `addShaderValue`/`updateShaderValue`/`removeShaderValue`/`hasShaderValue` ; `IShaderUniforms.addTo`/`update` écrivent un groupe de valeurs (Phong, lumières) dans l'un ou l'autre.
- `Shader.sendValueToShader` ne renvoie qu'une valeur changée ; uniform absent du programme signalé une fois et ignoré (sauf par le repli).

- **Service des shaders** (`IShaderService`, clé `mightylib:shaders`, `engine.shaders()` ; `ShaderService` par défaut, `final`, sans GL, remplaçable par `registry.services().replace`) : `declarations()` = l'objet `shaders` de `shaders/shaders.json`, lu une fois à la création du service (copie profonde à chaque appel) et fusionné par entrée à travers les sources (celui du moteur déclare les siens, celui du jeu les siens ; type `ShaderData` dans les batchs et les commandes) ; une entrée a `files` (relatifs à `folder()` = `shaders/`), `tags` (`2D`/`none` → shader 2D) et, optionnel, `defines` (`{"NOM": "valeur"}`, `""` pour un simple `#define NOM`, un nombre ou un booléen gardé tel qu'écrit, toute autre valeur refusée ; deux entrées peuvent partager leurs fichiers avec des defines différents ; gardés, immuables et triés, dans la `ShaderData`). **Prélude** (`prelude(defines de l'entrée)`), écrit avant chaque source : `#version 330 core` (seule version : `GLContext` demande un contexte 3.3 core ; un service remplacé peut en écrire une autre), defines globaux triés par nom, defines de l'entrée (ils gagnent sur un global de même nom) ; le préprocesseur ajoute `#line 1 0`. **Defines globaux** : `setDefine(nom, valeur)`/`removeDefine(nom)` (thread principal ; nom = identifiant GLSL sans préfixe `GL_`, valeur sans retour à la ligne, même règle pour ceux d'une entrée : `checkDefine`, méthode `default` du contrat qu'un service remplacé peut changer, appelée par le `ShaderLoader` avant la lecture ; un define d'entrée invalide → `ResourceException`, repli), `defines()` = instantané immuable trié (une `TreeMap` copiée à chaque changement, publiée par un champ `volatile` ; le worker la lit une fois par lecture de shader, la même pour toutes ses étapes). - **Bibliothèque GLSL** (`ShaderPreprocessor(lecteur, dossier, prélude)`, sans GL, appelé par `ShaderLoader` sur le worker) : les fichiers GLSL n'ont pas de `#version` (le prélude l'écrit) ; un `#version` dans un fichier, principal ou inclus → `ResourceException` (repli, exception en mode strict). `#include "chemin"` cherché d'abord à côté du fichier qui inclut, puis dans le dossier des shaders (`#include "utils/colorsManipulation.glsl"`) ; un projet ajoute ses fichiers sans toucher au JSON du moteur. Un fichier inclus une fois par source (les suivants restent en commentaire), cycle ou include manquant → `ResourceException` (la donnée échoue, repli). Sortie = prélude + `#line 1 0` + source ; des `#line n id` sont insérés (id = indice du fichier, 0 = le principal ; un avant et un après chaque include pour revenir au fichier qui inclut) et le journal du compilateur est traduit au mieux (`0(12)`, `0:12`) en `fichier:ligne`. `ShaderData.sourcePaths()` = ses fichiers, ceux qu'il inclut et les chemins d'un include manquant (liste immuable remplacée par le worker, lue par l'observateur) : modifier une bibliothèque ou créer l'include manquant recharge le shader, y compris après un rechargement échoué (`ShaderData.reloadFailed` ajoute les fichiers de la copie aux siens). - **`Material`** (`graphics/renderer`, `final`, `EXPERIMENTAL`) : programme (référence urgente, repli comme avant), valeurs communes, textures (principale unité 0, canaux 1 à 30 : `setMainTexture`, `setTextureChannel`) et `RenderState` (profondeur, culling, **blend** `EBlendMode` : `NONE`, `ALPHA` par défaut, `PREMULTIPLIED`, `ADDITIVE`, `MULTIPLY`, mode de couleur). `Renderer.setLayer` et `setSortDepth` l'alimentent. **Barrières** (le tri ne les traverse jamais) : renderer dessiné seul, `clear`, `setScissor`/`clearScissor`, liaison d'un framebuffer, changement de contexte, début du lot d'une autre vue du même contexte, fin de `display` de la vue, `flush()` explicite (avant du GL brut), changement de mode ; `GLContext.flushDraws` les relaie par `IPendingDraws`. **Modes** (`EBatch2DMode`, `EngineConfig.setBatch2DMode`, `-Dmightylib.batch2D`, commande `batch mode`, à chaud) : `OFF` (dessin immédiat, référence du rendu), `ORPHAN` (défaut ; `glBufferData(null)` puis `glBufferSubData`), `RING` (`glMapBufferRange` non synchronisé, une fence par envoi ; avant d'écrire une plage, attente de tous les blocs qui la recouvrent, où qu'ils soient dans la file : `RingBlocks`), `INSTANCED` (comme `ORPHAN`, et les séries de quads parallélogrammes d'une couleur de `BatchFormats.SPRITE`, dont le matériau a un programme instancié de `SPRITE_INSTANCED`, en instances d'un quad unité, après les instances des formats ; les autres par les sommets dans le même envoi). Tampons créés au démarrage du moteur et à l'ouverture d'un contexte, ceux d'un mode quitté ou d'un contexte fermé supprimés. API directe : `DrawBatch2D.drawRegion`, `drawRectangle`, `drawQuad` (avec un `Material`). **Culling de vue** : chemin d'un dessin de renderer : `Renderer.batchPlace(batch)` (valeurs propres, part de matériau : `Material.batchPart`, son chemin rapide (table, générations, version, programmes du shader et du programme de lot) lu d'abord, la vérification du format seulement à la reconstruction ; place de caméra ; un état sans mode de couleur), puis `Renderer.viewCulled(batch, place)`, puis seulement pour un dessin visible `batchState(place)` (mode de couleur résolu : `resolveColorSpace`, `BatchStateTable.withLinear`) et l'écriture ; `batchState(batch)` fait les deux d'un coup (`TileMapRenderer`, qui teste ses tuiles). `viewCulled` teste sa boîte (`ViewCullBounds`, un objet réutilisé par lot : aucune allocation) contre la boîte de la vue de la caméra de l'état (`DrawBatch2D.isCulled`). `BatchStateTable` calcule cette boîte une fois par place de caméra, en unités du monde (inverse de projection × vue sur les coins du clip, un peu élargie contre l'arrondi des flottants ; une caméra tournée donne une boîte plus grande, jamais un dessin visible perdu ; une caméra qui n'est pas une transformation 2D affine, comme une perspective, n'a pas de boîte : rien n'est éliminé). Une boîte qui touche la vue n'est pas éliminée ; un dessin éliminé n'écrit ni sommets, ni indices, ni indice d'appel, et ne coupe aucune série. La boîte d'un dessin vient de l'accroche `Renderer.viewCullBounds(ViewCullBounds)` (boîte locale, transformée par le modèle, ou du monde ; marges en unités du monde et en pixels du viewport ; `false` = aucune boîte, jamais éliminé et compté « sans boîte » par classe) : `Shape2DRenderer` (positions de `calculatePosition`), `Animation2DRenderer` (quad), `MeshRenderer` à données CPU (boîte des positions du canal 0, recalculée quand `MeshCpuData` change : `Text`, `GraphRenderer`, `NodesRenderer`, `MatrixRenderer`), formes vectorielles (rectangle du quad + `ShapeStroke.quadMargin`, avec la taille d'un pixel de la caméra et du viewport : `ShapeCullBounds`, copie du calcul des vertex shaders), `PointsRenderer` (boîte des centres + demi-taille d'un point + marge), formes géométriques (boîte des bases + plus longue extrusion × (demi-épaisseur + frange)) ; `TileMapRenderer` garde son test par tuile ; l'API directe (`drawRegion`, `drawRectangle`, `drawQuad`) teste ses coins et rend `true` quand elle élimine. Marge des sommets déplacés par un shader (ondulation, vent) : `Renderer.setViewCullMargin` et champ `"cullMargin"` (≥ 0, unités du monde, sinon `ResourceException`) d'une entrée de `shaders.json`, le maximum de celles du shader et de ses programmes de lot étant dans la part de matériau. **Actif par défaut** : `EngineConfig.setViewCulling2D`, `-Dmightylib.viewCulling2D=on|off`, `Engine.setViewCulling2D` (à chaud), commande `batch cull on|off` ; retrait par renderer `setViewCulling(false)`. Les dessins seuls (3D, test de profondeur, shader sans lien de lot) et `DebugDraw2D` ne sont pas testés. Outils de vérification (`ViewCullTools`, un par moteur) : `batch cull inset|show|freeze|list`. **Compteurs** : par vue (`DrawBatch2D.lastFrame*`, `describe`) et dans `stats` : dessins testés, éliminés, sans boîte (par classe dans `batch`), octets envoyés (sommets, indices et instances comptés à l'envoi ; par format, ceux que les dessins ont écrits), dessins et octets par appel, tuiles de carte éliminées et écrites ; avec `batchFlushesPerFrame`, `batchedDrawsPerFrame`, `batchBarriersPerFrame` et `renderCpuMs`. Scène : `ViewCulling2D`. La 3D reste hors du lot (dessinée seule), mais le format ne suppose pas la 2D. **Coût CPU d'un dessin** (hors appels GL, 16 000 renderers, `python tools/bench.py --isolated --repeat 3`) : rectangle ou animation visible ~70 à 90 ns, forme vectorielle ~155 ns (écrite valeur par valeur), texte court ~270 à 470 ns (selon les décisions du JIT d'une JVM à l'autre), dessin éliminé ~40 à 50 ns ; aucune allocation par dessin (`Identifier` garde son hash, `Views.current` lit la dernière vue de son thread sans `ThreadLocal`) ni par appel de dessin (attributs des formats pointés sans itérateur, `BatchLayouts`) ; à 128 000 objets le coût double (chemin borné par la mémoire : un `display()` par objet, même hors champ). L'envoi d'un lot (tri, tampons, appels GL) est l'événement JFR `mightylib.BatchSend` ; le reste de `mightylib.Frame` est l'écriture CPU.
- **Dessins de debug** (`graphics/debug`, `DebugDraw2D`, un par vue : `IView.debugDraw()`, `Scene` et `WindowView`) : `line`, `polyline`, `rect`, `circle`, `cross`, `arrow`, `text`, en coordonnées du monde (caméra 2D de la vue) ou de l'écran (taille virtuelle, `EDebugSpace`), épaisseurs en pixels d'écran ; sans renderer : écrits dans le lot de la vue avec les formats existants (traits = quads `SPRITE` de `colorShape2D`, cercles = instances `SHAPE` de `circle2D`, texte = quads de l'atlas par `TextLayout.Place`, la fonction de placement que `Text` utilise aussi). Dessinés une fois par frame après une barrière, par-dessus tout, à la fin du dessin de la vue (dans `setAndDisplayRealScene` avant le passage final, sinon à la fin de son `display`) ; vidés au `unload` de la scène et à la fermeture de la fenêtre (matériaux rendus). **Durées de vie** (`IDebugLifetime.alive()`, demandée une fois par frame avant le dessin ; `DebugLifetimes`) : `oneFrame()` (défaut ; un nouveau tick de mise à jour remplace ceux du tick précédent), `frames(n)`, `seconds(s)` (somme de `GameTime.DeltaTime`), `whileTrue(condition)`, `untilRemoved()` ; chaque dessin rend une `DebugDrawHandle` (`remove()` ; `DebugDrawHandle.NONE` partagée pour une frame : aucune allocation). La file (`DebugDrawQueue`) garde ses tableaux d'une frame à l'autre. Interrupteur global (`Engine.debugDraws()`, `DebugDraws`) : `EngineConfig.setDebugDraw`, `-Dmightylib.debugDraw=on|off` (défaut `on`, release compris), commande `debugdraw` ; éteint, rien n'est enregistré et les dessins en attente sont jetés. Scène : `DebugDrawing2D`.
- **Police par défaut** : un `Text` sans `setFont` prend `EngineConfig.getDefaultFont()` (`setDefaultFont`, `EngineResources.DEFAULT_FONT` = `engineSans` par défaut, à charger au démarrage, sinon police de repli) ; `setFont` la remplace.
- Textes dessinés (`DrawnTexts`, thread principal) : chaque `Text.display()` enregistre son texte, la position de son premier caractère (espace de sa caméra), sa taille et son corps dans des entrées réutilisées (aucune allocation une fois les frames stables) ; `MainLoop` appelle `beginFrame` avant `Engine.displayWindows`, et la commande `gl text` lit la dernière frame complète, triée de haut en bas puis de gauche à droite (toutes fenêtres confondues).
- **Retour à la ligne** : `Text.setMaxWidth(largeur)` (0 = aucun, défaut ; padding non compté) coupe aux espaces avec `TextWrap` (sans GL, mesure injectée) : le saut de ligne est ajouté **après** l'espace qui finit un mot, donc `text()` reste le texte donné et chaque caractère garde son indice (`getPositionOfChar`) ; un mot plus long que la ligne est coupé là où elle est pleine (un caractère au moins), les sauts de ligne du texte sont gardés. Les espaces en fin de ligne d'un texte coupé ne comptent pas dans sa largeur (alignement centré ou à droite, taille). `fitText` et la coupe par caractère de la console sont à part. Scène : `TextPaddingScene`.
- **Projection des caméras** : `updateProjection()` (`writeProjection`) remplace la projection (`setOrtho`, `setPerspective`), jamais composée avec la précédente : `Camera2D.invertView`, `Camera3D.setViewAngle`/`setViewMode` la recalculent. Test : `CameraProjectionTest`.
- **Référence d'une boîte** : `Direction.AnchorOffset(référence, largeur, hauteur, out)` = décalage du coin haut gauche par rapport au point de référence (y vers le bas : x `0`, `-l/2`, `-l` ; y `0`, `-h/2`, `-h` ; `None` = centre, `Undef` = coin haut gauche), sans allocation ; utilisé par `Text` et `TileMapRenderer`. `TileMapRenderer.setReference` décale toute la carte dans son espace local (sommets et culling ; la position passe par la matrice du modèle), en pixels entiers vers zéro ; scène `TileMapReferences2D` (les neuf références). Tests : `DirectionTest`, `TileMapRendererTest`, `TileVisibilityTest`, `TileMapBatchGLTest`.
- **Animations** (`resources/animation`) : `Animation()`/`Animator()` lisent les ressources de la vue courante, `Animation(Resources)`/`Animator(Resources)` celles données (tests, outils, sans moteur). `update()` = `update(GameTime.DeltaTime())` ; `update(secondes)` (× vitesse) passe autant de frames que le temps en couvre, le temps au-delà de la fin d'une boucle continue dans la suivante, sans boucle l'animation finit sur sa dernière frame. `isCurrentFrameChanged`/`Animator.isFrameChanged`/`animationChanged` restent vrais jusqu'au `lateUpdate` (`Animator.lateUpdate` appelle celui de l'animation courante ; `Animation2DRenderer.update` l'appelle). Donnée pas encore chargée (ou en échec, ou nom inconnu) : le repli (`FallbackAnimationData`), puis redémarrage quand la donnée devient utilisable. Une durée de frame ≤ 0 ou non finie fait échouer le fichier au chargement. Tests : `AnimationTest`, `AnimatorTest`, `AnimationDataTest`, `Animation2DBatchGLTest`.
- **GUI** (`graphics/gui`) : `GUI` (composants sélectionnables : survol, `forceSelect`), `GUIList` (navigation haut/bas entre composants, activation), sliders, sélecteurs, `BackgroundlessButton`. `TextField` (un `GUI`) : une ligne de texte, prend le focus de sa fenêtre au clic dedans (`InputFocus`) et le rend au clic dehors (le clic reste pour la scène), Échap, Entrée, Haut ou Bas ; édite avec les touches de la ligne de saisie de la console (`inputs/text/LineEditKeys` : curseur, mots, Début/Fin, Retour arrière/Suppr, sélection Maj, Ctrl+A/C/X/V, partagées avec `ConsoleInput`) ; souris comme la ligne de saisie : clic (Maj : étend la sélection), glisser, double clic = le mot, triple clic = toute la ligne (`ClickCounter`) ; texte d'invite gris, curseur clignotant, ligne défilée autour du curseur. La logique est `TextFieldModel` (sans GL, testée) ; la scène appelle `update()` puis lit `isChanged()`, `isSubmitted()`, `getLeftWith()` (touche qui a rendu le focus). `inputs/KeyRepeat` (sans GL, temps donné par l'appelant) répète une action tenue comme le clavier du système : un pas à l'appui, puis après 0,5 s un pas toutes les 1/30 s (réglages par défaut de Windows) ; une touche déjà tenue au retour du focus ne répète pas. Un seul champ est prévu (focus par composant, Tab et plusieurs champs : `later.md`). `ScrollList` : liste à molette, une ligne sélectionnée en permanence (`ListSelection`, sans GL : sélection, première ligne montrée, `setItems` qui garde l'élément sélectionné s'il existe encore, sinon la première) ; haut/bas par `setupKeyboardActions` (tenu : répétition de `KeyRepeat`, `setKeyRepeat(délai, intervalle)`) ou `moveSelection(±1)` (`false` aux extrémités, sans boucle), la molette fait défiler sans changer la sélection, le survol la déplace quand la souris bouge, un déplacement au clavier ou de nouveaux éléments cachent le survol jusqu'au prochain mouvement de souris, coup de molette ou clic (un clic sur une ligne la choisit même si la souris n'a pas bougé) ; `getActive()` = ligne survolée sinon sélectionnée, `getActivated()` = clic sur la ligne survolée ou action d'activation sur la sélectionnée. Scène : `TextFieldScene2D`.
- **Menu de la démo** (`MenuScene`, `SceneChoices` sans GL) : un champ filtre (contient, casse ignorée, sur le nom court), la liste des scènes, un panneau de description, Quit. La liste vient du registre de scènes (`engine().scenes()`, rempli par `DemoScenes` : classe, fabrique, description), sauf le menu lui-même, triée par nom affiché, par dernier ajout ou par dernière modification (Tab ou clic sur le bouton « Sort » à droite du champ ; le tri choisi est gardé d'une visite du menu à l'autre). Les dates viennent de git (`SceneHistory`, lu une fois par exécution dans un worker) : ajout = premier commit du fichier source de la scène (renommages suivis, y compris depuis les anciens dossiers des scènes : `SCENES_DIRECTORIES` liste le dossier actuel puis l'ancien `src/…/scenes/`, et git voit le déplacement comme un renommage parce que les deux sont demandés), modification = dernier commit, ou date du fichier sur disque s'il a des changements non commités ; sans git, aucune date et les scènes sans date viennent après, par nom. Outil de développement : une démo distribuée sans dépôt n'a que le tri par nom ; le nom affiché est le nom court (`PlatformerBox2D`), le nom relatif (`platformer2d.PlatformerBox2D`, `DemoScenes.RelativeName`) seulement si deux scènes ont le même nom court (le nom relatif reste la clé des dates et des descriptions). Un choix lance `Commands.execute("scene <identifiant>")`, Quit et Échap (la scène a le focus) `execute("exit")` : démonstration d'une commande lancée par le code, sur la fenêtre de la scène ; un échec s'écrit en rouge dans le panneau et dans le journal. Navigation : haut/bas (W/S) champ → liste → Quit, Entrée choisit (dans le champ : commence la saisie ; Entrée pendant la saisie lance la première scène de la liste). Une nouvelle scène de la démo s'ajoute à `DemoScenes` (`DemoScenesTest` vérifie qu'aucune ne manque).

## Entrées
- **Gestionnaire** : `IInputManager` (contrat lu par le jeu, la GUI, les caméras et les liaisons), un par fenêtre (`WindowContext.getInputManager()`), créé par la fabrique du registre (`registry.services().inputManager`, `InputManager::new` par défaut) puis lié par `bindDefaults` ; clavier, souris et manettes restent ceux du moteur.
- **Souris** : `MouseManager.getState(bouton)` (lu par les liaisons souris des actions, `InputSimple`) = le vrai bouton ou un bouton simulé (`simulateButton`, `input mouse hold`), masqué par la capture, comme `getButton`. `Camera2D` garde son propre vecteur de zoom : `setZoomLevel(Vector2f)` le copie (sans modifier celui donné), `getZoomLevel()` renvoie une copie, `copy()` ne partage rien.
- **Actions et axes** : une clé `InputAction.of("demo:move_right")` / `InputAxis.of(...)` n'est que son `Identifier` `namespace:path` (`registry/`, minuscules `[a-z0-9_.-]`, `/` permis dans le chemin ; égale à toute clé du même identifiant), constante du jeu. Les plugins les déclarent avec leur liaison par défaut (`registry.inputs().action(clé, IAction)` / `.axis(clé, IAxis)`, liaison facultative ; un identifiant est une action ou un axe, pas les deux). Au gel, le registre construit l'`InputRegistry` de l'`Engine` (`engine.inputs()`, figé), qui attribue à chaque élément l'index de simulation (valable pendant le lancement seulement) ; chaque `InputManager` le reçoit à sa création. À la création d'une fenêtre, `bindDefaults(hasProjectInputs)` lie les défauts de l'espace `mightylib` dans toutes les fenêtres et ceux des autres plugins dans les fenêtres du jeu (`WindowConfig.setProjectInputs`, faux pour la console détachée) ; `init(ActionInput[], AxisInput[])` remplace ces liaisons (défauts du moteur gardés). Moteur (`EnginePlugin`) : `EngineActions.TOGGLE_CONSOLE` (`²`, `GLFW_KEY_GRAVE_ACCENT`, touche à gauche de 1 quelle que soit la disposition), `DETACH_CONSOLE` (F2) et `RELOAD_TEXTURE` (F5, mode debug). Démo : `ActionId`/`AxisId` déclarés dans `DemoPlugin`. Toute l'API (`getState`, `getValue`, `isInput`, `getAxis`, simulation, GUI, composants caméra) prend les clés : une clé non déclarée → `IllegalStateException` (déclarée mais non liée dans la fenêtre : jamais pressée) ; `null` = pas d'action pour `isInput`. Recherche par texte (`InputRegistry.findAction`/`findAxis`, commandes) : identifiant complet, ou chemin seul sans casse s'il est unique. Disposition clavier : `EngineConfig.setKeyboardLanguage()` (QWERTY par défaut, et pour un contexte créé sans `WindowCreationInfo`).
- **Manettes** : un `GamepadManager` commun (`Engine.contexts().getGamepadManager()`, ou `InputManager.getGamepadManager()`), mis à jour par `ContextManager.postUpdate` avant les entrées des fenêtres (chaque fenêtre a son `InputManager`) ; GLFW (`glfwGetGamepadState`, disposition Xbox, SDL_GameControllerDB intégrée, `addMappings`, et `gamecontrollerdb.txt` de la pile des sources lu au démarrage : `ContextManager.ReadMappings` ; le moteur en fournit un (`EngineResources.GAMEPAD_MAPPINGS`, SDL_GameControllerDB figée), celui d'une source plus haute à la racine le remplace) derrière `IGamepadSource` (fausse source en tests).
  - Emplacements 0–15 = joysticks GLFW, 16+ = 8 virtuelles. Connexions appliquées dans `postUpdate` (ensemble stable par tick ; `connectedThisTick()`/`disconnectedThisTick()` durent un tick).
  - Joueurs : plus petit libre, repris à la reconnexion s'il est libre ; `setAutoAssign(false)` + `assignPlayer` pour « appuyez pour rejoindre ». Sans mapping : connectée sans joueur.
  - `Gamepad` : ids GLFW ; sticks -1..1 (y vers le bas), zone morte radiale remise à l'échelle ; gâchettes 0..1.
  - Actions : `InputGamepadButton(bouton[, joueur])`, `InputGamepadAxis(axe, POSITIVE|NEGATIVE[, seuil, joueur])`, `InputSimple(bouton, EInputType.Controller)` ; sans joueur = `ANY_PLAYER`.
- **Valeur** : `InputManager.getValue(action)` 0..1 (1 pour touche/bouton/simulé, progressive pour `InputGamepadAxis` sans seuil ; `InputOr` = max, `InputAnd` = min). Déplacement : `getValue(droite) - getValue(gauche)`, longueur limitée à 1 (cf. `MovingCameraComponent`).
- **Axes** (`AxisInput(axe, IAxis)`, `inputManager.init(actions, axes)`, `getAxis(axe)`) : valeur signée non bornée, sens donné par la liaison (cf. `AxisId`).
  - Liaisons : `AxisGamepad(axe[, joueur])`, `AxisMouse(X|Y|SCROLL_X|SCROLL_Y)` (pixels de fenêtre pendant le tick, `MouseManager.deltaX/Y`, indépendant de la taille virtuelle), `AxisButtons(nég, pos)` (deux `IAction`, ou deux clés d'actions lues dans l'`InputManager` de la fenêtre, simulation comprise ; sans double comptage via `InputOr`), `AxisSum(...)`.
  - Réglages, dans l'ordre : `curve(exposant)` (signe gardé ; 2 = précis près du centre), `scale(facteur)` (négatif = inversion), `perSecond()` (× durée du tick : vitesse → déplacement). `scale` sur `AxisSum` = sensibilité commune : regard de la démo = `AxisSum(souris px, stick × 3000 px/s).scale(0.05 °/px)`.
- **Caméra 3D** : `Camera3D` ne lit pas les entrées (`rotate(dYaw, dPitch)` en degrés, droite et haut positifs, tangage ±89°). `FreeCamera3DComponent` (`addUpdatable`) la pilote par axes (déplacement -1..1 × `camera.getSpeed()`, regard en degrés, × `quickFactor` avec `QuickSpeed`) et met la vue à jour avant le code de la scène ; `setLookLocked` bloque le regard.
- **Caméra 2D pilotée** : `FreeCamera2DComponent` (`addUpdatable`) réunit `MovingCameraComponent` (actions de déplacement, plus vite avec l'action rapide, en pixels d'écran à tout zoom), `DraggingCameraComponent` (le monde suit la souris tant qu'une action est tenue) et `ZoomingCameraComponent` (la molette zoome autour de la souris) ; chaque partie n'est active que si ses actions sont données ; `isInteracting()` dit que le joueur l'a touchée (arrêt d'un parcours automatique). La démo la branche en une ligne : `DemoCamera.free(this)` dans le `launch` de chaque scène 2D (Z Q S D en AZERTY et flèches, Maj = vitesse double, clic droit glisser, molette ; `DemoCamera.free(this, ActionId.MIDDLE_CLICK)` quand la scène utilise le clic droit) ; une scène qui avait besoin de ces touches a reculé les siennes ; textes et interface fixes à l'écran : `setReferenceCamera` d'une copie de `camera2D()` prise au `launch`. Exclues : `TextFieldScene2D` (saisie), `GUIWidgetsScene` (interface), `PlatformerBox2D` (le joueur).
- **Texte et touches tapées** : `KeyboardManager.getTypedText()` (texte du tick, disposition et IME du système) et `getKeyEvents()` (touches appuyées ou répétées par le système, dans l'ordre, avec modificateurs `KeyEvent` ; touches simulées comprises) pour l'édition de texte. Les deux listes se remettent dans l'ordre par `KeyEvent.textBefore(longueur)` (caractères du texte du tick arrivés avant la touche ; touche simulée : après tout le texte, `AFTER_TEXT`) : la console et `TextField` insèrent ce texte puis appliquent la touche (« a », Retour arrière, « b » dans un tick donne « b »). `KeyEvent.letter()` est la lettre que la touche produit dans la disposition du système (`glfwGetKeyName(touche, scancode)` lu dans le callback, minuscule, `0` sans nom ; touches simulées : `glfwGetKeyName(touche, 0)`), demandée seulement quand Ctrl est enfoncé (`KeyEvent.NeedsLetter` : sous Wayland, `glfwGetKeyName` signale une erreur pour une touche sans caractère, touche morte…), `0` sinon : les raccourcis Ctrl+lettre comparent cette lettre, pas la position physique (Ctrl+A en AZERTY est la touche physique Q), et ignorent Ctrl+Alt (AltGr sous Windows, qui tape des caractères : AltGr+L = « ł » en polonais) ; les touches non imprimables (flèches, Début…) restent comparées par code.
- **Focus** (`InputManager.focus()`, `InputFocus`) : qui lit les entrées d'une fenêtre. Pile de détenteurs (objets quelconques), vide = la scène. Tant qu'elle n'est pas vide, la scène ne voit plus touches, texte, souris (curseur hors fenêtre, ni bouton, ni molette, ni mouvement), actions ni axes, **sauf les actions de l'espace `mightylib`** ; lu à chaque requête, donc immédiat. `request(détenteur)` empile (ou remonte) un détenteur, `release(détenteur)` le retire où qu'il soit : la console ouverte par-dessus un `TextField` rend le focus au champ en se fermant. Le sommet (`isCurrent`) lit les valeurs brutes (`getRawKeyEvents`, `getRawTypedText`, `getRawKeyState`, `getRawMouseScroll`, `MouseManager.getRawPos`/`getRawVirtualPos` (pixels de la fenêtre / coordonnées virtuelles), `getRawButton`, `rawButtonPressed`/`rawButtonReleased`, qui suivent la simulation de `input mouse`). **Pas de fuite d'appui** : un changement du sommet efface pour tous, jusqu'au tick suivant, les appuis et relâchements, le texte tapé et la molette du tick en cours (la touche qui rend le focus n'est pas un appui pour le détenteur suivant : Échap qui sort d'un champ ne quitte pas le menu) ; `releaseForClick` (clic ailleurs) garde l'appui de la souris pour la scène, qui reçoit le clic sur un autre composant. L'état des boutons de la souris est calculé à chaque tick quel que soit le focus (seules les lectures publiques le masquent) : un bouton tenu quand le focus est rendu ne compte pas comme un nouvel appui. Distinct du blocage modal (`setBlocked`), qui masque tout, actions du moteur comprises. Un détenteur doit rendre son focus en quittant la scène (`TextField.unload` le fait).

## Commandes
- **Registre** (`utils/enginecommand/Commands`, `Engine.commands()`) : un par `Engine`, créé dans `Engine.setup` avec les commandes générales (`ListGeneralCommand`) ; le `SceneManager` du contexte principal traite les commandes en attente à chaque tick (`updateMain` → `processPendingCommands`). Les commandes générales visent la fenêtre `Engine.targetWindow()` (et son contexte) : celle choisie par `window` (`Engine.commandWindow()`) pour une commande venue de la console, de l'entrée standard, du serveur de debug ou de `submit` ; celle de la vue courante (`Views.current().context()`) quand le code d'une vue appelle `Commands.execute(ligne)` ou `complete(début)` hors d'une commande (`Commands.getCallerWindow()`, rétablie ensuite ; une commande lancée par une autre garde la cible). Les commandes lisent leur cible par `targetWindow()`/`targetContext()`/`ListGeneralCommand.targetScenes()`, jamais par `commandWindow()` (réservé à `window`/`windows`). Appelé depuis le code, `execute` a la source `api` (niveau `DEV`) : il marche aussi quand le build n'a aucun accès aux commandes (`setMaxCommandAccess(null)` borne le niveau de la session, pas les appels du code).
- **Syntaxe déclarée** (`utils/enginecommand/syntax`) : chaque commande déclare son arbre dans `BaseCommand.syntax(CommandNode)` (littéraux, arguments typés `ArgumentType`, options `Option`, handler par branche, description, niveau et condition par nœud ou option). `Commands.executeNow` trouve la commande (nom ou identifiant), vérifie son niveau, puis `BaseCommand.run` appelle `CommandParser.parse` sous le propriétaire : littéraux avant arguments, options `--nom valeur`/`--nom=valeur`/drapeaux valables dans le sous-arbre du nœud qui les déclare, `--` termine les options ; une branche ou option hors niveau, ou dont la condition silencieuse est fausse, donne l'erreur d'un mot inconnu ; sinon l'erreur est précise (« Expected an integer between 1 and 100 for <count>, got ->abc<- ») suivie de l'usage de la branche atteinte. Le handler reçoit un `CommandContext` de valeurs typées et renvoie un `CommandResult`. Le même arbre produit la complétion (`CommandParser.complete`, appelée par `Commands.completeNow`), l'aide (`CommandHelp` : usage par branche, arguments, options, descriptions) et son JSON ; `--help` est une option ajoutée à toute commande. Un schéma incohérent est refusé à l'enregistrement. `resources/internal/ResourceArguments` fournit la sélection de ressources aux commandes qui en prennent. `as` et `complete` (`DEV`) exécutent une ligne ou complètent un début de ligne avec un niveau abaissé.
- **Propriétaires** (`CommandOwner`) : un plugin (`CommandOwner.Plugin(espace)`, égal par espace, `help` montre « plugin demo » ; le moteur est `ENGINE`, espace `mightylib`), ou une vue (`CommandOwner.Of(vue, "scene"|"window")`, égal par identité de la vue). `register(commande, propriétaire)`, `registryFor(propriétaire)` (interface étroite `CommandRegistry`), `removeOwnedBy(propriétaire)` ; une commande n'est enregistrée qu'à un endroit à la fois (retirée, elle peut l'être à nouveau : scène réutilisée). Plugins (moteur compris) : `registry.commands().register(commande)` dans `IPlugin.register`, identifiant de l'espace du plugin ; `setup` les enregistre chacune à son plugin puis `Commands.freezePluginCommands()` : ensuite seules les vues ajoutent des commandes (gardées tout le programme). Une commande générale qui a besoin de `Commands` le lit par `BaseCommand.commands()` (son enregistrement), pour être créée avant l'`Engine`. Scène : `Scene.addCommand` (dans `init` : la commande existe pendant le chargement), retirées par `Scene.unloadByManager` à côté de `closeWindowsOpenedBy`, donc même si la scène est quittée pendant son chargement ; `WindowView.addCommand`, retirées dans `unloadByContext`.
- **Exécution sous le propriétaire** : la commande d'une vue (et sa complétion) s'exécute sous cette vue (`Views.enter`) avec le contexte GL de sa fenêtre, rétabli ensuite : elle crée des objets comme le code de la scène. Une commande de scène déclare l'état dont elle dépend : `Scene.isLaunched()`, `requires(CommandCondition.launched(scène))` sur sa racine → « Scene still loading » (`camera` fait de même). Une `CommandException` devient la réponse d'erreur, sans « Command X failed ».
- **Identifiants** (`BaseCommand(Identifier, ECommandLevel, description)`, `registry/Identifier`) : générales dans `mightylib`. Résolution comme les actions : identifiant complet ou chemin seul sans casse s'il est unique parmi les commandes **visibles** ; nom ambigu refusé avec la liste des identifiants visibles ; identifiant déjà pris → `IllegalArgumentException`, sauf entre deux vues différentes (même scène ou `WindowView` dans deux fenêtres) : la vue visée l'exécute (`Commands.setViewChooser`, branché par l'`Engine` : vue de `commandWindow()`, sinon la seule de son contexte), sans vue visée la commande est refusée en demandant `window`. Complétion : chemins, plus les identifiants des chemins partagés (tous une fois `espace:` tapé).
- **Niveaux** (`ECommandLevel` : `USER` < `CHEAT` < `DEV`, chacun inclut les précédents ; pas une sécurité) : obligatoire dans le constructeur. `USER` : `help`, `console` (sauf `log`/`follow`), `screenshot` (dossier par défaut seulement), `stats fps`, `cheats` ; `CHEAT` : commandes de triche du jeu ; `DEV` : le reste. Une commande au-dessus du niveau de la source n'existe pas pour elle : absente de `help`, de `help <nom>` et de la complétion, refusée avec **exactement** le message d'une commande inconnue, ignorée par la résolution et l'ambiguïté. Branche ou option : `.level(niveau)` (même refus, absente de la complétion, de l'aide et du JSON), `CommandContext.currentLevel()` pour adapter la réponse.
- **Sources** (`ICommandSource.name()`, `level()`) : console en jeu `game` (niveau de la session, relu à chaque commande), `stdin` et `server#N` (`DEV`, n'existent qu'en debug), `api` (`DEV`, défaut, appel direct). `Commands.getCurrentLevel()` ; `execute(ligne, source)` et `complete(début, source)` s'exécutent comme la source. Scripts (`CommandScript`) : la source de `exec` est capturée et rétablie pour chaque ligne, différées comprises.
- **Accès** : `EngineConfig.setCommandAccess(niveau|null)` (niveau de la session au départ ; `null` : aucun, pas de console ; défaut `DEV` en debug, aucun en release), `setMaxCommandAccess` (plafond du build, défaut `DEV` en debug, `USER` en release ; `null` : aucun accès, jamais, l'option de lancement est ignorée avec une ligne au journal), `-Dmightylib.commands.access=none|user|cheat|dev` (mode développeur d'un jeu publié, borné par le plafond). `Commands.setSessionLevel(niveau)` (le jeu active la triche par ses propres moyens) est borné par le plafond. `EngineConfig.setCheatCommand(true)` enregistre `cheats on|off` (`USER`, bascule `USER`/`CHEAT`, sans effet en `DEV`) si le plafond permet `CHEAT`. Le moteur n'impose aucune règle de sauvegarde.
- Démo : `demo:menu` (jeu, `USER`), `CommandsScene2D` et `demo:spawn` (scène, `CHEAT` : `spawn <nombre 1..100> [--color] [--size] [--at x y] [--shape]`, `spawn clear`, `spawn list` en `DEV`, condition `launched`), `cheats` activée ; options `-Ddemo.release=true` (release, accès `USER`, plafond `CHEAT`) et `-Ddemo.commands.max=none|user|cheat|dev`.
- Tests : `CommandsTest`, `CommandLevelsTest`, `CommandScriptTest`, `main/CommandAccessTest`, `syntax/CommandParserTest`, `syntax/CommandHelpTest`, `resources/ResourceSelectionTest` (sélection et `ResourceArguments`).

## Console
- **`Console`** (`console/`, service `mightylib:console`, contrat `IConsoleService`, `Engine.console()`, `null` sans accès aux commandes) : moteur, indépendante des scènes. Existe quand `EngineConfig.getCommandAccess()` n'est pas `null` (voir **Commandes**) ; `setConsoleFont` (défaut `EngineResources.CONSOLE_FONT` = `engineMono`, à chasse fixe, à charger au démarrage, sinon police de repli), `setConsoleLogCapacity` (5000 lignes). `print(texte[, niveau])` : message du jeu au joueur (`MESSAGE`, `USER` par défaut).
- **Touches** : `²` (`TOGGLE_CONSOLE`) ouvre et ferme à tout niveau ; un jeu la relie comme toute action (plusieurs touches avec `InputOr`).
- **Modes** : `CLOSED` ; `OVERLAY` (`²`, ou `console open`) : bande en bas de la fenêtre principale (45 % de la hauteur, fond noir à 55 %), dessinée en pixels réels après la scène (`Context.displayWindows`/`redrawWindow` → `Engine.displayOverlays`, couche 1000, au-dessus des autres overlays), y compris pendant un chargement ; la console prend le focus de la fenêtre principale (curseur montré, rendu à la fermeture). Échap ou la touche d'ouverture ferment ; le focus est rendu aussitôt, la touche qui ferme n'est pas vue par la scène (voir **Focus**). `DETACHED` (F2 console ouverte, `console detach`) : sous-fenêtre « Console » (`ConsoleWindowView`, persistante, ouverte sous la vue `Engine`, sans les entrées du projet), fond noir et texte blanc ; F2 dans cette fenêtre la refusionne (overlay ouvert, focus rendu), sa fermeture ferme la console ; la touche d'ouverture dans la principale lui donne le focus.
- **Tick** : `Console.update()` (phase `update` des services) au début d'`Engine.update`, avant les scènes : lit les entrées brutes de la fenêtre de la console (`ConsoleInput` : texte, ←/→, Ctrl+←/→, Début/Fin, Retour arrière/Suppr, Ctrl+Retour arrière (mot), Maj+←/→/Début/Fin et Ctrl+Maj+←/→ étendent la sélection de la saisie, Ctrl+A/C/X/V (voir **Sélection**), ↑/↓ historique avec brouillon, Entrée, PageHaut/PageBas, Maj+↑/↓ (une rangée), Ctrl+Début/Fin (plus ancienne ligne / fin), molette, souris (voir **Souris**), Ctrl+L vide la console (voir `clear(niveau)` dans **Journal**), Tab style bash : partie commune, puis liste des choix au second Tab ; la même liste n'est pas réécrite tant que rien n'a été écrit après elle (`CompletionListing`) : la ligne de saisie s'éclaire 150 ms à la place, comme un bip visuel) ; une ligne validée part par `Commands.submit(ligne, game)` et s'exécute dans le même tick ; la complétion se fait au niveau de la session.
- **Journal** (`ConsoleLog`, `Engine.consoleLog()`, présent si console ou mode debug) : anneau thread-safe de lignes `{id croissant, type OUT|ERR|COMMAND|RESULT|ERROR|DATA|MESSAGE, source, texte, niveau minimal pour la voir}`, `version()`, `version(niveau, types cachés)` (ne change qu'avec ce que ce niveau voit : le panneau ne se refait pas pour une ligne cachée), `last(n)`, `last(n, niveau)` (lignes visibles, sans celles effacées pour ce niveau), `upTo(id, n, niveau, filtre)`, `after(id, n, niveau, filtre)`, `between(de, à, niveau, filtre)` (lecture par id), `since(id)`, écouteurs ; `clear()` oublie tout, `clear(niveau)` (Ctrl+L, `console clear`) en `DEV` aussi, en dessous seulement pour ce niveau et ceux du dessous (le développeur garde le journal : `console log`, serveur de debug). Niveaux : sortie du programme (`OUT`/`ERR`) `DEV` ; commande et `message` de la réponse au niveau de la source quand la commande s'exécute (le même pour les deux, même si elle change ce niveau : `cheats off`) ; `data` (JSON indenté, type `DATA`) `DEV` ; autres lignes `USER` par défaut. `LogCapture` remplace `System.out`/`err` dès `Engine.setup` par des flux qui écrivent dans les vrais et donnent chaque ligne complète au journal (retiré à la fin de `shutdown`) ; `rawOut()`/`rawErr()` écrivent sans copie (réponses de l'entrée standard, déjà au journal). `CommandEcho` y écrit chaque commande soumise (`[source] > ligne`) et son résultat, quelle que soit la source (jeu, stdin, client du serveur), au niveau de la source, ou à son niveau d'après quand la commande l'a baissé (`cheats off` reste visible du joueur repassé `USER`). Le serveur de debug (`DEV`) voit tout.
- **Mise en page et défilement** (`ConsoleLayout`, sans GL : la largeur des caractères est injectée, `charAdvance` du `Text` en jeu) : coupe les lignes à la largeur (une rangée = un morceau, au moins un caractère), choisit les rangées visibles et convertit un point du panneau en position du journal et inversement. Le défilement est **ancré sur une ligne du journal** : `null` = suit la fin, sinon `Anchor(id de la ligne du bas, rangées de cette ligne cachées en dessous)` ; les nouvelles lignes ne déplacent donc pas une vue remontée. Une ligne d'ancre cachée par le filtre : la vue se cale sur la ligne visible précédente, l'ancre ne change pas ; ligne oubliée par l'anneau : la plus ancienne gardée ; journal vidé : la fin. Chaque panneau (overlay, fenêtre détachée) a sa mise en page et son ancre. Le travail ne dépend que de ce qui est affiché, pas de la taille du journal (`ConsoleLog.upTo`/`after`/`between`, recherche dichotomique). Entrée et validation ramènent à la fin.
- **Indicateur** : quand la vue n'est pas en bas, « v N lines » (N = lignes visibles sous la vue, filtre et niveau appliqués, une ligne coupée par le bas de la vue compte pour une, « 999+ » au-delà ; la police n'a pas de flèche) est dessiné sur la droite de la dernière rangée ; un clic dessus ramène à la fin. Le compte est refait seulement quand le journal ou l'ancre changent.
- **Filtre** : la console (pas le journal) garde un ensemble de types cachés, partagé par l'overlay et la fenêtre détachée ; `console logs off|on` (`DEV`) cache ou montre `OUT`/`ERR`, état initial `EngineConfig.setConsoleLogsShown` ou `-Dmightylib.console.logs=shown|hidden` ; `console data on|off` (`DEV`) montre ou cache `DATA` (cachées au départ : la console ne montre que les messages lisibles ; le serveur de debug reçoit les `data` dans ses réponses), état initial `EngineConfig.setConsoleDataShown` ou `-Dmightylib.console.data=shown|hidden`. Le panneau ne se refait pas pour une ligne cachée par le filtre (`ConsoleLog.version(niveau, types cachés)`).
- **Sélection** : une seule à la fois, dans la saisie (`CommandLineEditor` : ancre, `selectionStart/End`) ou dans le journal (`LogSelection` : bornes `LogPosition(id de ligne, caractère du texte affiché)`, tabulations = 4 espaces). Ctrl+A : la saisie, puis (2e appui, ou saisie vide) tout le journal visible ; Ctrl+C copie la sélection (rien sans sélection), Ctrl+X coupe dans la saisie et copie dans le journal ; ←/→ sans Maj sur une sélection de la saisie vont à son début/fin ; taper, coller, effacer ou valider efface la sélection du journal. Copie du journal = le texte affiché, lignes d'origine jointes par un saut de ligne sans les coupures dues à la largeur, lignes cachées (filtre, niveau) non copiées (`LogSelection.CopyText`, aussi pour `console copy`). Ctrl+V de plusieurs lignes : une commande par ligne complète (au niveau de la session), la dernière reste dans la saisie. Presse-papiers par `ConsoleInput.IClipboard` (`SystemInfo` de la fenêtre).
- **Souris** (`ConsoleInput.handleMouse`, état du bouton gauche en coordonnées du panneau) : clic dans la saisie place le curseur, glisser sélectionne, Maj+clic étend ; dans le journal, glisser sélectionne ; double clic = un mot (séparateurs de Ctrl+←/→), triple clic = la ligne (du journal, pas la rangée) ; glisser après un double ou triple clic garde le mot ou la ligne ; glisser au-dessus ou au-dessous du journal le fait défiler d'une rangée toutes les 50 ms. Nombre de clics par `inputs/text/ClickCounter` (4 px, 500 ms, partagé avec `TextField`). Un appui au-dessus de l'overlay (sur le jeu) n'est pas pour la console.
- **Rendu** (`ConsolePanel`, sous une `ConsoleView` : vue à caméra 2D en pixels réels de la fenêtre, `Text` exigeant une caméra) : ne fait que dessiner ce que donne `ConsoleLayout` ; seules les lignes visibles au niveau de la session ; un `Text` par rangée visible (couleur par type, `ConsoleColors`), refaits seulement si le journal, le défilement ou la taille changent : le panneau compare `ConsoleLayout.buildCount()` au compte de son dernier dessin (une lecture qui recalcule, souris ou défilement, ne cache donc pas un calcul au panneau) ; mesure linéaire `Text.measureWidth`/`charAdvance`, pas `fitText`. Surlignage de la sélection : un rectangle par rangée sélectionnée, d'une réserve réutilisée d'une image à l'autre, libérée dans `unload` (les rangées qui finissent une ligne sélectionnée ont 4 px de plus pour qu'une ligne vide se voie). Ligne de saisie défilée horizontalement autour du curseur, sélection dessinée derrière le texte.
- **Couleurs** (`ConsoleColors`, en attendant un thème) : `OUT` gris terne, `ERR` orange terne, `COMMAND` jaune, `RESULT` blanc, `ERROR` rouge vif, `DATA` gris bleuté, `MESSAGE` cyan clair ; sélection bleue translucide.
- **Démo** : `ConsoleFeedScene` écrit une ligne de chaque type à intervalle réglable (↑/↓), pour essayer l'ancre, le filtre, la sélection et l'indicateur pendant que le journal avance. Objets de l'overlay créés à la première ouverture, libérés par `Console.unload` à l'arrêt ; ceux de la fenêtre à sa fermeture.

## API publique
- **Statut de stabilité** par l'annotation `@API` d'apiguardian (`org.apiguardian:apiguardian-api`, rétention `RUNTIME`), posé par le `package-info.java` de chaque package de `mightylib` ; un type ou un membre ne s'annote que s'il est moins stable que ce qui l'entoure. `STABLE` = promis pour la 1.0 (changements cassants encore permis avant) ; `EXPERIMENTAL` = utilisable, contrat susceptible de changer (3D : `graphics.lighting`, `graphics.renderer._3D`, `resources.models`, `resources.cubemap` ; `network`, `physics`, `physics.collision`, `algorithms`, `graphics.debug`, `utils.valueDebug`, `inputs.keyboardlanguage`, `resources.sound.decoder`, `resources.source`, `console`) ; `INTERNAL` = public seulement pour un autre package de la bibliothèque, à ne pas utiliser. Les autres packages sont `STABLE`.
- **Packages `internal`** : un package est `INTERNAL` si et seulement si son nom finit par `.internal` (à côté de son propriétaire : `console.internal`, `graphics.internal`, `inputs.internal`, `main.internal`, `resources.internal`, `utils.enginecommand.internal` (commandes générales, `DebugServer`), `physics.tweenings.internal`) ; aucun type `INTERNAL` dans un autre package. Seuls des **membres** de types exportés restent `INTERNAL`, ceux qui exposent un type interne ou servent un package interne : `Engine.consoleLog`, `IConsoleService.getLog`, constructeur de `Console`, `Window.getGLContext`/`createNewWindow`, `GLResources.shared`, `Resources.setGLElementSink`/`loaders`, les `Delete…(GLContext, …)` de `GenDeleteResources`, et `Icon.getBuffer`/`SoundDataType.readVorbis` (types LWJGL, non transitifs) ; `GLResources`, `CubeMapPlaceholders` et `TexturePlaceholders` implémentent une interface interne (accepté, alerte `-Xlint:exports` coupée dans le pom ; la liste se contrôle en compilant une fois avec `-Xlint:exports` ; les retirer : `later.md`).
- **`module-info` de `mightylib`** : `exports` de tous les packages sauf les `internal` (non qualifiés) ; `requires transitive` de ce que l'API publique expose (`java.desktop`, `org.joml`, `org.json`, `jbox2d.library` : `physics.B2Utils`) ; `requires static org.apiguardian.api` (annotations seulement, non transitif : un jeu compile sans) ; `requires jdk.jfr` (événements JFR, dans `main.internal`), `jdk.zipfs` (fournisseur des systèmes de fichiers des jars, cherché à l'exécution seulement : nommé pour qu'une image `jlink` le contienne), modules LWJGL, et trois **modules automatiques** nommés d'après leur jar (`jbox2d.library`, `jlayer`, `opensimplex` ; alerte `-Xlint:requires-automatic` coupée). **Aucun `opens`** : `ClasspathSource` cherche le dossier `assets/<espace>` (paquet `assets`, qui n'est celui d'aucun module tant qu'aucun fichier n'est posé directement dans `assets/`, donc non encapsulé ; repli sur `assets/<espace>/`, paquet sans nom), puis le lit comme chemin (dossier ou système de fichiers du jar), jamais par le module : un module de jeu n'ouvre rien non plus pour ses ressources. Le `module-info` de la démo ne fait que des `requires` (bibliothèque, `org.lwjgl.glfw`, `org.lwjgl.openal`).
- **`final` par défaut** : toute classe publique concrète est `final`, sauf les classes extensibles et celles que la bibliothèque étend elle-même (liste `EXTENDED_BY_THE_LIBRARY` : `Shader`, `ShaderData`, `CubeMapData`, `Model`, `AnimationData`, `SoundData`, `JSONFile` (leurs replis), `CommandException`, `MouseManager` (souris des tests), `RectangleRenderer`, `Camera2D`, `BasicPhongMaterial`, `NodeContainer`, `UUID` ; pas des accroches). Les classes abstraites hors des classes extensibles ont un constructeur package-private (hiérarchie fermée : `Camera`, `Collision2D`, `AxisBinding`, `ListNode`, `PositionListNode`, `ServerThread`, `Resources.LoadingMethod`) ; les utilitaires statiques sont `final` à constructeur privé.
- **Classes extensibles** (liste unique `mightylib/src/test/java/…/ExtensibleClasses.NAMES`), chacune avec ses accroches documentées (Javadoc courte : quand, quoi faire, quoi appeler), le reste `final`, aucun champ `protected` :
  - scènes et vues : `Scene` (`getInvolvedBatch`, `createLoadingScene`, `createVirtualSceneBindable`, `init`, `launch`, `update`, `postUpdate`, `display`, `unload`, `release` ; état par `context()`, `resources()`, `glResources()`, `camera2D()`, `camera3D()`, `sceneManager()`, `args()` (copie)), `WindowView` (mêmes accroches sans chargement), `TemplateSceneLoading` ;
  - rendu : `Mesh` (`draw`, `unload`), `Renderer` (`draw`, `updateShader`, `applyRenderState`, `display`, `unload`, et les modificateurs qu'une sous-classe suit : `setPosition`, `setRotationZ`, `position`, `setColorMode`, `setNoColorNoTextureMode`, `setFaceCulling`), `MeshRenderer`, `Shape2DRenderer` (`getIndices`, redemandé après `updateShapeIndices`, `calculatePosition`, `calculateTexturePosition`, `setSizePix(l, h)`, `setPosition(Vector2f)`, `setReferenceDirection`), `VectorShape2DRenderer` (`writeShapeParameters`, `extraMargin`, `updateShader`) ;
  - ressources : `DataType` (`internLoad`, `internUnload`, `internCancelPreload`, élément GL, estimations mémoire, rechargement : `createReloadCopy`, `swapContent`, `reloadFailed`), `SingleSourceDataType` (`path()`), `MultiSourceDataType`, `ResourceLoader` (`getType`, `getResourceNameType`, `create`, `discover`, `createFallback`, `filterFile`, `fileDetected`, `initWithFile`), `TextureData` (`internLoad`, `loadBufferedImage`, `setSize`), `GLElement` (`load`, `reload`, `unload`), `Texture` (`fallbackDataType`, `getWidth`, `getHeight`, `load`, `reload`, `unload`) ;
  - commandes et GUI : `BaseCommand` (`syntax`), `GUI` (`GUIMouseSelected`, `mouseDisableIt`, `display`, `unload` ; caméra par `referenceCamera()`), `Slider` (placement et valeur du bouton, appelés en partie par le constructeur), `ValueSelector` (`nameOf`) ;
  - ouvertes, `EXPERIMENTAL` : `KeyboardLanguage` (`keyboardConfigurationName`, `addInputEntry`), `Tweening` (`update` avec `updateBase`, `value`, `goalValue`, `initTwoValue`, `initRangeValue`).
- **Tests de garde** : `ApiStatusTest` (tout package classé ; aucune annotation plus stable que son type ou son package ; package nommé `internal` ⇔ `INTERNAL` ; aucun type `INTERNAL` dans un package exporté) ; `ModuleDescriptorTest` (lit `module-info.class` : nom, `exports` = packages non `INTERNAL`, aucun `opens`, apiguardian `static`, liste des `requires transitive`). La frontière est ensuite tenue par le compilateur : un module qui lit la bibliothèque (la démo) ne compile pas s'il nomme un type d'un package `internal` ; les membres `INTERNAL` de types exportés restent accessibles (non détectés); `ExtensionFieldsTest` (aucun champ `protected` dans une classe des deux listes ; toute classe publique concrète hors des deux listes est `final` ; les classes listées existent et sont ouvertes).

## Pièges connus (non corrigés)
- Sous Wayland, une sous-fenêtre n'est liée à son parent ni par la position ni par l'empilement (GLFW n'expose pas `xdg_toplevel.set_parent`) : un dialogue peut passer derrière la fenêtre principale ; `BORDERLESS` ne choisit pas son écran.
- Une `TileMap` relue perd les changements faits par le code (`setTileType`).
- **Boîte d'un texte** (`leftUpPosition()`, `size()`) recalculée à chaque changement de texte, de taille, de référence, de padding ou de position.
- **Padding du texte** : `Text.setPadding(gauche, haut, droite, bas)` écarte le texte des bords de son rectangle, qui l'inclut : `size()`, `leftUpPosition()`, la référence (`setReference`) et la position portent sur le rectangle avec padding, l'alignement des lignes sur la largeur du texte seul. Scène : `TextPaddingScene`.
- `Mesh.updateVbo` réutilise le buffer à taille égale (`glBufferSubData`), sinon réalloue ; les `calculate*()` allouent un `float[]` à chaque appel.
- `TileMapRenderer` : une animation de tuile ne réécrit que ses UV, mais toute modification de carte (`hasBeenUpdated()`) reconstruit tout.
- `Shape2DRenderer` alloue en `STATIC_STORE` même pour des VBO modifiés.

# Architecture

## Structure
```
src/io/github/mightycode/
  mightylib/       # bibliothèque (ne dépend PAS de mightylibdemo/)
    main/          # MainLoop (la boucle), Engine (services partagés, démarrage, arrêt), Context (scène + fenêtres), WindowContext (une fenêtre + ses entrées), WindowView, WindowConfig, DisplaySettings/EWindowMode (affichage d'une fenêtre), IView/Views (vue courante), Window, ContextManager, MainThread, Workers, GameTime
    scenes/        # Scene, SceneManager, SceneManagerInterface, TemplateSceneLoading, caméras 2D/3D
    resources/     # Resources (pipeline, une instance par Engine), DataType, ResourceLoader, batchs
    graphics/      # GLResources, GLElement, renderer/ (Shape, Renderer, _2D, _3D), shader/, text/, GUI/, lightning/
    inputs/        # InputManager (actions), KeyboardManager, MouseManager, dispositions clavier
    sounds/        # SoundManager (OpenAL, une instance par Engine), arbre de gains
    physics/       # collisions maison, tweenings, B2Utils (JBox2D)
    algorithms/    # A*, Dijkstra, graphes, Wave Function Collapse
    utils/         # commandes, JSON, maths, Logger
  mightylibdemo/   # démo : Main, ProjectLoading, ActionId, scènes de démo
resources/         # assets ; batchs/*.batch = groupes de ressources
```

## Démarrage
`Main` remplit un `EngineConfig` (setters enchaînables, seule la scène de départ est obligatoire) → `MainLoop.run(config)` crée l'`Engine`, l'installe comme vue courante et appelle `Engine.setup` : GLFW → contexte `"Main"` (fenêtre principale + entrées) → `ShaderManager.init` → `Resources` → `GLResources` → son (`SoundManager`) → `SceneManager` → `IProjectLoading.init` (loaders projet) → `contextLoading(fenêtre)` (liaisons d'entrées, appelé de même pour chaque fenêtre ouverte ensuite) → `resources.init()` + `load()` (bloquant) → première scène. `MainLoop.run` fait ensuite la boucle, puis `Engine.shutdown` libère tout.

## Boucle (`MainLoop.run`)
Pas fixe découplé : chaque itération fait **soit** un tick (`Engine.update` : `update` de chaque contexte et de ses sous-fenêtres, son, entrées de toutes les fenêtres, puis `postUpdate`), **soit** une frame (`Engine.displayWindows` : chaque fenêtre est activée (`makeCurrent`) et affiche sa vue, puis `Engine.swapWindows` : `swapBuffers` de chacune, un seul `glfwPollEvents`, fermetures). Ticks en retard abandonnés, sans rattrapage (sous charge le jeu ralentit, le temps de jeu dérive du temps réel). Après les affichages, la frame (contexte GL de la fenêtre principale) traite dans l'ordre `Resources.processUntil`, `MainThread.process` et `GLResources.process` avec le reste de la frame (budget : voir « Ressources CPU »). Arrêt : fenêtre qui `closesEngine` fermée (la principale du contexte principal par défaut) ou `sceneManagerInterface.exit(status)` du contexte principal (fin du tick). `run` libère tout et **renvoie** le code (`ListError`) sans `System.exit` (`Main` fait `System.exit(MainLoop.run(config))`).

## Temps
`GameTime.DeltaTime()` : temps réel entre deux ticks (variable). `FixedDeltaTime()` : 1/TPS, **pour la physique**.

## Threads
- **Principal** (`MainThread`) : seul à avoir le contexte GL. Y revenir par `MainThread.execute`/`run`/`supply` (→ `CompletableFuture`, la tâche garde la vue courante de celui qui la poste) ou `thenAcceptAsync(…, MainThread.EXECUTOR)`. File vidée après chaque `display()` dans le reste de la frame (au moins une tâche), après `Resources.processUntil` et avant `GLResources.process`, puis entièrement à la sortie.
- **`Workers`** : pool de `EngineConfig.maxThreads` (`MightyLibrary-Worker-N`, daemon) pour I/O et calcul courts (`Workers.run`/`supply`), **sans GL**. Les étapes `THREAD_CONTEXT` de `Resources` y tournent.
- Boucles longues/bloquantes (réseau, `DebugServer`, console, encodage de `Screenshot`) : threads dédiés `MightyLibrary-…`, daemon.
- Avec `Logger.DO_CHECK`, `GenDeleteResources` lève une exception si un objet GL est créé/détruit hors du thread principal.

## Moteur et vue courante
- **`Engine`** (`main/`) : les services partagés, une instance par processus (GLFW et le périphérique son l'imposent), créée et pilotée par `MainLoop` : `resources()`, `glResources()`, `shaderManager()`, `soundManager()`, `contexts()` (fenêtres et entrées), `sceneManager()`, `config()`. Plus aucun singleton : `Resources`, `GLResources`, `ShaderManager`, `SoundManager`, `ContextManager` s'obtiennent par lui.
- **Vue** (`IView` : `engine()`, `context()`, `camera2D()`, `camera3D()`) : ce pour quoi le code s'exécute. `Scene` est une vue (caméras créées au `launch`) ; l'`Engine` l'est aussi hors de toute scène (démarrage, commandes, chargement), sans caméra.
- **Vue courante** (`Views.current()`, `Views.engine()`) : posée par le moteur autour de tout le code d'une vue (`Scene.initByManager`/`launchByManager`/`updateByManager`/`postUpdateByManager`/`displayByManager`/`unloadByManager`, `MainLoop.run`) par `try (Views.Scope s = Views.enter(vue))`. `MainThread.execute` la capture à la soumission et la rétablit à l'exécution. Sans vue courante (worker, avant `run`) : `IllegalStateException` explicite, jamais de repli sur une autre fenêtre.
- Ce qui est créé sans paramètre explicite appartient à la vue courante : `Renderer`/`Shape` (`resources`, `glResources`, caméras par défaut), `Text`, `Animation`, `Texture(String)`, `GUI()`, `ScrollList`, `Scene` (engine et contexte du créateur). Les objets déjà liés à un propriétaire le rendent : `DataType.resources()`, `ResourceLoader.resources()`, `GLElement.glResources()` ; une donnée construite par le code avant d'être ajoutée utilise `resourcesOrCurrent()`.
- Commandes : exécutées sur le thread principal sous la vue de l'`Engine`, elles prennent leurs services par `Views.engine()`.
- Gardés statiques, par nature de processus : `MainThread`, `Workers`, `GameTime`, `Logger.DO_CHECK`, `MainLoop.getMode()`, `EngineStats`, `GenDeleteResources`, `Screenshot`, `TextureUploader`.

## Contextes et fenêtres
- **`Context`** = une scène (son `SceneManager`, ses changements de scène, son écran de chargement) et les fenêtres qui la montrent ; **`WindowContext`** = une fenêtre avec son `GLContext`, ses entrées (`InputManager`, `KeyboardManager`, `MouseManager`) et son presse-papiers. Un `Engine` a un contexte principal (`EngineConfig` : fermer sa fenêtre principale arrête le moteur) et autant d'autres que voulu (`Engine.openContext(nom, WindowConfig, Supplier<Scene>)` : la scène est créée avec le contexte pour vue ; fermer sa fenêtre principale, ou son `exit`, ne ferme que lui, et décharge les batchs de sa scène). Les ressources sont communes à tous.
- **Affichage** : `DisplaySettings` = le mode (`EWindowMode` : `WINDOWED`, `FULLSCREEN` exclusif, `BORDERLESS` = fenêtre sans bordure couvrant son écran à sa résolution) et les réglages fins de chaque mode, chacun avec sa valeur par défaut et ignoré hors de son mode (donc aucun ordre d'appel, et changer de mode n'en perd aucun) : écran (tous ; non donné : celui du parent, sinon celui de la fenêtre principale, elle-même sur l'écran de `EngineConfig.setMonitorSelector`), taille fenêtrée (1280x720), bordure, redimensionnable (fenêtré), résolution (celle de l'écran), fréquence (celle de l'écran) et réduction à la perte du focus (plein écran). Raccourcis : `setWindowMode`, `setSize`/`setWindowSize` (taille fenêtrée), `setMonitor` sur `WindowConfig`/`EngineConfig`. Configs et fenêtres gardent leur copie. En cours de jeu : `WindowContext.setDisplay(...)`/`setWindowMode(...)`, appliqués aussitôt par `glfwSetWindowMonitor` et les attributs GLFW (la fenêtre, son contexte GL et ses callbacks restent ; la taille virtuelle ne change pas) ; une fenêtre réduite est d'abord restaurée, puis placée au frame suivant (le système lui rend sinon son ancien emplacement) ; la position fenêtrée est retenue pour y revenir. Un écran n'a qu'une fenêtre en plein écran exclusif : une deuxième passe en sans bordure (message `--`). `WindowInfo.size` suit la taille réelle (callback de framebuffer, relu à chaque fois) ; pendant la lecture des événements, le callback de rafraîchissement redessine la fenêtre (`Context.redrawWindow` : affichage de sa scène ou vue puis swap), car sous Windows la boucle attend dans `glfwPollEvents` tant qu'un bord est tiré : l'image suit le redimensionnement, les ticks attendent le relâchement ; `getWindowMode()` donne le mode appliqué. `MonitorInfo.getVideoModes()` : résolutions et fréquences de l'écran. Démo : `DisplayModesScene` (F1/F2/F3 modes, B bordure, Z redimensionnable, L résolution 1280x720, W seconde fenêtre ; touches lues dans la fenêtre qui a le focus).
- **Sous-fenêtres** : `Context.openWindow(WindowConfig, WindowView, args…)` (`Scene.openWindow`), depuis le code d'une scène ou d'une vue. `WindowView` = petite scène sans changement de scène ni écran de chargement (`launch`, `update`, `postUpdate`, `display`, `unload`, caméras, surface virtuelle, `close()`) ; ses ressources doivent déjà être chargées (batchs de la scène qui l'ouvre). `WindowConfig` : titre, affichage (`DisplaySettings`, voir **Affichage**), taille virtuelle (non donnée : la taille de la fenêtre à sa création), disposition clavier, parent (défaut : fenêtre principale), `modal`, `persistent`, `closesEngine`, `projectInputs`.
- **Arbre des fenêtres** (`WindowTree`, sans GLFW, testé par `WindowTreeTest`) : fermer une fenêtre ferme d'abord ses enfants ; un parent est **bloqué** tant qu'un descendant modal est ouvert (`InputManager.setBlocked` : plus de touche, de bouton, de molette, de texte, d'action ni d'axe, curseur hors fenêtre ; les manettes ne sont pas concernées) ; une fenêtre appartient à la scène (ou vue) qui l'a ouverte, qui la ferme à son `unload` sauf `persistent`. Fenêtre fermée par l'utilisateur ou par `WindowContext.requestClose()` : traitée à la fin de la frame.
- **Natif** : une sous-fenêtre est centrée sur son parent et, sous Windows, a le parent pour propriétaire (`NativeWindowOwner` : `GLFWNativeWin32` + `User32.SetWindowLongPtr(GWL_HWNDPARENT)` : au-dessus du parent, masquée avec lui, sans entrée dans la barre des tâches) ; ailleurs, simple `GLFW_FLOATING`.
- **Plateforme GLFW** (`WindowPlatform`, journal `--GLFW platform : …`) : GLFW choisit (Wayland dans une session Wayland), `-Dmightylib.glfw.platform=x11|wayland|win32|cocoa|null` l'impose. Sous Wayland le compositeur place les fenêtres : ni position lue ou fixée (pas de centrage, pas de retour à la position fenêtrée, `monitors` ne connaît l'écran que d'une fenêtre en plein écran), ni `GLFW_FLOATING`, ni icône ; le moteur saute ces appels (`CanPlaceWindows`, `CanFloatWindows`, `CanSetWindowIcon`) au lieu de laisser GLFW lever `GLFW_FEATURE_UNAVAILABLE`.
- **Code d'une vue** : le moteur active le contexte GL de la fenêtre de la vue avant d'exécuter son code (`bindWindow` dans les `…ByManager` de `Scene` et `…ByContext` de `WindowView`) et le rend ensuite ; un objet créé dans une fenêtre (renderer, texte) peut être affiché dans une autre (VAO créé à la demande, voir « Contextes GL »), pas un `FrameBuffer`.
- Démo : `MultiWindowScene` (D : dialogue modal, T : fenêtre d'outils qui affiche le renderer de la fenêtre principale, C : second contexte avec `Scene2D`).

## Cycle de vie d'une scène
`init(args)` → (scène de chargement pendant les batchs) → `launch(args)` → `update()`/`postUpdate()`/`display()` → `unload()` → `release()`.
- Exemple commenté : `mightylibdemo/scenes/DocumentationScene` (batch `documentation`, `resources/data/documentationScene.json`, texture créée dans `init`, supprimée dans `release`).
- Paires : `launch` ↔ `unload` (seulement si `launch` a eu lieu, avec `super.unload()`) ; `init` ↔ `release` (toujours, même si quittée pendant le chargement).
- `init`/`launch` facultatifs, **sans `super`** : le moteur (`initByManager`/`launchByManager`) crée la scène de chargement, puis caméras et framebuffer virtuel avant `launch`. `init` déclare (ressources préchargées), `launch` crée les renderers.
- Menu de la démo (`MenuScene`) : à gauche `GUIList` de boutons (Scene2D, Scene3D, Scene3DBis, Quit), à droite `ScrollList` (`graphics/GUI`) de toutes les scènes. `ScrollList` : liste verticale défilée à la molette, seules les lignes visibles existent en GL (pool de `BackgroundlessButton` remplie au défilement), survol, barre de défilement ; la sélection au clavier n'y est pas gérée. Activation : chaque `GUI` a un déclencheur (`setTrigger(EInputState)`, `Pressed` par défaut ou `Released`) et `isActivated(inputManager, actions...)` ; `GUIList.getActivated()` et `ScrollList.getActivated()` renvoient l'élément activé à ce tick après `setupActivationActions(actions...)`. `InputManager.isInput(id, EInputState)` choisit Press, Release, Pressed ou Released par une valeur d'enum. La liste des scènes est écrite en dur dans `MenuScene.createSceneEntries` : une nouvelle scène de démo s'y ajoute.
- Scène de chargement : `EngineConfig.setLoadingScene` (défaut `DefaultLoadingScene`, fond gris) ou `createLoadingScene(args)` (`null` = rien) ; elle reçoit le `sceneManagerInterface` de la scène chargée et peut changer de scène (démo : Échap → menu, la scène en cours de chargement est déchargée). Surface virtuelle : `createVirtualSceneBindable()`.
- Ressources : surcharger `getInvolvedBatch()` (fichiers de `resources/batchs/`). Changement de scène (`SceneManager.changeScene`) : `unload` de l'ancienne scène, `loadBatch` de la nouvelle, puis `unloadBatch` de l'ancienne et annulation du préchargement : ce que les deux partagent (données et éléments GL) n'est jamais libéré entre-temps. `Scene.unload` n'appelle `unload` qu'une fois par objet (ajouté comme updatable et displayable).
- `display()` : `setVirtualScene(); clear(); …; setAndDisplayRealScene();`. Changer de scène : `sceneManagerInterface.setNewScene(new XScene(), args)`. `postUpdate()` remet à zéro les états pressed/released.

## Ressources CPU (`Resources`)
- Type = `DataType` + `ResourceLoader` (`Resources.Loaders` ; projet : `ProjectLoading.init`). Accès : `resources.getResource(TextureData.class, "nom")` (`resources` : champ de `Scene`, `Views.engine().resources()` ailleurs). Nom = fichier sans extension → **unique par type**.
- États : créé → **preload** (`initWithFile` : disque, dépendances) → **load** (`internLoad`, dépendances chargées) → unload (`internUnload`, ou `internCancelPreload`).
- `TYPE_SET_UP` : `THREAD_CONTEXT` (workers, ≤ `maxThreads`), `MAIN_CONTEXT` (thread principal, dans le budget de la frame), `THREAD_PRELOAD_MAIN_LOAD` (lecture par un worker, calcul sur le thread principal : `Shader`), `IMMEDIATELY_IN_CURRENT_CONTEXT` (dans l'appel, ex. descriptions de batchs). Unload toujours sur le thread principal. Une étape en file est vérifiée **au moment de démarrer** (`stepStillNeeded`) : donnée plus voulue (scène quittée, copie abandonnée) ou à relire → sautée (`skippedSteps` dans `resources`), puis `update` la vide ou la relance ; voulue à nouveau entre-temps → étape gardée. Un chargement peut se faire en plusieurs étapes : `internLoad` renvoie `true` et `loadContinues()` aussi, `Resources` relance alors `internLoad` comme une nouvelle étape (les autres étapes passent entre deux) ; `Shader` compile vertex, fragment, geometry puis lie, une étape chacun ; abandonné en route, il est libéré par `internCancelPreload`. Une étape commencée va au bout (ou s'arrête à `checkCancelled()`). Sons : un `SoundDecoder` par format (`resources/sound/decoder` : ogg = STB Vorbis, wav = `javax.sound.sampled`, mp3 = JLayer (LGPL), flac = `FlacStream` écrit pour le moteur ; `SoundLoader.addDecoder` en ajoute, le dernier ajouté gagne pour une extension) ; les noms de ressource sont ceux des fichiers sans extension (deux fichiers de même nom : avertissement). `SoundDataType.readVorbis` décode par morceaux (`DECODE_CHUNK_SAMPLES`) avec `checkCancelled()` entre deux ; le PCM est en mémoire native (`SoundLoadInfo.nativeBuffer`), libéré par `SoundLoadInfo.release()` après l'envoi à OpenAL ou par `SoundData.internCancelPreload`.
- **Priorités** : une donnée voulue maintenant (batch chargé, code, dépendance d'une donnée voulue) est *urgente* ; celle qui n'a que des références `preload:` passe après (file à deux niveaux dans `ResourceScheduler`, promue en O(1) quand elle devient urgente ; un worker reste libre pour les urgentes). `finishedCurrentLoading` ne compte que l'urgent : un écran de chargement n'attend pas le préchargement. API : `Resources.preloadBatch`/`cancelPreloadBatch`, `SceneManagerInterface.preloadScene` (scène `PreloadScene`) ; `loadBatch` après un préchargement ne recharge rien.
- **Budget de frame** : `MainLoop` donne une échéance commune à `Resources.processUntil`, `MainThread` et `GLResources` ; sous un écran de chargement le chargement a toute la frame, sinon `EngineConfig.setInGameLoadingShare` (30 % par défaut, pour `Resources` et `GLResources` ; `MainThread` garde toute la frame). Chaque file fait au moins une étape par frame.
- **Poids et progression** : `DataType.estimatedCpuBytes`/`estimatedGpuBytes`, pour le debug seulement (taille décodée une fois lue : pixels des textures, échantillons des sons, tableaux des modèles ; avant lecture, taille des fichiers × un ratio par format : 4 pour les textures, 10 pour OGG/MP3, 2 pour FLAC ; sur la carte, les textures seules), commande `resources batch <nom>`, `Resources.wantedProgress()` ({fait, total} des données voulues maintenant ; l'écran de chargement de la démo affiche « LOADING x / n »).
- **Propriétaire unique** : seul le thread principal change références et états ; les appels d'autres threads (`addOwnedResource` depuis un loader, `addPreLoadedResource` depuis `internLoad`) passent par une file vidée par `process`. Un worker ne fait que lire/calculer. Une donnée ne lit aucun `Resources` global à sa construction : celui qui l'enregistre (création par les loaders, découverte, fallback, `addResourceAndSetUp`, `addPreLoadedResource`, `addOwnedResource`, copie de rechargement) s'y attache (`DataType.attachTo`), une seule fois ; `DataType.resources()` le rend, et échoue (`IllegalStateException`) tant que la donnée n'est pas enregistrée. `Model` ajoute et libère ses textures possédées auprès de ce même `Resources`.
- **Découpage de `Resources`** (façade, cycle d'état `update`/`startStep`/`endStep`/`fail`) : `ResourceScheduler` (files à deux niveaux, workers, échéance), `DependencyGraph` (dépendances, attentes), `ReloadManager` (rechargement à chaud), `BatchManager` (lots), `FallbackRegistry` (données de repli), `ResourceDescriber` (JSON de debug). Tous package-private, thread principal.
- **Réconciliation** (`Resources.update`) : voulue = référencée (sauf suppression/sortie). Une donnée dont une étape tourne n'est jamais modifiée ; à la fin, voulu/état est recomparé.
- **Dépendances** : une donnée voulue et préchargée référence les siennes (`dependency:<Type>:<nom>`, pas à lister dans le batch, gardées tant qu'elle est chargée ; `onlyAsDependency` dans `resources`) ; elle est réveillée quand l'une est chargée.
- **Échec** (`Resources.fail`, exception du loader, `internLoad` → `false`) : retour à l'état initial, dépendances rendues, pas de nouvel essai tant que voulue (sauf `reloadAllOfType`). Ceux qui attendent prennent le placeholder du type, sinon échouent en chaîne. Échec **attendu** (fichier manquant/illisible, format inconnu, contenu mal formé) : le loader lève `ResourceException` (sans pile ; `FileMethods.readFileAsString`/`readJSONObject`, `IconLoader`, `FontFile.load` le font) → une ligne ; toute autre exception = bug → pile complète (`Logger.LogException`). Une icône en échec laisse l'icône par défaut.
- **Placeholders** (`ResourceLoader.createFallback`, nommés `error`, générés, chargés au démarrage, jamais déchargés/rechargés ; un placeholder en échec lève une exception) pour les types primaires : texture (damier magenta/noir, + version rectangle), son (bip), shader (magenta), police (carrés), animation (une image), modèle (cube). Types complexes (JSON, CSV, tilemaps, tilesets, batchs…) : `null`, plantage accepté. `Resources.usable(type, donnée)` = donnée si chargée, sinon placeholder (échec **ou chargement en cours**) ; `getResourceOrFallback` pour un nom inconnu (signalé une fois). Les utilisateurs (`Texture`, `SoundSource`, `Shape`, `Text`, `Animation`, `ModelRenderer`) résolvent à l'usage : une donnée chargée plus tard ou relue avec succès remplace le placeholder. Placeholder signalé une fois, à l'échec ; `resources` liste `usingFallback`.
- **Mode strict** (`EngineConfig.setStrictResources`, `-Dmightylib.resources.strict=true`, `scenario.py --strict`, debug seulement) : échec ou nom inconnu → exception.
- Références par nom (batch, `preload:<batch>` pour un préchargement, `"manually"`, `"all"` pour `loadAllOfType`, `dependency:<Type>:<nom>`, propriétaire) ; liste, doublons permis.
- **Rechargement à chaud** (`Resources.reload(donnée)`, `reloadAllOfType`, commande `reload`) :
  - donnée **chargée** jamais vidée : `DataType.createReloadCopy` → copie lue à part (`reloading` dans `resources`), puis `swapContent` (identité et références gardées), la copie décharge l'ancien contenu. **Échec = version précédente gardée** (exception en strict). Nouveau `reload` pendant la lecture : nouvelle copie lue tout de suite, l'ancienne abandonnée (plus voulue : son étape en cours s'arrête au prochain `checkCancelled()` du loader, sinon va au bout et son résultat est jeté ; si elle attendait ses dépendances, libérée aussitôt) ;
  - **annulation** : `update` pose le drapeau `cancelled` d'une donnée dont l'étape en cours est inutile (plus voulue, relecture demandée) ; le loader l'interroge par `checkCancelled()` (`CancellationException`, silencieuse, comptée dans `skippedSteps`), à placer avant la phase coûteuse ;
  - **copies bornées** (`Resources.setMaxReloadCopies`, 32 par défaut) : au-delà, la donnée reste utilisable avec l'ancien contenu et attend une place (`ReloadManager.mustWait`/`wakeDeferred`) ;
  - `DataType.getVersion()` augmente à chaque changement ; les utilisateurs comparent leur version (`Texture`, `TileMapRenderer`, `Text`, `ModelRenderer`), pas d'écouteurs ;
  - les `dependents` (via `DependencyGraph.acquire`) sont relus en chaîne (texture → tileset → tilemap, atlas → police), chacun attend ses dépendances (`DependencyGraph.allReady`) : un seul calcul par donnée lors d'un `reload all` ;
  - non relues : sans source (`hasSource()` faux), préchargées par le code, placeholders ; recalculées (sauf placeholders) si une dépendance change. Une donnée en échec ou en premier chargement est relue sur place ;
  - type sans copie (`createReloadCopy` → `null` : mods, sous-types) : vidé puis relu sur place (signalé une fois). Un sous-type n'hérite pas de la copie du parent ;
  - batch : `loadBatch` garde sa liste, `unloadBatch` libère exactement celle-là ; description relue pendant qu'il est chargé → ajouts chargés, retraits libérés ; description citant une donnée inconnue non appliquée (vaut aussi pour un batch préchargé) ;
  - **observateur de fichiers** (`Resources.watcher()`, `ResourceWatcher`) : **éteint par défaut**, démarré explicitement par le code (`watchAll()`, `watchType(...)`, `watch(ResourceSelection)`), la commande `watch` ou `-Dmightylib.resources.watch=poll|service` (`EngineConfig.setWatchResources`, intervalle `…watch.interval` en ms). Une `ResourceSelection` (réutilisable ailleurs, ex. batchs) = tout, ou un type, + noms et/ou regex sur le nom (nom dans la liste OU regex) ; les sélections s'additionnent. Seules les données chargées (ou en échec) avec fichier (`DataType.sourcePaths()`), ni placeholders ni créées par le code. Modification ou création → `Resources.reload` (les dépendants suivent) ; suppression ignorée (version gardée, une ligne). Changement rapporté quand le fichier est stable 200 ms (éditeurs qui écrivent en plusieurs temps). Détection (`FileChangeDetector`, thread démon) : **scrutation** date/taille à chaque intervalle (défaut 1 s, marche partout) ou **WatchService** (moins coûteux, non récursif : un enregistrement par dossier, repli sur la scrutation d'un dossier non enregistrable). Liste des fichiers suivis rafraîchie chaque seconde. **Regroupement** : les changements d'une même donnée (description + sources écrites l'une après l'autre) sont rechargés une seule fois, 300 ms après le dernier. **Fichiers nouveaux** : les dossiers de `resources/` sont suivis aussi (date du dossier / `WatchService`) ; un dossier modifié lance `Resources.discoverNewFiles` (thread du détecteur, `ResourceLoader.discover`, par défaut `create`) puis enregistre sur le thread principal les données absentes que la sélection accepte, et rafraîchit les batchs chargés (motifs). `TextureDataLoader.discover` ajoute les images de `textures/` absentes de `textures.json`, avec les paramètres par défaut de `TextureData` (realistic, 2D) et un avertissement. Limite : fichier déposé dans un sous-dossier créé il y a moins d'une seconde, vu au prochain changement de dossier. Tests : `FileWatchTest` ;
  - nouveau type : implémenter `createReloadCopy` (copier les réglages donnés par le code, ex. `TextureData.copySettingsFrom`) et `swapContent` (échanger tout ce que lisent `initWithFile` et `internLoad`).
- Commande `resources` : par type, chargées/préchargées/référencées, mémoire estimée (`cpuBytes`/`gpuBytes`, totaux), chargées sans référence (fuite), référencées non chargées, état du pipeline (dont `wantedDone`/`wantedTotal`, étapes de préchargement) ; `resources batch <nom>`, `resources preload|unpreload <batch>`. Tests : `Resources*Test` (base `ResourcesTestBase` ; batchs, annulation, dépendances, échecs et repli, ressources manuelles, rechargement, préchargement, cycles aléatoires).

## Ressources GPU (`GLResources` / `GLElement`)
- Objets GL partagés et comptés, clé = classe + nom : `addElementOrReturnIfPresent()` ajoute une référence urgente (à équilibrer par `releaseResource()`) ; `getResource()` cherche sans référencer. Libérer plus que référencé (objet déchargé deux fois) est refusé avec une ligne d'erreur.
- **Éléments des batchs** : une donnée listée directement dans un batch fait envoyer son élément GL pendant le chargement (`DataType.glElementType`/`glElementName`/`createGLElement` : `TextureData` → `Texture` de même nom, `TileMap` → texture de son atlas `tilemap:<carte>`, celle de `TileMapRenderer`) ; une entrée de batch s'en exclut par `"gpu": false` (ex. textures de tilesets dans `init.batch`, qui ne servent qu'à construire l'atlas) ; une dépendance n'est pas envoyée. `BatchManager` tient une référence par chargement de batch (via `IGLElementSink`, implémenté par `GLResources` et donné à `Resources` par `MainLoop` ; absent dans les tests de `Resources`), rendue par `unloadBatch`/`cancelPreloadBatch` ou une nouvelle description. Les renderers trouvent l'élément déjà chargé : `launch` n'envoie que ce qui n'est pas dans les batchs.
- **Urgence** : un élément est urgent s'il a une référence urgente (renderer, batch chargé) ; sinon préchargé (`preload:<batch>`). Deux files ordonnées (`LinkedHashSet`, passage de l'une à l'autre en O(1)) : `process` passe les urgents puis les préchargés ; `hasElementsToLoad` ne compte que les urgents (`gl summary` : `waitingToLoad`/`waitingToPreload`). À la sortie, `unload` supprime aussi les éléments encore référencés.
- **Jamais bloquant** : l'ajout met en file ; après chaque `display()`, `GLResources.process(deadline)` avec l'échéance du chargement (toute la frame sous un écran de chargement, part `setInGameLoadingShare` sinon), au moins une étape ; plafond `EngineConfig.setMaxGLUploadMillisecondsPerFrame`. `GLElement.load(ms)` renvoie `false` tant qu'il n'a pas fini. Une étape peut libérer d'autres éléments (`releaseResource` les retire des files en cours de parcours). Tests : `GLResourcesTest` (sans GL).
- `Texture` : > 4 Mio (2D) envoyée par bandes `glTexSubImage2D` (256 Kio–4 Mio selon débit mesuré et temps restant). Non chargée (en cours/échec) → `bind` du placeholder de même type (1×1 transparent tant que le placeholder n'est pas envoyé) ; `hasElementsToLoad` ignore les échecs. Donnée rechargée (version différente au `bind`) → renvoyée dans une seconde texture GL (`GLElement.requestReload`/`reload`, même budget) qui remplace l'ancienne une fois complète. `getWidth/getHeight` = taille affichée ; ce qui en dépend attend `Texture.isUpToDate()` (ex. `TileMapRenderer` garde ses tuiles, animations en pause).
- `ModelRenderer` : une version = un `MeshSet` (une `Shape` par mesh, ses textures), un mesh par frame ; une nouvelle version remplace l'affichée une fois complète. La `Shape` de base ne sert qu'au shader.
- Atlas d'une `TileMap` (`TileSetAtlas`, texture `tilemap:<carte>`) = contenu de la carte construit dans `internLoad`, échangé au rechargement.
- Son rechargé : `SoundData.internUnload` détache le buffer des sources (`Resources.detachSoundBuffer`, branché sur `SoundManager` par son constructeur) avant suppression.
- Chargement de scène : l'écran de chargement reste tant que `GLResources` a des éléments urgents (ceux des batchs de la scène et ce que `launch` a demandé) ; avertissement après 10 s.
- Renderers 2D utilisables dès le constructeur ; géométrie envoyée au premier `display()` puis après chaque modification.
- **Toujours** `GenDeleteResources` (VAO, VBO, EBO, textures, FBO, RBO ; VAO, FBO et RBO sont supprimés dans le contexte qui les a créés), jamais `glGen*`/`glDelete*` (`PrintAll()` au changement de scène).
- **Contextes GL** (`graphics/GLContext`, thread principal) : un contexte racine caché (créé avec la première fenêtre, détruit après la dernière) crée le groupe de partage ; chaque `Window` a son `GLContext` et partage ses objets avec lui. **Partagés** (créés une fois, utilisables dans toutes les fenêtres) : textures, VBO, EBO, PBO, programmes (`Shader`) → `Resources`/`GLResources` restent uniques. **Propres à un contexte** : VAO, FBO, RBO, programme lié (`currentProgram`). `GenDeleteResources.Gen*` enregistre un VAO/FBO/RBO dans le contexte courant ; sa suppression prend le contexte propriétaire (`DeleteVertexArrays(owner, id)`) : immédiate s'il est courant, au prochain `makeCurrent` sinon, ignorée si sa fenêtre est détruite. `Count`/`PrintList` additionnent les contextes vivants. `Window.bindWindow()` = `GLContext.makeCurrent()` (fait aussi `GL.setCapabilities`). `GLResources.process` termine par `glFlush` quand plusieurs fenêtres existent (ce qui est envoyé n'est visible des autres contextes qu'une fois les commandes émises).
- **`Shape`** a un VAO **par contexte**, créé au premier `bind()` dans ce contexte et reconstruit depuis la description des attributs (`vbosVertexSize`, `vbosInteger`, `vbosEnable`, EBO) quand elle change (`layoutVersion`) : un renderer s'affiche dans n'importe quelle fenêtre du groupe. `FrameBuffer` reste lié au contexte qui l'a créé (`bindFrameBuffer` le vérifie sous `Logger.DO_CHECK`). Une création de fenêtre qui échoue est signalée par le callback d'erreur GLFW et la fenêtre reste « non créée ».

## Rendu
- `Shape` = VAOs (un par contexte GL) + VBOs (+ EBO) + `Shader` ; canaux 0 position, 1 UV, 2 normales. `Renderer` = `Shape` + transform (→ `model`) + `ShaderValue` envoyées à chaque `display()`.
- `Shader.sendValueToShader` ne renvoie qu'une valeur changée ; uniform absent du programme signalé une fois et ignoré.
- Uniforms génériques : `projection`, `view`, `model`, `color` (`ShaderManager`). Shaders listés dans `resources/shaders/<3_30|1_40>/shaders.json` ; **un nouveau shader existe dans les deux versions**.
- 2D/3D décidé par le shader (`isDimension2DShader`), qui bascule le depth test à chaque dessin.

## Entrées
- IDs d'action `int` statiques (`InputManager.getAndIncrementId()`, 0 et 1 réservés : `COMMAND`, `RELOAD_TEXTURE`). Projet : `ActionId` + liaisons dans `ProjectLoading.contextLoading`. Disposition clavier : `EngineConfig.setKeyboardLanguage()` (QWERTY par défaut, et pour un contexte créé sans `WindowCreationInfo`).
- **Manettes** : un `GamepadManager` commun (`Engine.contexts().getGamepadManager()`, ou `InputManager.getGamepadManager()`), mis à jour par `ContextManager.postUpdate` avant les entrées des fenêtres (chaque fenêtre a son `InputManager`) ; GLFW (`glfwGetGamepadState`, disposition Xbox, SDL_GameControllerDB intégrée, `addMappings`) derrière `IGamepadSource` (fausse source en tests).
  - Emplacements 0–15 = joysticks GLFW, 16+ = 8 virtuelles. Connexions appliquées dans `postUpdate` (ensemble stable par tick ; `connectedThisTick()`/`disconnectedThisTick()` durent un tick).
  - Joueurs : plus petit libre, repris à la reconnexion s'il est libre ; `setAutoAssign(false)` + `assignPlayer` pour « appuyez pour rejoindre ». Sans mapping : connectée sans joueur.
  - `Gamepad` : ids GLFW ; sticks -1..1 (y vers le bas), zone morte radiale remise à l'échelle ; gâchettes 0..1.
  - Actions : `InputGamepadButton(bouton[, joueur])`, `InputGamepadAxis(axe, POSITIVE|NEGATIVE[, seuil, joueur])`, `InputSimple(bouton, EInputType.Controller)` ; sans joueur = `ANY_PLAYER`.
- **Valeur** : `InputManager.getValue(action)` 0..1 (1 pour touche/bouton/simulé, progressive pour `InputGamepadAxis` sans seuil ; `InputOr` = max, `InputAnd` = min). Déplacement : `getValue(droite) - getValue(gauche)`, longueur limitée à 1 (cf. `MovingCameraComponent`).
- **Axes** (`AxisInput(id, nom, IAxis)`, `inputManager.init(actions, axes)`, `getAxis(id)`) : valeur signée non bornée, sens donné par la liaison ; ids du même compteur (cf. `AxisId`).
  - Liaisons : `AxisGamepad(axe[, joueur])`, `AxisMouse(X|Y|SCROLL_X|SCROLL_Y)` (pixels de fenêtre pendant le tick, `MouseManager.deltaX/Y`, indépendant de la taille virtuelle), `AxisButtons(nég, pos)` (sans double comptage via `InputOr`), `AxisSum(...)`.
  - Réglages, dans l'ordre : `curve(exposant)` (signe gardé ; 2 = précis près du centre), `scale(facteur)` (négatif = inversion), `perSecond()` (× durée du tick : vitesse → déplacement). `scale` sur `AxisSum` = sensibilité commune : regard de la démo = `AxisSum(souris px, stick × 3000 px/s).scale(0.05 °/px)`.
- **Caméra 3D** : `Camera3D` ne lit pas les entrées (`rotate(dYaw, dPitch)` en degrés, droite et haut positifs, tangage ±89°). `FreeCamera3DComponent` (`addUpdatable`) la pilote par axes (déplacement -1..1 × `camera.getSpeed()`, regard en degrés, × `quickFactor` avec `QuickSpeed`) et met la vue à jour avant le code de la scène ; `setLookLocked` bloque le regard.

## Pièges connus (non corrigés)
- Sous Wayland, une sous-fenêtre n'est liée à son parent ni par la position ni par l'empilement (GLFW n'expose pas `xdg_toplevel.set_parent`) : un dialogue peut passer derrière la fenêtre principale ; `BORDERLESS` ne choisit pas son écran.
- Une `TileMap` relue perd les changements faits par le code (`setTileType`).
- 2D sans batching : chaque `Shape2DRenderer`/`Animation2DRenderer`/`Text` a VAO/VBO/EBO et draw call, avec `glUseProgram`, uniforms et depth test à chaque dessin.
- `Shape.updateVbo` réutilise le buffer à taille égale (`glBufferSubData`), sinon réalloue ; les `calculate*()` allouent un `float[]` à chaque appel.
- `TileMapRenderer` : une animation de tuile ne réécrit que ses UV, mais toute modification de carte (`hasBeenUpdated()`) reconstruit tout.
- `Shape2DRenderer` alloue en `STATIC_STORE` même pour des VBO modifiés.
